# HA State Model — taxonomy, transactions, failure semantics, budgets

This document is the normative companion to [ADR-0007](../adr/0007-shared-state-and-ha-modes.md). It defines the state taxonomy, transaction and ordering rules, failure matrix, leader/fencing semantics, privacy model, and blocking budgets for issue #241's implementation PRs. Each PR cites this document rather than restating it; changes here are review-blocking for any PR that depends on the changed section.

## 1. State taxonomy

Every piece of mutable state is classified into exactly one row. A PR that introduces new shared state must add it here first.

| State | Standalone authority | Cluster authority | Consistency requirement |
| --- | --- | --- | --- |
| Policy document, ETag, history | Local file + compiled snapshot + SQLite history | Versioned PostgreSQL document; CAS by revision/ETag; document + history + audit outbox commit atomically | Linearizable; strict per-request revision |
| Tool definitions (and Connections per #240) | Local file/process snapshot | Same versioned CAS/revision/outbox contract as policy | Linearizable; strict per-request revision |
| Connection change evidence (#425) | None: the admin audit event after the commit is the only attribution | Since migration 16, one append-only `connection_change_evidence` row per committed Connection delete, written in the deleting transaction beside the unchanged outbox tombstone: actor, action, event and operation UUIDs, prior version, the tombstone's shared revision and database-clock `committed_at`. No foreign key, so it survives the cascade; identifiers only, no specification or secret material | Exists exactly when the delete committed; a refused, stale, raced or rolled-back delete leaves none. Not yet delivered downstream or pruned (later #425 slices) |
| Service tokens | SQLite + per-process caches | PostgreSQL rows; atomic create/rotate/revoke; authoritative check on every request | Revocation effective on next request cluster-wide |
| Service-token and JWT revocation change evidence (#425) | One append-only `service_token_change_evidence` row per committed rotate/revoke inside the token database's own transaction: actor, action, event and operation UUIDs, token ID, commit time | Since migration 18, `service_token_change_evidence` (actor, action, event and operation UUIDs, prior and new row revision, the outbox row's shared revision, database-clock `committed_at`) beside each rotate/revoke outbox row, and `jwt_revocation_evidence` (actor, issuer, `jti` digest, resulting expiry, shared revision) for each JWT revoke that changes the denylist. No foreign keys: removing a token row, extending or reactivating a revocation, and expiry cleanup leave the evidence; identifiers only, no token material or raw `jti` | Exists exactly when the change committed; a repeat revoke, a refused rotate or a refused JWT revoke leaves none. Not yet delivered downstream or pruned (later #425 slices) |
| JWT revocations | Production no-op store today | PostgreSQL rows keyed by normalized issuer + hashed `jti`, with expiry | Required-check failure is `503` |
| OIDC pending login (state/nonce/PKCE) | Process-local map in standalone mode (sticky sessions); PostgreSQL in cluster mode since PR 9 | Hashed lookup + AEAD-encrypted fields; single atomic consume; DB-time expiry and quotas | Exactly one callback consumes a login, on any replica |
| Admin sessions (#424, ADR-0009) | `ADMIN_SESSION_MODE=standalone_memory`: a bounded process-local map; restart ends every session | `ADMIN_SESSION_MODE=cluster_postgres` since migration 19: rows keyed by a digest of the session cookie, the access token AEAD-sealed under the login keyring, the CSRF token kept as a digest; pending cookie logins shared so logout on any replica cancels them; absolute and idle deadlines on database time; the row read on every request and a conditional admit after the provider check; admissions under one advisory lock with a bounded prune; one append-only `admin_session_evidence` row per grant and withdrawal in the change's own transaction | Logout, replacement, a rejected token and an identity change are effective on the next request cluster-wide; a store failure is `503`, never `401` |
| Rate-limit buckets | Process-local bounded store (per #338) in standalone mode; PostgreSQL GCRA in cluster mode since PR 10 (local buckets stay as the per-replica emergency bound) | Atomic PostgreSQL operation on database time; HMAC'd keys; bounded cardinality | One burst of N permits N across the cluster |
| Tool/global concurrency | Process-local semaphores in standalone mode; PostgreSQL leases in cluster mode since PR 10 (semaphores stay as the per-replica bound) | PostgreSQL leases: expiry, renewal, cancellation, fencing | A stale holder cannot commit after a successor fences |
| Audit events | stdout/file/SQLite sinks | Idempotent PostgreSQL event log written by every serving replica's own sink since issue #11 PR 3 (`audit/postgres_sink.rs`: a bounded buffer the writer thread pushes onto, a flusher task that batches it through the store's single `ON CONFLICT (event_id) DO NOTHING` write path off the request path, bounded retry then drop-and-count under `audit_events_dropped_total{reason="postgres"}`, a flush on drain bounded by the drain's own deadline, and a batch transaction that rolls itself back if cancelled mid-way so no pooled connection is ever returned holding the stream lock) beside stdout and the optional file, and by `gateway import-standalone`; commit-safe durable cursor | At-least-once with exactly-once storage via `event_id`; a served request's row lands on the sink's next accepted batch (every 200 events or 250 ms while the authority accepts writes; a refused or lock-blocked batch lands only after its retries, and is dropped and counted past them — the gate suites poll for the rows under a convergence budget rather than asserting a latency), and a cleanly stopped replica's before it exits, its drain reporting success within `AUDIT_DRAIN_TIMEOUT_MS`; every row carries the writing replica's instance and boot identity |
| Discovery observations, endpoint inventory, detector state, signals | Local working set + SQLite snapshots (the audit-writer-thread aggregator) | Since PR 11: observations are the durable audit stream's `http.request_observed` events (idempotent by event ID); one checkpointed, fenced global projector (execution-lease slot `discovery-projector`, fence verified in every flush transaction) fills the shared discovery tables, persists its detector windows and learned templates, and is the only evictor; every replica reads the tables through one read store; the request path reads a refreshed snapshot, never the authority | Replays never inflate counts; projector failover loses nothing and continues the same detector windows; a signal identity opens once cluster-wide |
| Principals/reviews/signal and suggestion transitions/suggestion generation | Local working sets + SQLite snapshots | Since PR 12: every signal, suggestion, and endpoint review row carries a `revision`, and each transition is one conditional statement (the state is one the transition leaves — dismissal leaves `open` or `acknowledged`, everything else leaves exactly one — and, when the caller names one, `revision = <expected>`) — a refused transition returns the row as it stands and writes nothing; a cleared review keeps its row so an endpoint's review revision never restarts and a stale `If-Match` cannot match a later review; suggestion acceptance is the single transaction of rule 7; suggestion generation runs against the projected tables, the durable audit stream and the policy AUTHORITY (never the replica's snapshot), idempotent by suggestion identity | Two replicas transitioning one row produce exactly one winner; acceptance is all-or-nothing; regeneration inserts nothing new |
| Membership/revisions | None | `cluster_members` row per replica since PR 13: heartbeat every `CLUSTER_HEARTBEAT_MS`, static-config fingerprint, schema/document version ranges, compiled/observed security revisions, ready/draining stamps, and since migration 17 the closed capability set the replica implements (§7); liveness judged on database time against `CLUSTER_MEMBER_STALE_MS`; stale rows swept only by the maintenance singleton | A joining replica whose fingerprint differs from a live member's is never ready (`config_fingerprint_mismatch`) until they agree |
| Contract fence and backfill ledger (#426) | None: one process is the only reader | Since migration 20, one forward-only `contract_fence` row (minimum schema, required capabilities, generation; a trigger refuses lowering, removal and truncation) and one `schema_backfills` row per named backfill (`running`, `verified`, `failed`). Raised only by admitting an operation that declares a durable fence, in one transaction holding the migrator's advisory try-lock and the row `FOR UPDATE` while it reads the ledger, the backfill and the roster | Linearizable against membership: every heartbeat decides under `FOR SHARE` on the same row, so no member joins behind a raise that did not count it; checked at startup, every heartbeat, and every gated write |
| Readiness decision and the status view | Process-local: the lifecycle phase and the required upstream pools, which are the only two rungs `/readyz` has | Since PR 14 the same two rungs plus four authority-backed ones — the fingerprint gate (PR 13), one bounded history/checksum and writability read cached for `READINESS_PROBE_CACHE_MS`, this replica's own membership heartbeat age against `CLUSTER_MEMBER_STALE_MS`, and its compiled-versus-observed security watermark against the reconcile deadline. Derived state only: the probe writes nothing, holds no lease, and reads no other replica's row for its own decision | One coarse reason evaluated in the failure matrix's order and stopping at the first condition that holds; `/readyz`, the cluster status API's `state`/`reason`, and the readiness metrics are the same evaluation, so they cannot disagree |
| Maintenance leader / job ownership | Inline housekeeping (SQLite audit retention timer, pending-login prune on insert) | One `maintenance` lease slot (capacity 1, TTL `CLUSTER_MAINTENANCE_LEASE_TTL_MS`) since PR 13; `maintenance_jobs` ledger written only `WHERE fence = <holder's fence>` and while the lease at that fence is live on database time; each pass under a dedicated session-scoped advisory lock whose connection runs every job statement | Unfenced singleton work is a defect; a stale leader's late ledger write is refused from the instant its lease lapses |
| Audit retention (PostgreSQL) | `AUDIT_SQLITE_RETENTION_DAYS` timer | Bounded per-pass deletion by the leader past `AUDIT_POSTGRES_RETENTION_DAYS`, oldest stream position first, never at or past the retention floor (the discovery projector's committed checkpoint, PR 11); the position counter survives so cursors keep their meaning | Retention never removes an event a durable consumer has not applied |
| JWKS/introspection caches, upstream health/clients/pools | Process-local | Remain process-local, bounded, with explicit freshness contracts | Never shared; staleness bounds are configuration |

Classification rule: if incorrect or stale values for a field could produce a stale **allow** (authorization, revocation, replay, admission, limit), the field is *security state* and follows the strict revision discipline. Everything else is *observational state* and may lag visibly without blocking protected traffic.

## 2. Transactions, ordering, and revisions

1. **Control-plane mutations** (policy, tools, connections, token lifecycle, revocation, review/signal/suggestion transitions) run as one transaction: lock/read expected revision → reject stale `If-Match` with `412` → fully validate the candidate → write the immutable new version → advance the active pointer and the monotonic **security revision** → write history/lifecycle rows → write the audit outbox row → commit. If any step fails, nothing commits; two writers with the same expected revision produce exactly one winner.
2. **A mutation is not successful unless its audit is durable.** Outbox insertion failure rolls back the mutation.
3. **Read path:** every protected request reads the current security revision from the primary after the request starts; a compiled snapshot is usable only keyed by that exact revision; un-reconciled means bounded wait then `503`. The request records the revision it served under in audit.
4. **Notifications are hints.** `LISTEN/NOTIFY` reduces latency; durable revision/change rows plus periodic reconciliation provide correctness, including across listener loss and replica restart.
5. **Database time is authoritative** for expiry, retention, rate math, leases, heartbeats, and fencing. Wall-clock skew is monitored (JWT validation still uses it) but never decides shared-state expiry.
6. **Audit cursor ordering must be commit-safe.** A bare sequence assigned pre-commit can be skipped by a late-abort; the cursor design (serialized post-commit sequencing or equivalent) must prove no permanent gap under concurrent and aborted transactions.
7. **Suggestion acceptance is one transaction**: the suggestion row is locked and re-checked still open (and at the caller's expected revision, when given), exactly one policy rule/version is added, history appends, the security revision advances, the audit outbox row is written, and the suggestion transitions to `accepted` — all under one commit. No partial success exists: a stale policy `If-Match`, a suggestion another replica moved first, or a crash anywhere in between rolls back both halves. The outbox row is the durable audit record of rule 2; the emitted `policy.changed` and `suggestion.lifecycle_changed` events follow the commit, at-least-once, because an event describing a rolled-back acceptance must be impossible while losing the events of a committed one is tolerable. Since PR 12 this holds in cluster mode by construction, where the row lock excludes every other replica. Standalone mode keeps its sequence (validate, write the policy file, conditional transition), which is not itself atomic: one process serves many concurrent admin requests, so the gateway serializes suggestion lifecycle writes with a process-wide lock held across all three steps. A concurrent dismissal therefore runs entirely before the acceptance reads the row (and the acceptance is refused having written nothing) or entirely after it, never between the policy write and the transition.

## 3. Failure semantics (normative matrix)

| Condition | Readiness | Protected request / admin write | Recovery |
| --- | --- | --- | --- |
| Invalid/missing cluster config; dirty/incompatible schema; fingerprint mismatch | Never ready; startup fails where deterministic. A replica that meets one of these while already serving answers `config_fingerprint_mismatch` or `schema_incompatible` | No serving | Operator correction; no fallback |
| PostgreSQL unavailable at startup | Live-not-ready for transient failure (`starting`, since the lifecycle is not accepting work yet), or exit per bounded startup policy | No protected serving | Bounded-backoff retry |
| Primary lost / read-only / pool exhausted at runtime | `storage_unavailable` by the authority deadline — the probe's observation is at most one `READINESS_PROBE_CACHE_MS` window old, and a session that reached a standby or a read-only primary is this condition, not a healthy one | `503`, zero upstream attempts, no partial mutation | Reconnect, reconcile exact revision, then ready |
| Notification lost / listener reconnect | Ready while per-request revision checks still succeed | Correctness unchanged; polling catches up | Durable reconciliation |
| New security revision not locally compiled | Not ready for affected protected work: `security_revision_not_compiled` once the gate has been refusing every admission for longer than the reconcile deadline. Inside the deadline the replica stays ready and the status view reports `degraded` with `security_revision_lagging` | Bounded reconcile wait, then `503`; never stale allow | Fetch, validate, atomic swap; one admitted request clears the condition and its timer |
| Non-security projector lag/failure | Readiness unaffected; the status view reports the projector's `checkpoint_position`, `lag_events`, `leader_present`, and `last_flush_age_secs` | Discovery views show lag | Fenced leader resumes from checkpoint |
| Two administrators decide one signal, suggestion, or review from two replicas | Both replicas stay ready | Exactly one conditional write applies; the loser writes nothing and gets `409` with the row as it now stands and a stable reason (`*_not_open`, `*_revision_mismatch`); a losing acceptance's policy commit is rolled back with it | Re-read the row and decide again against the revision just returned |
| Audit outbox failure during a control mutation | May remain ready | Mutation rolls back; `503` | Retry the whole mutation with the same precondition |
| Data-plane audit queue saturation | Observable, and **ready**. This row previously promised a `strict` mode that becomes unready; no such setting exists, no code path makes a saturated queue unready, and `state_and_reason` has no queue-depth arm, so a saturated queue does not even report `degraded`. Corrected in PR 16 to what the code does. The status view reports `audit.queue_depth`, `queue_capacity`, `oldest_age_secs`, and `dropped_total` — the oldest age is the one depth hides, because a sink stuck on a single event has an empty queue behind it. The PostgreSQL sink behind the queue is bounded the same way: its buffer holds at most the queue's capacity, a batch the authority refuses is retried a bounded number of times and then dropped, and both drops count under `reason="postgres"` (issue #11 PR 3) | The data plane keeps serving; bounded and counted, never unbounded and never silent | Retry/drain; alert on age/drop, which is the only signal there is |
| Leader connection/lease lost | Replica may stay request-ready if no security prerequisite is affected; a job that recorded a failure on its last run shows in the status view as `degraded` with `maintenance_job_failing` | Stale job stops before its fence can be superseded (PR 13: a renewal that finds the lease gone, or half a TTL without an answered one, cancels the pass in flight; a lost dedicated session cancels the remaining jobs) | Successor elected with jitter (`interval/4 ± interval/8` from the instance ID) after the TTL lapses on database time; a draining leader releases at once |
| Member stops heartbeating (crash, partition) | Other replicas unaffected; the member itself answers `instance_lease_invalid` once its last **successful** heartbeat is older than `CLUSTER_MEMBER_STALE_MS`. One failed heartbeat is not the condition; a heartbeat that has been failing for longer than the window is | None from the row: liveness is a read-side judgement on database time | Row swept by the maintenance singleton after `CLUSTER_MEMBER_STALE_MS`; never by request handling and never by the member itself |
| Roster unreadable while the replica is otherwise healthy | Ready: an unreadable roster is not a reason to stop serving. The status view reports `degraded` with `replicas_unavailable` and empty replica counts rather than inventing a single-member deployment | Unaffected | The next read that answers restores the view; nothing is retried or cached |
| A live member reports a classified failure on its own row | Ready: the reporting replica's readiness is its own affair | Unaffected | The status view reports `degraded` with `member_error_reported`; diagnose from that replica's logs, not from the roster string, which is redacted to the classifier's fixed kinds |
| Replica partitioned from authority | Not ready; load balancer removes it. `storage_unavailable` first, then `instance_lease_invalid` once the stale window passes without a heartbeat landing | `503`, not stale local dispatch | Full revision/config/lease reconciliation |
| Rolling version/schema incompatibility | Incompatible replica never ready: `schema_incompatible` when ledger history or the explicit read/write contract fails, including a database with no ledger at all | Compatible replicas continue | Complete the migration with the old set stopped: no adjacent binary pair has been qualified across a schema change (§7) |
| The durable contract fence excludes this build | Never ready: startup is refused before any other authority state is read, and a running replica whose heartbeat the fence refuses answers `contract_fenced` for the rest of its life | Its gated writes refuse with `contract_fenced`; it writes nothing more to the roster, so it never counts as live again. Like every readiness refusal, requests still routed to it are not refused | Replace it with an eligible build; never lower the fence or rewind the database to readmit it (§7) |
| Shutdown/drain | Not ready immediately, with reason `draining`; the status view reports `state: "draining"` rather than `not_ready`, so an intentional drain is distinguishable from a fault at a glance | No new admissions; in-flight contract per #239 | Bounded flush/join and exit |

Two rows deserve emphasis because they are the ones reviewers will probe hardest: dependency failure is always `503` (never `401`/`403`, so "cannot check" is never laundered into "checked and denied"), and a partitioned replica never dispatches under a stale allow state — it stops.

## 4. Leadership, fencing, and singleton work

- No leader serves requests or control-plane writes; PostgreSQL transactions and CAS coordinate those. Leadership exists only for singleton maintenance jobs (migration, retention/partitioning, pending-login/revocation/limiter cleanup, discovery projection/compaction, scheduled suggestion generation).
- Short database-only work uses transaction-scoped advisory locks. Long jobs own a lease row with a monotonically increasing **fencing token**, renewed on database time; results are accepted only while owner-and-fence still match.
- Losing the dedicated session or the lease cancels local work *before* the lease can be reclaimed; a crashed holder's lease expires on database time; a stale holder's late write is rejected by the fence.
- Since PR 13 the periodic housekeeping (JWT revocation cleanup, rate-limit idle sweep, pending-login prune, stale member sweep, PostgreSQL audit retention, execution-lease reaping, and since migration 19 the admin session prune) is exactly this shape: one `maintenance` lease slot, a `maintenance_jobs` ledger adopted at the holder's fence and written only `WHERE fence = <that fence>`, one bounded step per job per pass, and a session-scoped advisory lock (`pg_try_advisory_lock`, never waited for) held by the pass's dedicated connection. `gateway maintenance-run` takes the same lease for one pass, so an operator's cron and the in-process singleton can never run side by side.
- Projector crash between read and commit yields neither loss nor double application: the successor resumes from the committed checkpoint, and observation ingestion is idempotent by event ID.
- Endpoint cardinality admission/eviction is global and fenced: one replica cannot evict an endpoint another replica's traffic still evidences.

## 5. Privacy model

- Notifications carry only deployment/resource identifiers and revisions — never payloads, principals, tokens, or paths.
- Rate-limit and quota keys are stored as HMAC digests, never raw tokens, IPs, principals, cookies, OIDC state, or JTIs.
- Plaintext service tokens appear exactly once (create/rotate response) and never enter logs, audit, traces, DB logs, or errors. OIDC state is stored as a hash; the PKCE verifier and nonce are AEAD-encrypted under operator-supplied keys with deployment/row/purpose bound as associated data.
- The DSN, database user/host/name, and secret-derived fingerprint values never appear in `Debug`, status, metrics, panics, or HTTP errors. SQL parameters never appear in error classes.
- No metric is labelled with instance IDs, principals, routes/hosts, token IDs, URLs, query text, or error strings.
- `/readyz` is unauthenticated, so it reports one coarse reason from the closed vocabulary above and nothing else — no error text, no SQLSTATE, no counts, no identifiers. The classified failure behind a reason is logged and, where it belongs to a replica's own background work, recorded on that replica's membership row; it is never returned to the probe.
- The cluster status API (`admin:cluster:read`) reports every string field only when the value is recognizably of that field's shape — a three-component semantic version, 64 lowercase hex characters, a UTC timestamp, one of the repository classifier's fixed error kinds, one of the singleton's fixed job names — and replaces anything else *whole* with `unknown`, or `null` for a timestamp. Recognition rather than filtering, because a filtered DSN still leaves an address behind. Every other field is a number, a fixed enum, or a UUID, so no DSN, database host/user/name, IP address, policy or tool content, query text, or raw error string can travel through it.
- The single exception is opt-in and self-only: `local.hostname` is `null` unless `CLUSTER_STATUS_EXPOSE_HOSTNAMES=true`, and even then carries only the reporting process's own hostname, bounded in length and character set. No membership column holds another replica's hostname, so the roster endpoint has none to expose at any setting.

## 6. Blocking budgets

These budgets bound what a protected request may spend talking to the authority. They are targets the release gate (PR 16) measures; a PR that cannot meet its budget redesigns, not re-baselines.

| Operation | Budget (p99, per request, warm pool) | Notes |
| --- | --- | --- |
| Security-revision check (read primary) | ≤ 5 ms | One round statement, prepared; this is the floor added to every protected request |
| Service-token authoritative check | ≤ 8 ms | May combine with the revision check in one round |
| Revocation lookup | ≤ 5 ms | Batched per issuer where possible |
| Distributed rate-limit decision | ≤ 8 ms | One atomic statement per lane; policy lane may add one more |
| Lease acquire/renew (tool admission) | ≤ 10 ms acquire; renew off the critical path where possible | Queue wait is admission, not blocking |
| Reconcile wait after a new revision | ≤ 250 ms bounded, then `503` | Compile happens off the request path; the wait is for fetch+validate+swap |
| Audit enqueue (data-plane, async batches) | 0 ms on the request path | Bounded queue, and behind it a bounded sink buffer batched to PostgreSQL by a flusher task (issue #11 PR 3); backpressure/strictness per the failure matrix |
| Control-plane mutation (admin write) | ≤ 500 ms p99 including validation and outbox | Not request-path |
| Connection acquire (pool, warm) | ≤ 50 ms | Pool sizing documented as replicas × per-replica pools + headroom |


Since PR 14 the readiness column is a closed vocabulary, and the order of these rows is the order the chain evaluates them in. `/readyz` reports the first condition that holds and stops, so a replica meeting several reports the one that has to be fixed first — storage before schema, schema before this replica's own membership lease, that lease before its security watermark — and nothing below a rung is judged on an authority that could not be read. The nine not-ready reasons are `starting`, `draining`, `contract_fenced`, `config_fingerprint_mismatch`, `storage_unavailable`, `schema_incompatible`, `instance_lease_invalid`, `security_revision_not_compiled`, and `required_upstream_unavailable`; the four degraded reasons a *serving* replica can carry are `replicas_unavailable`, `security_revision_lagging`, `maintenance_job_failing`, and `member_error_reported`. Adding a reason string, or changing what one means, changes this matrix first.
Aggregate rule: the authority adds no more than **25 ms p99** to a protected request's pre-upstream critical path in cluster mode, and **0 ms** in standalone mode.

**Where these numbers come from.** Since PR 16 they are measured rather than asserted: `gateway/tests/ha/performance.rs` measures every row above — the audit-enqueue one, since issue #11 PR 3 gave cluster mode a durable writer to stall, as a stall experiment (`the_audit_enqueue_stays_off_the_request_path`: the sink held behind `ACCESS EXCLUSIVE` on `audit_events` for a measured run, the request p99 compared against the unstalled run, zero drops, one row per request once the lock goes; its non-ignored twin is `smoke::every_served_request_leaves_exactly_one_durable_audit_row`) — and the `nightly-performance` workflow runs it `--release` and single-threaded against a real PostgreSQL and publishes `ha-performance.json` as a 90-day build artifact. Each entry in that artifact carries the operation's name, its budget, the budget's source in this document, the method used, and a `source_anchor` naming the code the measurement copied — a number without a stated claim behind it is not evidence. The absolute budgets here are the gate; the workflow additionally fails when a p99 has grown by more than 25 % over the previous night *and* has reached 80 % of its budget, which catches a slide toward a ceiling before it hits one. A missing baseline is a pass and is logged as one. Adding a row to the table above without adding a measurement fails `performance::the_report_covers_every_budget_the_state_model_publishes` on the pull request that adds it, which is deliberately not a nightly-only failure.

## 7. Compatibility

- Checked-in, ordered, checksummed migrations; no automatic downgrade. Invalid history or incompatible read/write contracts refuse startup and readiness. Readiness refusal does not cancel admitted work or block requests still routed to the replica; the load balancer must remove it.
- **Schema-changing releases still require a coordinated upgrade.** The shipped read and write contracts are each exactly schema 20, with no approved additive extension; migration 20 (the durable contract fence) moved the point from 19, as migration 19 (shared admin sessions) moved it from 18, migration 18 (service-token and JWT revocation change evidence) from 17, migration 17 (member capability advertisements) from 16 and migration 16 (Connection change evidence) from 15, so each of those releases is a coordinated drain, migrate, restart. Different binaries can share an unchanged schema when their other contracts agree; one such pair, at schema 18, is qualified [below](#the-qualified-pair-at-schema-18-issue-426-pr-2), and migrations 19 and 20 leave it behind this binary's schema point: neither of its builds can serve schema 20. No pair has been qualified across a schema change, so `BINARY_SCHEMA_COMPATIBILITY` stays exactly `(20, 20)` and `rolling_upgrade::an_expand_migration_has_no_overlap_window_so_it_cannot_roll` retains the existing gate. Drain the old set before migrating; follow [the deployment guide](../deployment/postgres.md#coordinated-upgrade-schema-19-to-20). Which builds may share a database, and the procedure for each, are published [below](#the-published-support-matrix-issue-426-pr-4).
- One logical deployment per database. Every authoritative pointer and revision counter in the schema is a singleton by construction, so a database holds exactly one deployment's state; the first boot binds the database to its `DEPLOYMENT_ID` (`greengateway.deployment_binding`) and every later boot and one-shot command refuses another. The deployment ID remains the domain separator for every digest, sealed envelope, and lock namespace, so state restored under another ID cannot be mistaken for it.
- ADR-0002 holds: one cluster is one tenant and one trust domain. Multi-region active/active and multiple writable primaries are non-goals.

### Separate history and serving contracts (issue #426)

`storage/migrations.rs` separates three decisions, and `storage/compatibility.rs` adds two more:

| Decision | Required evidence | Current behavior |
| --- | --- | --- |
| Migration history integrity | Ordered contiguous versions and exact SHA-256 checksums from compiled history | Any gap, reorder, checksum change or unknown version is refused |
| Application read/write compatibility | Valid history and the intersection of explicit read and write schema bounds | Both bounds are 20..=20; no overlap is approved |
| Migrator authority | The executable SQL manifest and its immutable checksums | `migrate check`, `migrate up` and import preflight accept only that manifest; extension recognition never grants a prepared binary permission to execute successor SQL |
| Operation admission | A registered operation requirement, this binary meeting it, the durable contract fence admitting this binary, the named backfill recorded verified, and every live member's advertisement meeting both the requirement and the fence, read immediately before the write | One operation is registered, `policy.role_descriptions`; the gate refuses anything unregistered, excluded by the fence, waiting on an unverified backfill, or not advertised by every live member, and admits a durable-fence operation only by raising the fence |
| Contract fence | One forward-only row read at startup, decided in every heartbeat's own statement, and read by every gated write | Seeded open by migration 20; nothing in this release raises it |

An approved additive extension is an exact `(version, checksum)` descriptor compiled into a prepared binary **before** the successor applies that SQL. Its checksum identifies the reviewed bytes under the existing trusted migrator/database boundary; it is not a signature or protection against a privileged operator rewriting both schema and ledger. Merely increasing a range, seeing a new membership version, or accepting a checksum supplied by the database cannot establish approval. The current descriptor list is empty. Synthetic unit fixtures exercise recognition and rejection rules; they are not evidence that a real old/new pair can serve together.

Startup and each cached readiness refresh use the same history and read/write validator. Readiness samples at most the compiled history plus one extra row, with checksums capped at 65 characters; either extra history or a nonmatching checksum fails closed. One statement reads the versions, checksums and session writability from the same database snapshot. Missing ledger means `schema_incompatible`; read-only sessions and database failures retain the higher-priority `storage_unavailable` reason. The status API carries the full compatibility verdict as well as the sampled version, so a matching extent cannot conceal a rejected history.

Membership `schema_version_min/max` advertises the read/write intersection. It is a diagnostic summary, not authorization for new operations or destructive DDL. The existing document-version advertisements and static-configuration agreement remain independent prerequisites.

### Operation requirements and capability advertisements (issue #426)

A replica that serves the schema can still be unable to interpret, or to enforce, data that a newer replica writes through an operation the older one has never heard of. The serving contract cannot see that: both replicas accept the same ledger. Since migration 17 an operation that needs more than the serving contract says so explicitly, and each replica says what it can do.

**Advertisement.** Every heartbeat writes the replica's capabilities to its own `cluster_members.capabilities`: names from a closed, compiled-in vocabulary (`storage::compatibility::Capability`), sorted, deduplicated and comma-separated. The column's check constraint bounds it at 32 names of at most 64 lowercase letters, digits and underscores; the writer refuses a set the column cannot hold rather than truncating it. Instance IDs are generated per boot, so a row's advertisement is always the running process's own. The default is the empty list, and nothing is backfilled: a row written by a gateway that predates the column advertises nothing. This release advertises three capabilities. `openapi_swagger2_catalogs`: the member generates, refreshes and replays a managed OpenAPI catalog whose specification is a Swagger 2.0 document (issue #443). `operation_requirements`: the member advertises its capabilities and enforces operation requirements before a gated write; a member without it predates the protocol and can be shown to support nothing. `policy_role_descriptions`: the member reads, validates and serves a policy document whose roles carry a `description`.

**Recognition.** A reader recognizes only the names it was built with. An unknown name, written by a newer gateway or by hand, is counted and grants nothing; a value outside the column's bounds grants nothing at all. The cluster status API reports each replica's recognized `capabilities` and an `unrecognized_capabilities` count, never the unrecognized text.

**Requirement descriptors.** An `OperationRequirement` names, for one write operation:

| Field | Meaning | Checked against |
| --- | --- | --- |
| `minimum_schema` | The lowest schema version whose objects the operation writes | This binary's serving minimum, and every live member's advertised `schema_version_max` |
| `document_format` | The policy or tools document major the operation writes, if any | This binary's and every live member's `document_version_min..=max` |
| `capability` | What every live member must advertise | This binary's own set, and every live member's recognized advertisement |
| `backfill` | `NotRequired`, or a named backfill that must be complete and verified | The backfill ledger (`schema_backfills`, migration 20): `Required` is admitted only once the named row says `verified` |
| `activation` | `LiveMembers` when a lacking member that returns later fails closed on the data, `DurableFence` when it would misread it | `DurableFence` is admitted only by raising [the durable contract fence](#the-durable-contract-fence-issue-426-pr-3) in the transaction that confirms every live member meets it |

**The gate.** `ClusterMembership::admit_operation` runs immediately before a registered operation's write. It reads the roster on the database clock and admits only when the requirement is in the shipped registry (`OPERATION_REQUIREMENTS`), this binary meets it, this replica's own row is live, and every live member, draining members included because they still answer what was routed to them, advertises the capability, recognizes the schema and reads the document format. Admission is never sticky: a lacking member can join at any time, so every write asks again. Stale rows are ignored, as they are for fingerprint agreement. Each refusal writes nothing and carries one stable reason: `operation_not_supported`, `activation_fence_unavailable`, `backfill_unverified`, `roster_unavailable`, `roster_missing_this_replica` or `capability_not_advertised`. It is logged with the lacking members' instance IDs and audited as `cluster.operation_refused` with the operation, capability, schema and format requirement, reason, and member counts, but no member identifiers. Standalone mode has no roster: its one process is the only reader, and the registry test pins every shipped requirement to one this binary meets.

**What this does not establish.** The roster judges liveness against `CLUSTER_MEMBER_STALE_MS`; on its own it is not a durable fence. A lacking member can be stopped, swept and restarted after an operation was admitted, which is why an operation whose data such a member would misread must declare `DurableFence`: since migration 20 it is admitted only by raising [the durable contract fence](#the-durable-contract-fence-issue-426-pr-3), which that member then meets at its door. The shipped registry holds two operations. The first change that needed one was a release without a migration whose writes an older replica cannot read: `policy.role_descriptions` is committing a policy document in which a role carries a `description` (minimum schema 17, document format 0, capability `policy_role_descriptions`, no backfill, `LiveMembers` activation). A gateway built before the field refuses the whole document, because a role entry's fields are closed: a running one stops compiling the active revision and holds `security_revision_not_compiled`, and a starting one fails startup. That is failing closed, never a misreading, which is why live-roster agreement is enough and the durable fence is not raised. Both cluster-mode policy commit paths ask the gate before such a commit, the policy API's mutations and a discovery suggestion's acceptance, and a document without role descriptions never asks. A refusal is a `409` with reason `capability_not_advertised`, or a `503` when the gate cannot decide; nothing is written. The second, from issue #443, is `connections.openapi_swagger2_catalog`: storing a managed OpenAPI catalog converted from a Swagger 2.0 document, by registering one, refreshing to one or putting an overlay over one (minimum schema 17, no document format, capability `openapi_swagger2_catalogs`, no backfill, `LiveMembers` activation). Every replica regenerates from the stored specification, and a gateway built before Swagger 2.0 import cannot: it keeps serving the stored tool definitions, which it reads as published, but its refresh fails with `catalog_stale`, and with an overlay present it fails startup or, running, holds its Connection reconciliation unavailable. That too is failing closed, so the durable fence is not raised. The catalog service decides which writes need the gate, after generating and before writing or recording anything; the register, refresh and overlay endpoints ask the gate only then and repeat the write once admitted, so a refresh fetches its document again. Overlay deletion is not gated, because it removes what makes an older member fail. The refusals are the same `409` and `503`. The approved-extension list stays empty. Registering another operation is a reviewed change: add the descriptor, add its new capability to the vocabulary and to the advertised set, call the gate in every write path that can produce the data, answer a refusal with its reason, and update the registry test that pins the shipped list.

**Contract eligibility.** A live member that does not advertise `operation_requirements` is never contract-eligible. Advertisement is necessary but not sufficient: [the durable contract fence](#the-durable-contract-fence-issue-426-pr-3) is what keeps a retired member from returning, and raising it is the eligibility decision, made under its row lock against the live roster, the ledger and the backfill ledger. Nothing in this release contracts the schema.

**Which test proves it.** `storage::compatibility` unit tests pin the vocabulary, recognition, the registry invariants and every refusal. Against a real PostgreSQL, `migrations::tests::migration_seventeen_advertises_nothing_for_a_member_that_predates_it` proves the column's default, the unchanged older heartbeat and the check constraint; `contract_tests::heartbeats_advertise_this_binarys_capabilities` proves the advertisement round trip; `contract_tests::a_gated_operation_waits_for_every_live_member_to_advertise_it` proves the gate over a real roster, including draining and stale members, an unreadable roster, a missing own row, the shipped operation, and the audit event for each refusal; and `cluster_policy_tests::cluster_policy_role_descriptions_wait_for_every_live_member` proves the policy API's refusal, its status and reason, that nothing is committed, the audit event, the `503` without a roster, and the admission once the older member's row is stale. Those rows drive the policy API (`PUT`). For the Swagger 2.0 operation, `cluster_policy_tests::cluster_swagger2_catalogs_wait_for_every_live_member` proves the same through the managed OpenAPI register endpoint over a real roster; `managed_openapi_gated_swagger2_writes_fail_closed_without_a_roster` proves that registration, an overlay and a refresh each answer `503 roster_unavailable` and store nothing without a roster; and `connections::openapi::tests::gated_service_holds_converted_catalog_writes_until_admitted` proves that the catalog service stops every gated write before storing or recording anything and never gates OpenAPI 3.x documents, preview or overlay deletion. The discovery suggestion's acceptance asks the same gate through the same helper but has no row of its own: the active document carries a role description only after the gate admitted it, and a prepared member cannot start against that document, so a lacking member reaches that call only by racing a commit.

### The durable contract fence (issue #426, PR 3)

The roster forgets. A member whose row went stale or was swept can come back: restarted, or resumed after a pause or a partition longer than the stale window, in which case its next heartbeat re-creates its row with its old boot instants. A stale membership row disappearing is not proof that the member retired. Since migration 20 one row in `greengateway.contract_fence` does not forget.

**What it records.** `minimum_schema`, the lowest schema version a gateway's serving range must reach, and `capabilities`, the capability names a gateway must implement, in the roster's closed vocabulary and bounds. A gateway is admitted when its serving maximum reaches the minimum and every fenced name is one it implements; a name it was not built with is one it lacks, and a value outside the bounds admits nobody. `generation` counts raises, and `raised_at` (database clock) and `raised_by` (the raising operation) are for operators. The row is seeded open: generation 0, minimum 0, no capability.

**It only moves forward.** Every writer raises it to the higher of the two minimums and the union of the two capability sets, and a trigger makes that a property of the database rather than of the writer: an update that lowers the minimum, drops a capability or does not advance the generation is refused, and so are `DELETE` and `TRUNCATE`. The runtime role holds DML on every table in the schema, so without the trigger a buggy or hostile writer could reopen the door for a retired build. Only the schema owner can drop the trigger, which is DDL.

**Who checks it, and when.** Migration 20 is a coordinated upgrade, so no build that predates the fence accepts a ledger that has one: every build that can serve the database checks it.

- *Startup*, right after the ledger check and before the deployment binding or any other authority state is read or written, so an excluded build refuses before it could compile a policy it misreads. One-shot commands are refused the same way, an import's dry run and apply with the same code, and a fence that cannot be read refuses too.
- *Rejoin*: every heartbeat decides in its own statement, under `FOR SHARE` on the fence row, and writes the roster row only if the fence admits it. The ready and draining stamps, which also refresh the heartbeat instant, make the same decision over the row's own advertisement, so neither can make the stale row of an excluded build live again. An excluded boot row fails startup. An excluded running replica writes nothing more to the roster, its draining stamp included, refuses readiness with `contract_fenced` for good, and logs and audits `cluster.contract_fenced` once.
- *Admission*: the operation gate reads the fence before the roster, refuses with `contract_fenced` when it excludes this build, and counts a live member that falls short of it as lacking.

**Raising it is the eligibility decision.** An operation declaring `Activation::DurableFence` is admitted by one transaction on the admitting replica (`PostgresMembershipStore::raise_contract_fence`), under the pooled session's statement, lock and idle-in-transaction timeouts:

1. `pg_try_advisory_xact_lock` on the migrator's lock key. A migration in progress refuses with `migration_in_progress` instead of deciding on a schema that may be changing; a migrator that starts later waits for the transaction.
2. `FOR UPDATE` on the fence row.
3. The ledger, read under that lock. History or a contract this build does not serve refuses with `schema_incompatible`.
4. The named backfill. Anything but `verified` refuses with `backfill_unverified`: a missing row, a running one (including one that was interrupted and never finished) and a failed one.
5. The roster, with liveness on the database clock. Every live member, draining ones included, must already meet the operation's requirement and the raised fence; otherwise the refusal is `capability_not_advertised`. A stale row is ignored, because the raise is exactly what keeps its member out.
6. The raise, written only when the fence would change, and audited as `cluster.contract_fence_raised` with the operation, the generation and minimum schema before and after, and the live member count.

A heartbeat that took `FOR SHARE` before the raise asked for the row is waited for, and its row is in the roster the raise reads; one that arrives after the raise took the row waits for the commit and is then judged against the raised fence. No member can join behind a raise that did not count it. The transaction rolls back when its future is dropped, so a cancelled request never leaves the row locked. The fence records that an operation was activated, not that its write succeeded, and a raise is never undone.

**Which test proves it.** Against a real PostgreSQL: `migrations::tests::migration_twenty_seeds_an_open_fence_that_only_moves_forward` (the seeded row, the trigger's refusals, the bounds, the backfill states); `migrations::tests::startup_refuses_a_build_the_contract_fence_excludes` (including before the deployment binding); `import::tests::database::a_build_the_contract_fence_excludes_cannot_import` (dry run and apply refused alike, nothing written); `contract_tests::a_build_the_contract_fence_excludes_can_neither_boot_nor_rejoin` (the schema and capability halves of the heartbeat's decision, ready and draining stamps that refresh nothing for an excluded build, a paused replica resuming into `contract_fenced`, one audit event, a swept row that cannot come back, a refused restart); `contract_tests::a_heartbeat_racing_a_fence_raise_waits_for_it_and_is_refused`; `contract_tests::a_durable_fence_operation_raises_the_fence_only_when_every_live_member_meets_it` (a live lacking member holds the raise, a stale one does not and is then refused at its heartbeat and its boot, an idempotent repeat, `migration_in_progress`, `schema_incompatible`, the backfill states on both gate paths, a heartbeat mid-statement counted by the raise, the audit events); and `contract_tests::an_unreadable_contract_fence_refuses_every_gated_operation`. The pure decisions are unit-tested in `storage::compatibility`, and `/readyz` answering `contract_fenced` in `app_tests`. Each fixture stands in for a second build through its registration or a direct write to the fence; no release-gate row runs a fenced build, because no shipped operation raises the fence.

**What it does not establish.**

- **No shipped operation declares a durable fence or a backfill.** Nothing in this release raises the fence or writes the backfill ledger; the checks run everywhere, against the seeded row.
- **No schema contraction.** Nothing contracts the schema, and `migrate up` does not consult the fence. A contraction is a future reviewed migration that must raise the fence to its own version first, under the same lock order, before it removes anything; requirement 1 below still governs the expand side.
- **Not a per-request check.** A replica paused past the stale window while the fence was raised serves what is routed to it until its next heartbeat lands, about one `CLUSTER_HEARTBEAT_MS` after it resumes, and then refuses readiness. Like every readiness refusal, `contract_fenced` relies on the load balancer to stop routing to it, and it does not stop the replica's other background work; replacing the replica does. An operation whose data a lacking member would misread on the request path itself needs its own check there.
- **No proof that a build retired.** The fence decides who may serve; it never infers from the roster that a member is gone. Recovering from a raise means running eligible builds. Never rewind the database or restore an older backup to readmit a retired build: that can resurrect revoked authority.

### The qualified pair at schema 18 (issue #426, PR 2)

One adjacent pair is proven by running both binaries against one database. It is a pair at **one schema point**: the successor adds a gated operation and no migration. It says nothing about a schema overlap, which none has been approved for.

| Side | Pinned commit | Contract | Advertises | Registered operations |
| --- | --- | --- | --- | --- |
| Prepared | `b4c663ad128b4a8c1c8f3fac590cb43aed5c1254` (`main` after merge train round B: the protocol from migration 17 and migration 18) | Read/write exactly schema 18, document format 0, no approved extension | `operation_requirements` | None |
| Successor | `cd5331ab03c46de73910289c4847052920c866f7` (the prepared release plus role descriptions: the merge of the prepared commit into this change) | The same | `operation_requirements`, `policy_role_descriptions` | `policy.role_descriptions` |

**How the gate builds and runs it.** `gateway/tests/ha/rolling-upgrade-pair.json` pins both commits. In the `ha-upgrade-pair` job, which hands the built pair to the `ha-release-gate (ha_rolling_upgrade)` leg, `scripts/build_upgrade_pair.py` refuses a pin that is not two distinct full SHAs, or a commit HEAD does not descend from. It checks each commit out into its own detached worktree and builds it there with that commit's own sources, `Cargo.lock` and default features. It records each binary's commit and SHA-256 in `manifest.json`. One substitution is stated in the manifest and the evidence: each worktree's `gateway/build.rs` is replaced by an empty build script and the embedded admin UI by a one-file stub. The pinned build script only checks the Node.js and npm versions of its own commit and builds the UI; it emits no Rust configuration, and the script refuses to replace one that does. Without the substitution the pair would stop building the first time the repository's Node pin moved. The suite then compares the manifest with the pin compiled into it, hashes both binaries again, and refuses two identical binaries. It runs them in one deployment against a disposable database: the prepared binary applies the schema as the migration role, and every replica connects as a disposable role without DDL. Each pair row writes what it observed to `evidence/`. `scripts/upgrade_pair_evidence.py` then checks that evidence against [the published matrix](#the-published-support-matrix-issue-426-pr-4) and writes `summary.json`, and the leg retains the manifest, the evidence and the summary as the `ha-rolling-upgrade-pair-evidence` artifact, with both commits and hashes, the schema state, the operation matrix, the readiness at each step and the authority's numbers.

**Keeping the pin valid.** The pin proves the two pinned commits, not HEAD. Two rules follow from that:

- A pinned commit must stay reachable from every branch that runs the gate, because the script refuses a commit HEAD does not descend from. The successor here is a commit of the pull request that pins it, so that pull request is merged with a merge commit, as the merge trains are. A squash or rebase merge would leave the commit unreachable from `main`, and the required `ha-release-gate (ha_rolling_upgrade)` leg would then fail on `main` and on every later pull request until the pair is re-pinned.
- A later change to the successor's product code is not covered until the successor is re-pinned to a commit that contains it. A change to tests or documentation leaves the pinned binary as it was and needs no re-pin.
- A re-pin is published in the same change: the evidence check refuses a pin that `docs/deployment/upgrade-support-matrix.json` does not list as a qualified pair, with the observations its rows must record.
- A change to the shared schema contract re-pins both sides, because a binary serves exactly one schema point and refuses every other. This pair was first proven at schema 17 (`303908b` and `300505d`). Migration 18 then moved the contract to 18, and a schema-17 binary cannot serve a schema-18 database, so the prepared side moved to `main` after migration 18 and the successor to the merge of that commit into this change. The successor's product code is still the prepared release's plus role descriptions and nothing else. Migration 19 (shared admin sessions) moved the contract to 19, and migration 20 (the durable contract fence) moves this binary's contract to 20. The pinned pair still proves its two schema-18 commits against a ledger its own prepared binary migrates, but it no longer describes a pair at the current schema point until both sides are re-pinned.

**What it proves.** `rolling_upgrade::a_prepared_release_and_its_successor_serve_one_deployment`:

- The two processes are different builds and each says so. Each advertises what it was compiled with. The prepared release reads the successor's advertisement as the protocol plus one name it does not recognize, which grants nothing.
- Both serve exactly schema 18 and agree on one static-configuration fingerprint. The successor's `migrate up` is a no-op and both binaries' `migrate check` call the shared ledger current.
- One `If-Match` chain alternates between the builds: each accepts the ETag the other computed, both refuse a stale one, the history stays contiguous, and the shared revision advances once per commit. Every live member then reports the last revision compiled.
- A JWT revoked through either build's `revoke-jwt` is refused by both replicas, and each revocation advances the shared revision.
- Rolling the successor back to the prepared binary, before the new operation is used, serves the same document and the same revision counter. Revocations stay in force and the rolled-back member still writes. Rolling forward again does the same.
- A ledger version neither binary was built with (the next migration, with an unknown checksum) makes both replicas `schema_incompatible` and both `migrate check`s fail until it is removed. No unproved schema overlap is accepted.

`rolling_upgrade::the_successors_new_operation_waits_for_every_prepared_member_to_leave`:

- With a prepared member live, the successor refuses a document with a role description: `409 capability_not_advertised`, nothing written, and `cluster.operation_refused` audited without a member identifier. The prepared member stays ready because it never saw the document.
- The prepared release cannot write that document either: its parser refuses the field with `400`.
- A stopped, draining prepared member still holds the operation inside the stale window. Once its row is stale on the database clock, the same write is admitted and served.
- After the operation is used, the prepared binary refuses to start: it fails closed on a document it cannot parse, and nothing rewinds the authority to let it.
- Recovery is forward. A document without role descriptions brings the prepared member back, and the next role-description write is refused again while it is live, because admission is never sticky.

**Rolling procedure for this pair.** Replace replicas one at a time behind a readiness-gated load balancer, as `a_migration_free_rollout_replaces_every_replica_without_dropping_a_request` measures for one binary. No migration step is needed. Until the last prepared replica has stopped and its row has gone stale (`CLUSTER_MEMBER_STALE_MS`), a policy write that gives a role a `description` is refused with `409`; everything else works on either build. Rollback to the prepared binary is a binary replacement, safe until a role description has been committed. After that, the prepared binary refuses to start against the deployment. To roll back then, first commit a policy without role descriptions through a successor replica, then replace binaries. That recovery leaves the described versions in the policy history, and the prepared binary cannot parse them. On a prepared replica, a history page with `include_policy=true` that reaches one, and a rollback to one, fail with `500` (`policy history query failed`) rather than serving part of a document. A history page without `include_policy`, and a rollback to a version without role descriptions, still work there. No pair row asserts this: it follows from the prepared binary validating every snapshot it returns. Read the described versions through a successor replica. Rolling back to one is the gated operation again, so it waits until the prepared replicas have left. Never restore or rewind the database to fit the older binary: that can resurrect revoked authority.

**What it does not prove.**

- **No schema overlap.** Both sides serve exactly schema 18 and `approved_extensions` is empty, so no expand, backfill or contract step and no extension checksum is exercised. A schema-changing release is still a coordinated drain, migrate, restart. Requirements 1 and 5 below remain open for that case, and requirement 4 for a contraction.
- **No durable fence exercised.** The gate judges live membership on the database clock. This pair needs nothing more, because a returning prepared member fails closed; both builds predate the fence, which arrived with migration 20, so neither can serve a deployment that has one. An operation whose data an older member would misread needs [the durable contract fence](#the-durable-contract-fence-issue-426-pr-3) and a pair that carries it.
- **Not released binaries.** No release tag ships cluster mode yet. `rolling_upgrade::the_newest_release_tag_still_predates_cluster_mode` fails when one does, and that release then belongs in the pin. Already-released, schema-16 and schema-17 binaries are not in this pair and stay on the coordinated upgrade.
- **Not the shipped artifacts.** The gate runs debug builds of the pinned commits with the admin UI stubbed, not the release images. The pair rows exercise no admin UI.
- **Not a running prepared member meeting a described document.** The pair rows prove that the prepared binary refuses to *start* against one. That a *running* prepared member stops compiling and holds `security_revision_not_compiled`, rather than keep serving its last allow state, rests on the shared revision path, which `rolling_upgrade::an_unsupported_document_version_is_never_compiled_and_never_served` drives with one binary and an unsupported document version. No row writes a described document while a prepared binary is running: the gate keeps one from being committed while a prepared member is live, so that case needs a member that joins between the gate's roster read and the commit.
- **Not traffic continuity across builds.** The pair rows assert serving, mutations and readiness at each step. Uninterrupted traffic during a replacement is measured only for one binary.
- **Only this pair.** A later commit is not covered by it. A new adjacent pair needs its own pin and its own run.

### The published support matrix (issue #426, PR 4)

The deployment guide's [Upgrading a cluster](../deployment/postgres.md#upgrading-a-cluster) publishes which builds may share one database, the gated-operation matrix, the rolling and coordinated procedures on Kubernetes, the abort procedure and the rollback cutoff. [`upgrade-support-matrix.json`](../deployment/upgrade-support-matrix.json) is its machine-readable twin. Three rules govern it.

- **Order.** A schema-changing rolling upgrade, once one is qualified, runs prepare, expand, roll, backfill, activate and contract, in that order, and each phase is held by a mechanism of this section: an approved extension (requirement 1 below), the operation gate and the backfill ledger (requirement 2), and the durable fence (requirement 4). Prepare, expand and contract do not exist in this release, so every schema change remains a coordinated drain, migrate, restart.
- **Rollback cutoff.** Rollback is a binary replacement against the same security database. It is possible until the first of these: a migration the older build does not serve commits, an operation the older build cannot read is first committed, the fence is raised, or the schema is contracted. After that, recovery is forward only, and the database is never restored or rewound to fit an older build.
- **Evidence.** A row is supported only with the evidence it names. `migrations::tests::the_published_upgrade_matrix_describes_this_binary` pins the matrix's `this_build` and schema steps to this binary's contracts, manifest, document format, capabilities and operation registry, and requires the deployment guide to document a coordinated upgrade for every step. In the `ha-release-gate (ha_rolling_upgrade)` leg, `scripts/upgrade_pair_evidence.py` requires the pin to be a published qualified pair, and every pair row's evidence to exist, to carry the built binaries' identities and to match the observations the matrix publishes; a row that was removed, renamed or ignored therefore fails the leg although the suite passed. The leg is reusable: the same build, run and verify commands qualify any pinned pair. Target-environment evidence for #389 is a record of real upgrades on the intended platform, which the deployment guide lists; nothing in this repository produces it, and the gate's artifact does not stand in for it.

### Requirements before declaring an adjacent release pair supported

The remaining slices of #426 must satisfy all of these requirements before an operator can use a rolling schema upgrade:

1. **Prepare the exact extension.** Review and pin the successor's additive SQL in the older binary's descriptor list, prove its existing readers and writers tolerate that schema, and then release the prepared binary. Previously released unprepared binaries continue to require coordinated drain/migrate/restart.
2. **Register operation requirements.** For every new operation, register a descriptor naming the minimum recognized schema, reader/document format and capability, completed backfill requirement, and activation fence, and call the gate before its write (the mechanism exists since migration 17; see above). During overlap, refuse writes that would create authority or data the prepared reader cannot interpret or enforce. Schema presence alone never enables a feature. Existing mutations must preserve conditional writes, revocation and the shared security revision/outbox.
3. **Prove the real pair.** Build a prepared binary and its successor from distinct pinned commits/images, against disposable PostgreSQL with application and migrator roles separated. Publish their exact identities, extension checksum, operation matrix, readiness outcomes and authority/revision convergence results. Exercise both instances, not two instances of one new binary. Demonstrate application rollback to the prepared binary against the same expanded database without reverting authority state. *Done for the schema-18 pair [above](#the-qualified-pair-at-schema-18-issue-426-pr-2), which has no extension to checksum and no expanded schema; a pair across a schema change must repeat it with one.*
4. **Implement contract eligibility.** Before contraction, require completed and verified backfills, compatible live member advertisements using database-clock liveness, and a monotonic durable minimum-version/capability fence. Persist and recheck the fence at startup, rejoin and admission so a stopped or swept old member cannot return after contract. A stale membership row disappearing is not proof of retirement. Serialize migration/fence decisions, bound locks and statement timeouts, and refuse ambiguous membership, interrupted backfills, or competing migrations. Keep all DDL in the migrator role. *The fence, its checks at startup, rejoin and admission, and the raise as the eligibility decision are done ([above](#the-durable-contract-fence-issue-426-pr-3)), and no runtime path holds DDL. Still open: a contracting migration that raises the fence through the migrator before it removes anything, which arrives with the first contraction.*
5. **Publish the rollout and abort boundary.** Record the supported binary/schema/operation matrix and expand/backfill/activate/contract order in release evidence. Before contraction, rollback replaces binaries while retaining the security database. After contraction, the durable fence forbids the prepared binary; recover forward with an eligible build. Never rewind the database solely to make an older binary start: doing so can resurrect revoked authority. Feed target-environment evidence into #389. *Published [above](#the-published-support-matrix-issue-426-pr-4) and in the deployment guide, and the release gate checks the pinned pair's evidence against it. The order's prepare, expand and contract phases wait on requirements 1 and 4; the target-environment record is the operator's, on the intended platform.*

The schema-18 pair above is the only qualified rolling pair. No rolling schema upgrade, schema contraction, or general zero-downtime guarantee is established, and the published matrix claims none. The durable contract fence exists, and nothing in this release raises it.
