## [Unreleased]

### Production readiness fixes

- Publish the supported upgrade matrix and procedure (part of #426). The deployment guide's new [Upgrading a cluster](docs/deployment/postgres.md#upgrading-a-cluster) says which builds may share one PostgreSQL deployment and what proves each row: replicas of one build, the qualified schema-18 pair, other builds at one schema point (permitted by the protocol, not qualified), builds at different schema points (never; coordinated drain, migrate, restart), a build the durable contract fence excludes, and released binaries (which cannot join cluster mode). It adds the gated-operation matrix, how to choose a procedure, the rolling and the coordinated upgrade written for Kubernetes (`/readyz` probes, `maxUnavailable: 0`, the drain delay against endpoint removal, the migration Job, and the hooks that migrate too early), the expand, backfill, activate, contract order with which phases exist today, how to abort each kind of rollout, and the rollback cutoff: the events after which only recovering forward is possible. [`docs/deployment/upgrade-support-matrix.json`](docs/deployment/upgrade-support-matrix.json) is its machine-readable twin, and both halves are checked. `storage::migrations`' `the_published_upgrade_matrix_describes_this_binary` fails when this build's contracts, manifest, document format, capabilities, gated operations or schema steps drift from the matrix, or when a schema step has no coordinated-upgrade section in the guide; a pull request that adds a migration therefore publishes its step. The `ha-release-gate (ha_rolling_upgrade)` leg now ends with `scripts/upgrade_pair_evidence.py`, which refuses a pin the matrix does not list, a binary other than the one built, a pair row that recorded no evidence (one removed, renamed or ignored no longer leaves the leg green) or one the matrix does not publish, and any observation that disagrees with the matrix. It writes `summary.json` into the `ha-rolling-upgrade-pair-evidence` artifact, naming both commits and binary hashes, the gate's commit, the schema point, the operation matrix and the readiness at each step. The same build, run and verify commands qualify any pinned pair. Nothing changes what is supported: every schema change is still a coordinated upgrade, no extension is approved, nothing raises the fence or contracts the schema, and no zero-downtime guarantee is claimed. The gate runs debug builds of pinned commits, not the shipped images or Kubernetes; the guide lists what to record during real upgrades on the intended platform for [#389](https://github.com/Greenhat-Security/GreenGateway/issues/389). No migration and no runtime change.
- Retire the last policy rule matching beside the compiled evaluator (part of #422). The enum-source precheck, which runs before any DNS, credential or transport work for an OpenAPI enum source, copied the live policy and built its own rule matcher on every call; it now asks the shared evaluator of the live lane's installed snapshot, the one live requests are judged by: the named tool's enable bit, then deny rules alone for an anonymous contextless `GET` of the rendered path. Its answers, failure reasons and audit records are unchanged. A source the evaluator refuses to answer for, which no compiled overlay produces, is refused before any I/O as `http_rule_denied` and audited with reason `policy_evaluation_error` and no rule. The tool-name check rule suggestions use to skip what the policy already covers asks the evaluator too, with unchanged answers. A tool runtime with no policy configured has no rules to evaluate, and its configuration can no longer carry any; bootstrap never gave it any. The evaluator now holds the only serving rule matcher, and a test fails any other construction outside test code. The previous implementations remain only as test oracles, compared over the existing generated corpora (fixed seeds 422_002 and 422_005) and named cases. No live HTTP, tool-call, rate-limit or egress decision, endpoint, permission, schema or migration changes. See [the legacy retirement](docs/architecture/policy-evaluation-parity.md#legacy-retirement).
- Alert on refused authority changes and on authority-event journal capacity and delivery (part of #440). The operational rule pack gains a `greengateway-authority-events-v1` group of seven cluster-only alerts over the durable authority-event metrics of #425: `GreenGatewayAuthorityEventCapacityRefusals` and `GreenGatewayAuthorityEvidenceWriteFailures` page per replica on any refused Connection delete, service-token rotate or revoke, or JWT revoke, during startup and drain too; `GreenGatewayAuthorityEventJournalFull` pages when retained events reach capacity and `GreenGatewayAuthorityEventJournalFilling` warns above 80 %; `GreenGatewayAuthorityEventDeliveryLag` warns when the oldest undelivered event has waited more than 120 seconds for 5 minutes, judged only where a dispatcher is configured, since without `AUTHORITY_EVENT_SINK` every retained event is undelivered by design; `GreenGatewayAuthorityEventDeliveryFailures` warns on dispatcher failures other than a fenced handover sustained for 10 minutes; and `GreenGatewayAuthorityEventJournalUnobserved` warns when no current maintenance leader exports the journal gauges with a retention success under 300 seconds old, so a missing or frozen reading is never taken for a healthy zero. The journal gauges are shared state that only a leader publishes and a former leader keeps exporting, so the journal rules read the current maintenance leader only and fire once per deployment. A new counter, `greengateway_authority_event_evidence_failures_total`, counts changes refused because the database refused or did not answer their evidence row or journal entry for any reason other than capacity, which stays `greengateway_authority_event_capacity_refusals_total`; each refused change is counted once, and a PostgreSQL test refuses each evidence table and the journal in turn to prove it. Nine new synthetic promtool scenarios, plus assertions added to the standalone and counter-reset scenarios, cover firing, holds, recovery, a maintenance handover, stale former leaders, stalled retention, a deployment without a sink and a dispatcher that cannot take its lease; the runbooks are in [operational alerts](docs/deployment/operational-alerts.md#authority-event-journal). The fixtures prove expression behaviour on synthetic series only, not delivery to a responder or to a downstream system.
- Journal committed authority evidence and deliver it through a durable dispatcher (part of #425). In cluster mode every Connection delete, service-token rotate or revoke, and effective JWT revoke now appends one row to the new `greengateway.authority_event_journal` (migration 21) in the same transaction as its evidence row, under that row's own event ID, at a position reserved under a lock held to commit, so position order is commit order and the journal has no gaps; existing evidence is journaled by the migration in commit order. The reservation is bounded by `AUTHORITY_EVENT_JOURNAL_CAPACITY` (default 1,000,000 retained events): when the journal is full the mutation is refused with `503` (a `revoke-jwt` exits with a store error) and commits nothing, and no accepted event is ever evicted, so a revoke refused at capacity leaves the credential live until it can commit. `AUTHORITY_EVENT_SINK=log` or `file` (default `none`) starts a dispatcher on whichever replica holds the new `authority-event-dispatcher` execution lease: it reads at most 100 journal rows after a persisted, fenced cursor, delivers them as `authority_event_delivery.v1` records ([schema](docs/schemas/authority_event_delivery.v1.schema.json)) whose actor and resource are keyed safe references, and advances the cursor only after the sink accepted, retrying a refused batch with backoff from 0.5 s to 60 s and never skipping one; delivery is at least once, so consumers deduplicate on `(authority_id, event_id)`. The `log` sink writes one structured `INFO` line per event; the `file` sink appends JSON lines to `AUTHORITY_EVENT_FILE` and syncs before accepting. A sink requires `AUTHORITY_PSEUDONYM_KEY_ALIAS` (and optionally `AUTHORITY_PSEUDONYM_PREVIOUS_KEY_ALIAS`), resolved at startup under the `authority_pseudonym_key` purpose; a key that does not resolve refuses startup, the load is audited as `authority_event.keyring_loaded` with key IDs only, and no Connection may bind either alias (`422 secret_purpose_conflict`; a stored binding refuses startup). The delivered record names the actor by a new issuer-less `actor.recorded` reference domain, because the evidence records only the actor's subject; it is not the proposed `authority_event.v1`. A new maintenance job, `authority_event_retention`, prunes only delivered journal rows older than `AUTHORITY_EVENT_RETENTION_HOURS` (default 168) and never an evidence row; before any dispatcher has run, rows past the window are pruned by age. New metrics: `greengateway_authority_event_journal_retained`, `_journal_capacity`, `_undelivered`, `_oldest_undelivered_age_seconds`, `_delivered_total`, `_delivery_failures_total{kind}` and `_capacity_refusals_total`. All six settings are cluster-only (refused in standalone mode) and part of the static-configuration fingerprint, except the file path. Not covered: admin session evidence is not journaled, standalone mode has no journal, and required-durability mode, which would make a sink mandatory, is still not implemented. See [Durable delivery](docs/authority-evidence.md#durable-delivery). **Coordinated upgrade required:** the PostgreSQL read/write schema contract moves from exactly 20 to exactly 21, so a schema-20 and a schema-21 gateway never serve the same database; see [the schema 20 to 21 upgrade](docs/deployment/postgres.md#coordinated-upgrade-schema-20-to-21).
- Route the admin analysis consumers through the compiled policy evaluator (part of #422). The historical rule preview (`POST /v1{ADMIN_PREFIX}/policy/rules/preview`), the traffic inventory's endpoint coverage and the check rule suggestions use to skip what the policy already covers each judged policy with their own copy of part of the matching; they now ask the shared evaluator, so the facts they supply are validated and refused as a live request's are, and the frozen pre-cutover consumers remain only as test oracles, compared over a generated corpus (fixed seed 422_005) and named cases. The preview is still a historical match counter over the candidate rule alone, not a simulation of the policy. It now reports an observation it cannot judge instead of counting it either way: `unevaluated_event_count`, with `unevaluated_reasons` per reason (`missing_dispatch_fact` for an unclassified observation against a rule with a `dispatch` binding, `missing_principal_fact` for an actor in an authentication mode no principal carries against a rule with `principal` constraints, `malformed_observation` for a method, path, principal or routing context the evaluator refuses, such as a percent-encoded or dot-segment path no served request reaches the policy stage with). Any such observation sets `complete: false`, so `match_count` is a lower bound, and the admin UI says so. A client-certificate actor is now judged with its identity, as live evaluation judges it, where the preview treated it as anonymous; an observation the preview used to count as a match against a refused path is now unevaluated. Endpoint coverage is `unknown` when no routing context was recorded or the evaluator refuses the representative request, and on a host-routed context a role's callers also count as covered when a direct deny decides them first. Suggestion coverage on a host-routed candidate now requires that the candidate's caller can activate a role granting the route's permission and meets no direct deny first, as live evaluation decides it; a signal candidate bound to a pooled route is judged as that route's traffic rather than as contextless traffic; and a candidate the evaluator cannot judge is still proposed and counted in the run's new `coverage_unevaluated`. Tool-name coverage of suggestions moved onto the evaluator with the legacy matcher retirement (part of #422, listed separately). Rule hit counts (`GET /v1{ADMIN_PREFIX}/policy/rules/hits`) are recorded attribution, not an evaluation; their response is unchanged, and they are now keyed by the live snapshot's own rule ids, the ones written as `matched_rule_id`. Discovery keeps no route id, so a rule bound by `route_id` to a route that is not pooled is not credited as coverage. No live authorization decision, endpoint, permission, schema or migration changes. See [the analysis consumer evidence](docs/architecture/policy-evaluation-parity.md#analysis-consumer-evidence-and-cutover-limits).
- Decide static egress through the compiled policy evaluator (part of #422). Every outbound destination check (`checked_destination`, and the DNS-free rebinding and revalidation of a pinned destination) now asks the shared evaluator's static egress lane, compiled per egress client from the same controls: the URL's shape and scheme, the exact and pattern host allowlists and the policy port list first, with no resolution facts, and only then the resolver's answers, every one judged against the non-global address registry and the policy CIDRs while non-global blocking is on, with the first answer pinned. A destination the static checks refuse is refused before any DNS lookup on every entry point, as before; tests now hold this with a resolver that panics when called. Every error, warning and safe category is the one the previous checks produced, so proxy answers, retry and passive-health classification and audit categories are unchanged; an evaluator error, which only a broken adapter invariant can cause, refuses the destination as `invalid_policy`. The DNS lookup, redirect refusal, the exact-pinned clients, TLS, the gRPC transport and request and response bounds are unchanged. The previous checks remain only as a test oracle, compared with the live adapter over a generated corpus (fixed seed 422_004) and a named matrix.
- Fence schema contracts durably at startup, rejoin and admission (part of #426). Migration 20 adds `greengateway.contract_fence`, one row that only moves forward: the lowest schema a gateway's serving range must reach and the capabilities it must implement, plus a generation and who raised it. A trigger refuses any update that lowers the minimum, drops a capability or does not advance the generation, and refuses `DELETE` and `TRUNCATE`, so the runtime role's DML cannot reopen it. The migration also adds `greengateway.schema_backfills`, a ledger of named backfills (`running`, `verified`, `failed`). The fence is checked in three places, and each fails closed. **Startup**, before any other authority state is read or written, the deployment binding included: an excluded build refuses to start, and so do one-shot commands; `gateway import` refuses its dry run and its apply alike with `target_schema_not_current`. **Every heartbeat**, inside its own statement under `FOR SHARE` on the fence row (the ready and draining stamps decide the same way): an excluded build writes no roster row, so it can neither boot into the roster nor rejoin it after its row went stale or was swept. A running replica that finds itself excluded writes nothing more to the roster, logs and audits `cluster.contract_fenced` once, and answers `/readyz` with the new reason `contract_fenced` for good. **Every gated write**: the operation gate refuses with `contract_fenced` when the fence excludes this build, and counts a live member that falls short of it as lacking. An operation that declares a durable activation fence is now admitted, where it was refused outright, by raising the fence in one transaction. That transaction takes the migrator's advisory lock as a try-lock, locks the fence row `FOR UPDATE`, and reads the ledger, the named backfill and the roster under that lock. It raises the fence only if every live member, draining ones included, already meets the raised fence, and audits the raise as `cluster.contract_fence_raised`. A heartbeat in flight is waited for and counted. An operation that needs a backfill is admitted only once the backfill is recorded `verified`, where it was refused outright. New refusal reasons: `contract_fenced`, `migration_in_progress` and `schema_incompatible`; `backfill_unverified` now reports the backfill's state. `gateway cluster-members` prints the fence. No shipped operation declares a durable fence or a backfill, so nothing in this release raises the fence or writes the backfill ledger, nothing contracts the schema, and `migrate up` does not consult the fence. A replica paused past the stale window while the fence was raised serves what is routed to it until its next heartbeat lands, then refuses readiness; like every readiness refusal, `contract_fenced` relies on the load balancer. **Coordinated upgrade required:** the PostgreSQL read/write schema contract moves from exactly 19 to exactly 20, so a schema-19 and a schema-20 gateway never serve the same database, and neither build of the qualified schema-18 pair can serve schema 20. Drain and stop the old fleet, run `gateway migrate up`, then start the new fleet. The fence table is read at startup, so re-apply the runtime role's `ON ALL TABLES` grant first if its default privileges are not set. See [the schema 19 to 20 upgrade](docs/deployment/postgres.md#coordinated-upgrade-schema-19-to-20) and [the durable contract fence](docs/architecture/ha-state-model.md#the-durable-contract-fence-issue-426-pr-3). Standalone mode is unchanged.
- Share admin sessions across replicas in cluster mode (part of #424, [ADR-0009](docs/adr/0009-shared-admin-sessions.md)). `ADMIN_SESSION_MODE=cluster_postgres` (only with `STATE_BACKEND=postgres`) keeps gateway-issued admin sessions on the PostgreSQL primary, so a sign-in completes on whichever replica receives it and a logout, a sign-in that replaces the session, a rejected access token or an identity change ends the session on every replica at its next request. The cookie, the login binding and the CSRF token are stored only as digests under the deployment ID; the server-held access token is sealed with XChaCha20-Poly1305 under `ADMIN_LOGIN_KEYRING` (keep a rotated-out key as `decrypt_only` for one `ADMIN_SESSION_TTL_SECS`), and the login provider still revalidates it on every request. Absolute and idle deadlines are judged on the database clock; every request reads the session on the primary and is admitted only while the row is still live after the provider check. `ADMIN_SESSION_MAX_ENTRIES` bounds live sessions and pending cookie logins across the deployment under one admission lock, admissions prune a bounded batch, and the maintenance singleton runs a new bounded `admin_session_prune` job. Each grant and withdrawal writes one append-only `greengateway.admin_session_evidence` row in the same transaction (reason `issued`, `logout`, `replaced`, `rejected` or `expired`, with the subject, issuer, absolute deadline and database-clock time, never a credential); a change whose evidence cannot be written fails with `503` and changes nothing. The authority-evidence inventory row for cluster sessions moves from `unsupported_future_operation` to `missing_metadata` and `missing_delivery`. `standalone_memory` remains refused in cluster mode, and `cluster_postgres` is refused in standalone mode. In both modes, new behavior: `ADMIN_SESSION_IDLE_TIMEOUT_SECS` (default: the TTL, which disables it) ends an unused session early, and each session is bound to the double-submit token its completion presented, so an unsafe cookie-authenticated request with any other self-consistent CSRF pair is refused with `403` and audited as `admin_session_csrf_unbound`; the completion sets the CSRF cookie again with the session's `Max-Age` so the two cookies live equally long. **Coordinated upgrade required:** the PostgreSQL read/write schema contract moves from exactly 18 to exactly 19 (migration 19, three new tables), so a schema-18 and a schema-19 gateway never serve the same database; see [the schema 18 to 19 upgrade](docs/deployment/postgres.md#coordinated-upgrade-schema-18-to-19).
- Derive keyed, domain-separated safe references for authority evidence (part of #425). A new pure module, `authority_events::pseudonym`, turns actor and resource identifiers into the 64-character `subject_ref`, `issuer_ref` and `resource.ref` values the proposed `authority_event.v1` schema requires: HMAC-SHA256 under a pseudonym key over a length-framed input that binds the evidence authority ID and a closed domain (`actor.subject` takes the canonical issuer and the subject, `actor.issuer` the issuer, and each schema `resource.kind` its identifier), led by an 8-character key ID derived from the key so a rotation is visible. A keyring holds the current key, which derives, and at most one previous key, which only verifies during a dual-key rotation window, comparing in constant time. The key is resolved through the secret providers under a new `authority_pseudonym_key` purpose that the encrypted local store neither holds nor resolves and the Connection admin API does not list as bindable; it must be exactly 64 hexadecimal characters, and any other material, a placeholder, one key named twice or an unversioned authority ID is refused, with no unkeyed fallback. Debug output and errors never carry key material. Nothing calls the module at runtime yet: no setting names a key and no event carries a reference. `docs/authority-evidence.md` gives the key source, rotation and backup policy and what the producer slice must add.
- Prove a rolling upgrade pair against shared PostgreSQL (part of #426). The `ha-release-gate (ha_rolling_upgrade)` leg now builds two real binaries from two pinned commits (`gateway/tests/ha/rolling-upgrade-pair.json`, built by `scripts/build_upgrade_pair.py`): the prepared release, which implements the compatibility protocol and serves schema 18, and its successor, which adds role descriptions and no migration. Both run in one deployment against a disposable database with the migration and runtime roles separated. The leg proves conditional policy writes, revocations and revision convergence across the two builds, rollback to the prepared binary without rewinding the authority, refusal by both builds of a migration neither was prepared for, and that `policy.role_descriptions` stays refused while a prepared replica is live or draining and is accepted after it has gone. It retains the observations as the `ha-rolling-upgrade-pair-evidence` artifact. The read/write schema contract stays exactly 18 and no schema extension is approved: this pair shares one schema point, and a schema-changing release is still a coordinated drain, migrate, restart. See [the qualified pair](docs/architecture/ha-state-model.md#the-qualified-pair-at-schema-18-issue-426-pr-2) for the procedure and what it does not prove.
- Let a policy role say what it is for, and gate that document on every live replica (part of #426). A `roles.<name>` entry may now carry a `description`: free text of at most 512 UTF-8 bytes, not blank and without control characters, that grants and restricts nothing. A gateway built before the field refuses a document that sets it, so writing one is the first registered gated operation, `policy.role_descriptions`. Every cluster-mode replica now also advertises `policy_role_descriptions`, and both cluster-mode policy commit paths (the policy API's mutations and a discovery suggestion's acceptance) ask the gate before committing a document with a role description, and commit it only when the roster, read on the database clock just before the commit, shows every live replica, draining ones included, advertising it. The check is not a durable fence: a replica that joins between that read and the commit cannot parse the document and fails closed rather than misreading it. While a replica lacks the capability the write is refused with `409` and reason `capability_not_advertised`, nothing is written, and the refusal is audited as `cluster.operation_refused`; a roster that cannot be read refuses with `503`. Documents without role descriptions are unaffected, and their ETags are unchanged. No migration and no schema change: the read/write contract stays exactly schema 18 and the approved-extension list stays empty. Standalone mode accepts role descriptions directly.
- Keep an admin UI SSO sign-in that completes with a bearer token when the dashboard's first permissions request is rejected before the token arrives. On a gateway that offers no admin session cookie (`ADMIN_SESSION_MODE` other than `standalone_memory`, so every cluster-mode deployment), that token-less request was answered `401` while the gateway was still exchanging the code, and the completion then reported "SSO completion discarded because the session changed" and dropped the token, so browser SSO sign-in failed. A rejected request no longer discards the completion; choosing other credentials in the tab, or leaving the page, while it is pending still does. Cookie-mode completion already behaved this way.
- Record who rotates and revokes service tokens, and keep JWT revocation provenance through extension and cleanup (part of #425). `ServiceTokenStore` rotate and revoke now take the acting principal, and each committed change writes one append-only evidence row in its own transaction: in cluster mode `greengateway.service_token_change_evidence` (migration 18) beside the unchanged outbox row, carrying the actor, the action, generated event and operation IDs, the token's row revision before and after, the outbox row's shared revision and the database-clock commit time; in standalone mode a `service_token_change_evidence` table in the `SERVICE_TOKEN_SQLITE_PATH` database, created on open, inside an immediate SQLite transaction that also serializes rotate and revoke across connections. Every `revoke-jwt` that changes the denylist writes one `greengateway.jwt_revocation_evidence` row (actor, issuer, `jti` digest, resulting expiry, shared revision), so an extension or reactivation no longer erases the earlier actor and expiry cleanup no longer erases the record. None of the rows has a foreign key or holds a plaintext token, hash, display prefix, scope or raw `jti`. A change whose evidence cannot be written fails and changes nothing, and is answered as a store failure rather than the revoked-token `409`; a repeat revoke, a refused rotate and a refused JWT revoke write nothing. Standalone evidence is not carried by `import-standalone`. The authority-evidence inventory also now lists admin session grant and withdrawal (#424) as unsupported for required durability, since the shipped sessions are process-local memory. **Coordinated upgrade required:** the PostgreSQL read/write schema contract moves from exactly 17 to exactly 18, so a schema-17 and a schema-18 gateway never serve the same database. Drain and stop the old fleet, run `gateway migrate up`, re-apply the runtime grants unless default privileges are set, then start the new fleet; see [the schema 17 to 18 upgrade](docs/deployment/postgres.md#coordinated-upgrade-schema-17-to-18).
- Advertise member capabilities and gate new operations on them (part of #426). Every cluster-mode heartbeat now writes the replica's capabilities to its own `greengateway.cluster_members.capabilities` row (migration 17): names from a closed vocabulary compiled into the binary, bounded by a check constraint to 32 names of at most 64 lowercase characters, and recognized by readers only when they know the name, so an unknown or oversized advertisement grants nothing. This change advertises `operation_requirements`. An operation that needs more than the schema contract now declares an explicit requirement descriptor: the minimum schema it writes, the document format, the capability every live member must advertise, any backfill, and the activation fence it needs. Its write path asks the gate first, and the gate refuses the write, logs the lacking members and audits `cluster.operation_refused` with a stable reason until every live member, draining ones included, advertises it. An operation needing a durable fence or a backfill is refused outright, because neither exists yet. This change registers no operation (the first, `policy.role_descriptions`, is the role-descriptions entry above), and the approved-extension list stays empty. The cluster replicas API and `gateway cluster-members` report each member's recognized capabilities and a count of unrecognized ones. **Coordinated upgrade required:** the PostgreSQL read/write schema contract moves from exactly 16 to exactly 17, so a schema-16 and a schema-17 gateway never serve the same database. Drain and stop the old fleet, run `gateway migrate up`, then start the new fleet. The new column is on an existing table, so no grants change. See [the schema 16 to 17 upgrade](docs/deployment/postgres.md#coordinated-upgrade-schema-16-to-17). Standalone mode is unchanged.
- Select policy `rate_limits` overrides with the compiled policy evaluator (part of #422). The policy rate stage now asks the shared evaluator which override governs an authenticated request, over the snapshot the RBAC lane installed, and charges the bucket built for that override from the same snapshot; buckets, capacity, the shared store and the global lanes are unchanged, and unauthenticated requests still reach no override. A selection the evaluator refuses or cannot complete refuses the request with `403`, an `authz.denied` record and no bucket charged, never an unmetered pass. The reachable cases are an authenticated request with an unsafe path (`unsafe_path`) or an asterisk-form target (`policy_evaluation_error`), which authorization already refused with the same answer; they no longer spend a matching override's burst first, so they are not answered `429` once it is spent. In cluster mode, installing a policy revision now also hands the rate stage that revision's overrides: previously the stage kept the overrides it started with until restart, because the install compared the snapshot `rcu` replaced, rather than the one it installed, with its candidate.
- Judge shared rate-limit decisions in the order the bucket row lock takes them. In cluster mode, each decision was judged at its statement's start, which PostgreSQL fixes before the statement waits for the bucket row, so a request that reached the row after one that started later was charged for time it had not used yet and could be answered `429` below the configured burst: three concurrent requests under a burst of three could admit two, and a busy key, such as many clients behind one address, saw spurious `429`s under contention. A decision is now judged at the later of its start and the bucket's last decision. That never runs ahead of the database clock, so the cluster still admits at most the configured burst and rate.
- Route live HTTP/RBAC authorization through the compiled policy evaluator pinned to the admitted snapshot (part of #422). Preserve direct-rule, host-bound route, MCP HTTP alias, shadow and audit behavior; block incomplete or inconsistent evaluation inputs before downstream work. Tool admission, rate selection and egress retain their existing authorities.
- Report missing and truncated policy evidence instead of zeros (part of #243). `GET /v1{ADMIN_PREFIX}/policy/rules/hits` and `GET /v1{ADMIN_PREFIX}/policy/rules/shadow-review` now answer `503` with `"reason":"audit_evidence_unavailable"` when no audit query store is configured -- including every cluster-mode deployment, which does not serve these aggregates yet -- rather than `200` with zero counts that read as "never matched" or "safe to promote"; rule preview's existing `503` carries the same reason. Rule preview scans at most 100,000 observations that pass its SQL method and path pre-filter and adds `scan_truncated` and `complete` to its response. The admin UI shows evidence unavailable, truncated, and a counted zero as distinct text, and a preview window with no pre-filtered observations as its own state rather than zero matches. The shadow review queue keeps Promote and Disable disabled while its evidence is unavailable and sends them with the ETag of the policy the review was read against, so a concurrent change answers `412` instead of changing a different position-keyed rule; the rule table re-reads hit counts after each change and hides position-keyed counts while rows have moved.
- Bind shadow-rule promotion and disable to the reviewed revision, evidence window and evidence digest (part of #243). `GET /v1{ADMIN_PREFIX}/policy/rules/shadow-review` adds `policy_etag` (the revision it was read from) and, per entry, `evidence_window` (oldest and newest would-deny timestamps read for the rule) and `evidence_digest` (an RFC 8785/JCS-framed SHA-256 over the entry's evidence and revision). `PATCH /v1{ADMIN_PREFIX}/policy/rules/{id}` accepts an optional `shadow_review` binding for exactly `{"action":"deny"}` or `{"enabled":false}`: it requires `admin:audit:read`, re-reads the review under the policy write lock, and refuses without writing -- `412 shadow_review_revision_stale`, `409 shadow_evidence_window_stale`, `409 shadow_evidence_digest_stale`, `409 shadow_review_rule_not_shadow`, or `503 audit_evidence_unavailable` -- whenever the binding no longer describes current evidence, emitting `policy.shadow_transition_refused`. A successful bound change records the binding in `policy.changed` and policy history. Unbound rule edits are unchanged. The shadow review queue sends the binding of the entry on screen, shows each entry's evidence window (marked, like the count, as covering only the newest scanned events when the scan was truncated), re-reads the review after every change, and shows each refusal as its own blocking state until the review is reloaded.
- Record durable evidence for PostgreSQL Connection deletions (part of #425). Each committed delete now also writes one `greengateway.connection_change_evidence` row (migration 16) in the same transaction as its unchanged outbox tombstone: the deleting actor, the action, generated event and operation IDs, the prior version, the shared security revision and the database-clock commit time. ### Added

- Explicit, deterministic conversion of a 0.x policy document to policy v1 (part of #243). `POST /v1{ADMIN_PREFIX}/policy/convert`, under `admin:policy:read` like validation, takes a 0.x document and returns the v1 document beside its source digest, its v1 semantic digest and a `changes` list; it writes nothing and changes nothing live, and startup, reload and replacement still never convert a document. The v1 document is the gateway's serialization of what the 0.x reader read, members in schema order and maps sorted by name, so one 0.x policy always converts to the same document whatever its formatting. A rule keeps its effective id (its `id`, or its zero-based index for a rule without one, the id audit events, hit counts, shadow review and the rule-management routes already use) when that is a valid v1 id no earlier rule has; every other element gets `rule-N`, `route-N` or `rate-limit-N` by its 0.x index, suffixed `-2`, `-3`, ... when that is taken. Every written or replaced id, every top-level member the 0.x reader ignored and every repeated member name it resolved is listed with a stable code and pointer. A conversion is refused unless its result reads back through the v1 reader as exactly the 0.x policy apart from version and ids, so the two documents authorize identically; golden tests pin the converted documents, ids and digests and ask both documents of every fixture and repository 0.x policy the same HTTP, rate, tool and egress questions through the shared evaluator. A 0.x document whose v1 form v1 refuses (a number above 2^53 - 1, or a normalized form over 1 MiB) is refused with the v1 reader's diagnostics, and a v1 document with the new `conversion_requires_v0`. Cluster mode can convert but still does not commit v1 documents.
- The versioned configuration bundle format and its reader (issue #242, alpha; not yet selectable). A bundle is a flat directory holding a `bundle.yaml` manifest (`GatewayBundle`), one deployment document (`GatewayDeployment`, YAML or JSON), and the policy and tools documents the manifest pins by SHA-256; `docs/schemas/gateway-bundle.v1alpha1.schema.json` and `docs/schemas/gateway-deployment.v1alpha1.schema.json` publish the two new documents. The reader accepts only the exact `greengateway.dev/v1alpha1` pairs, refuses every member a version does not define, reads YAML through a deliberately small safe subset (no anchors, aliases, tags, merge keys, multiple documents, block or multi-line scalars, tabs, duplicate keys, or unquoted values another YAML reader could type differently) and JSON strictly (duplicate members refused rather than overwritten), applies byte, nesting, member, element, value, string and key bounds while parsing, checks each file's pin before parsing it, and opens files only beneath the canonicalized bundle root by portable lowercase names without following links, refusing symbolic links, reparse points, subdirectories, special and hard-linked files, group- or other-writable files on Unix, and any `..data` layout other than the Kubernetes atomic writer's single generation. Referenced policy and tools documents must declare and contain exactly schema version `0.1.0`, and a policy may not carry a top-level member the loader would drop; both then pass their published schemas and production validators unchanged. Secret settings are fixed to opaque `{ secret: <alias-id> }` references and fractional settings to decimal strings, and the bundle's source digest frames the manifest bytes with ADR-0004's `GGDIGEST` frame. Every diagnostic carries a stable code, file, JSON Pointer, and line and column, and no document value. Nothing reads a bundle yet: there is no startup mode, environment variable, admin route, or command for it, environment configuration is unchanged, and the deployment document carries only its profile until the field catalog fills it. - Import Swagger 2.0 documents into managed OpenAPI Connections (part of #443). Preview, registration, refresh and overlay edits now accept a Swagger 2.0 document (a `swagger` field set to the string `"2.0"` and no `openapi` field) and convert it to the OpenAPI 3.0 document it describes before generating tools: `definitions` become `components.schemas` with every reference rewritten, `body` and `formData` parameters become request bodies per `consumes`, response schemas become content per `produces`, `#/parameters/` and `#/responses/` references are inlined, `collectionFormat` becomes an explicit style, and `securityDefinitions` become security schemes (`application` maps to `clientCredentials`, so it binds to an `oauth2_client_credentials` Connection; user-consent flows, `basic` and query keys stay incompatible as their OpenAPI 3.0 forms are). The catalog service decides, after generating and before writing anything, whether a write needs the gate, so OpenAPI 3.x documents, preview and overlay deletion never ask, and an admitted refresh fetches its document again. - Policy v1 with stable element ids, canonical digests and structured diagnostics (part of #243). A policy document whose `schema_version` is exactly `1.0.0` is policy v1 ([`docs/schemas/policy.v1.schema.json`](docs/schemas/policy.v1.schema.json)): it authorizes exactly as the 0.x document with the same members, and additionally requires an `id` (1 to 64 ASCII letters, digits, `.`, `_`, `-`) on every direct rule, route and rate override, unique across all three; refuses unknown members in every object instead of ignoring them, a repeated member name anywhere, a `null` member value, a document over 1 MiB, and any number outside the I-JSON safe range. Dispatch is exact: `1.0`, `1.0.1` or `1.1.0` is rejected, not read as v1. 0.x documents are read exactly as before: a route or rate override `id`, a v1-only member, is still refused in them (now as `member_requires_v1`), so a 0.x document means the same to every gateway that accepts it. `POST /v1{ADMIN_PREFIX}/policy/validate` keeps `valid` and `errors` and adds `schema_version`, `diagnostics` (stable `code`, `severity`, RFC 6901 `pointer`, `element_id`, a fixed `message` and `remediation` that quote nothing from the document, and which of simulation, tests, publication and evidence each finding blocks), `source_digest` (the ADR-0004 frame over the exact request bytes) and, for v1, `semantic_digest` over the RFC 8785 canonical form of the normalized policy. A 0.x document gets warnings, never errors, for what v1 would refuse, and has no semantic digest. Replacing the policy with a v1 document reports every structural problem; a 0.x document reports its one error in the same words as before. `canonical_json` now encodes fractions and exponents within the safe range as ECMAScript does (checked against the RFC 8785 Appendix B vectors) and gains the `source` digest frame. Nothing rewrites a policy file between formats, and a release that predates v1 refuses a v1 document. Cluster mode does not accept v1 yet: replicas still advertise document format `0..0`, so the policy API refuses to commit a v1 document with `400`, a replica refuses to serve one found in the authority, and `gateway import-standalone` refuses a standalone policy or history holding one. A 0.x document's serialization, and so its ETag, is unchanged.

- Versioned, checksummed PostgreSQL schema migrations with a validate-only serving posture (issue #241, experimental; builds on the PR-3 foundation). The cluster-mode schema now exists as one `greengateway` schema built by a checked-in, ordered manifest of transactional migrations, each pinned by a SHA-256 checksum recorded in a `schema_migrations` ledger row committed in the same transaction as the migration itself — a failed migration rolls back completely, so there is no dirty half-applied state and no automatic downgrade. Two one-shot commands run the lifecycle: `gateway migrate check` (validate and report: current, unapplied counts, not initialized, or refused with the reason) and `gateway migrate up` (apply pending migrations serialized by a stable advisory lock that is released by closing the migrator's connection on every code path, with per-transaction `SET LOCAL` statement and lock timeouts governed by the new `DATABASE_MIGRATION_STATEMENT_TIMEOUT_MS`, default 60 s, max 600 s). Serving replicas validate only: a schema behind the binary fails startup naming the migration job, a ledger that is not a checksum-matching gap-free prefix of the binary's manifest — an unknown version written by a newer gateway, an edited migration's checksum, a manually reordered or gapped ledger — fails startup fail-closed, and the new `DATABASE_AUTO_MIGRATE` (default false, rejected in standalone mode) opts development deployments into startup auto-migration without weakening any ledger rule. Pooled sessions pin `search_path` to the gateway schema so nothing resolves objects through ambient defaults, and migration SQL files are committed without line-ending normalization (`.gitattributes`) because their bytes are their checksums. CI runs the whole matrix — bootstrap, idempotent re-runs, tampered-checksum and newer-gateway refusals, concurrent migrators producing exactly one applier, and a no-DDL role that can validate but cannot migrate — against the real PostgreSQL 16 service. See the expanded [PostgreSQL deployment guide](docs/deployment/postgres.md) for the migration job, role grants, and the restore-based rollback boundary.

- The PostgreSQL foundation of cluster mode (issue #241, experimental): `STATE_BACKEND=sqlite|postgres` selects between unchanged standalone mode and an opt-in PostgreSQL-backed cluster mode whose substrate this change lays, behind a `postgres` cargo feature that ships in default builds so official binaries carry it while a `--no-default-features` build refuses the mode at startup naming the feature. Cluster mode requires `DEPLOYMENT_ID` (stable, non-secret, shape-validated) and `DATABASE_URL_FILE`, a permission-checked secret file holding the connection string — its contents never enter configuration, `Debug` output, logs, metrics, status, or errors, and the DSN itself must be a fully-stated `postgresql://` URL whose query parameters are limited to `user`, `password`, `host`, `port`, `dbname`, and `application_name`, so `sslmode`/`options` cannot override the gateway's own TLS policy and session timeouts. Any writable local authority (`POLICY_FILE`, `TOOLS_FILE`, any `*_SQLITE_PATH`) set alongside postgres mode fails startup naming the setting: a second authority next to the database is a fallback path, not a leftover; symmetrically, postgres material set in sqlite mode is rejected. Connections require TLS with certificate and hostname verification by default, against the platform trust store plus an optional `DATABASE_TLS_CA_FILE` bundle, with one named exception — `DATABASE_TLS_MODE=loopback-dev`, refused for any non-loopback or non-Unix-socket target. The pool is bounded (`DATABASE_POOL_MAX`, 1-256) with connect and acquire timeouts, and every pooled session carries server-side `statement_timeout`, `idle_in_transaction_session_timeout`, and `lock_timeout` set as startup parameters no code path can `SET` back. A database unreachable at startup is retried on a bounded doubling backoff (`DATABASE_STARTUP_RETRY_LIMIT`, ceiling 300) and then fails startup — never a silent fallback to local state. Each replica also generates per-boot instance and boot IDs and computes a SHA-256 static-configuration fingerprint over the security-relevant non-secret configuration (auth/providers, trusted proxies, cookie and exemption settings, routing, egress, policy mode, key-generation IDs — never secret values), which later #241 PRs register and check cluster-wide so a replica enforcing a different policy can never become ready. Cluster mode is not a supported HA configuration until the #241 release gate passes; see the new [PostgreSQL deployment guide](docs/deployment/postgres.md), which includes the least-privilege runtime and migration role model.

- Add the `google_domain_wide_delegation` Connection credential (part of #442). A Connection to a Google Workspace API can now call it as the calling user, with that user's own Google token minted by domain-wide delegation, without any per-user grant and without a service-account key in the gateway. It names a dedicated `service_account_email`, a `workload_identity_profile` (the `id` of a `CONNECTION_GCP_PROVIDER` profile: a reference to startup configuration, never a token file, audience or key), its `scopes`, `subject_claim: email`, and `subject_issuers`, the identity providers trusted to name Workspace users by email, because any configured provider can put any address in its tokens. On a cache miss the gateway builds the claim set (`iss` the service account, `sub` the caller's email, `scope`, `aud` `https://oauth2.googleapis.com/token`, `exp` 300 seconds after `iat`), has Google sign it through IAM Credentials `signJwt` authenticated as the profile's federated identity (the GCP provider's own token cache and refresh; a refused federated token is replaced once), refuses a signed assertion whose claims are not exactly those sent, and exchanges it with the JWT bearer grant (RFC 7523). As with every refusal on such a Connection, a composite tool reports `composite_failed` at the tool level with the step's reason only in the error details, a proxied request records the reason through tracing only, and a `TOOLS_FILE` tool or proxy route bound to it fails startup or the reload that contains it, like a binding to a disabled Connection.

- A Connection carrying a `caller_assertion` block is now refused instead of served without the assertion (part of #463). The block has been accepted and stored since it was added to the Connection model, but nothing mints or injects the assertion yet, so every call on such a Connection reached the upstream carrying only the service credential, including calls that arrived with no principal at all: a silent fail-open for an operator who configured "every call names its caller". Until request-path injection ships, tool calls, proxied requests, managed MCP sessions, OpenAPI and MCP discovery, enum and label source fetches and stored Connection tests on such a Connection fail before any DNS lookup, secret read, OAuth mint or upstream request, with the fixed reason `caller_assertion_not_enforced`. It appears in the `failure_reason` of `tool.invoke_failure` (for a composite tool that is `composite_failed`, and the step's reason is only in the error details returned to the caller), in the Connection test stage reason, in the `409` OpenAPI and MCP catalog error, and in `connection.enum_source_refresh_failed`; a proxied request returns `502` and records the reason only as `error_category` on the gateway's warning log line, as for every other Connection failure on a proxy route. A managed OpenAPI catalog on such a Connection is withdrawn from the tool list, as for a disabled Connection, and kept in storage. **Upgrade note:** a `TOOLS_FILE` tool or a proxy route bound to a Connection that already carries the block is now rejected the way a binding to a disabled Connection is, so startup or the whole reload that contains it fails, not only that binding. A replacement write that omits `caller_assertion` now keeps the current block instead of removing it, because the admin UI does not edit the block and a routine save there used to strip it and put the Connection back into service unattested; send `"caller_assertion": null` to remove it. New and replacement writes also reject `bind_approval: true`, since no approval subsystem exists to bind to, and an assertion `header_name` that matches an additional header name in any case. Documents persisted before these two rules remain readable and are refused at runtime like every other Connection carrying an assertion. Remove the block to use the Connection meanwhile.

- Tool input validation compares numbers exactly and no longer panics on them. The workspace keeps JSON numbers as their literal text (`serde_json`'s `arbitrary_precision`), but `jsonschema` was built without its matching `arbitrary-precision` feature, and those code paths assume every number fits a `u64`, `i64` or `f64`. An argument past that range, such as `1e400` or a 400-digit integer, checked against `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, a numeric `enum` or `const`, or `type: integer`, reached an `unreachable!()` and ended the request's task without a response or an audit record. jsonschema 0.58.0 removed some of those panics but not all of them: `type: integer`, an `enum` with a fractional member and a schema limit past `f64` still panic in 0.58.6. `jsonschema` now moves 0.56 to 0.58.6 and is built with `arbitrary-precision`, so these keywords compare exactly: `18446744073709551617` no longer matches an `enum` of `18446744073709551616`, `0.30000000000000001` now exceeds `maximum: 0.3`, and `1e400` is an integer and a multiple of 2. Exact comparison costs more as numbers get wider, roughly the square of the digits a number spans (mantissa digits plus exponent): eight bytes of `1e-99999` kept the validator busy for more than five seconds. So the numbers in one call's arguments now share a budget: each number wider than 20 digits is charged its span squared, up to what one 1,024-digit number costs (`1e400` fits six times), and a call over the budget fails as `invalid_params` with an audited `number_width` problem before the validator runs. Tool input schemas are held to the same budget when they load, and a served schema over it fails closed instead of compiling. 0.58 also fixes a `$ref` to an `$anchor` validating against a different anchor in the same document (0.58.2), `\s` in `pattern` missing most Unicode space separators (0.58.6), and ECMA regex character class literals being read as Rust set operations (0.58.6). A new test shows `idn-email` and `idn-hostname` still reject invalid values through the `idna` feature. The admin UI also moves to Vite 8.3.4, past three dev-server advisories published on 2026-10-06 that affect 8.3.0 to 8.3.2: [GHSA-rq7h-c2jc-7f22](https://github.com/advisories/GHSA-rq7h-c2jc-7f22) and [GHSA-vfpm-58rq-9qcg](https://github.com/advisories/GHSA-vfpm-58rq-9qcg) expose files outside `server.fs.allow`, and [GHSA-9jrq-w75r-8gcw](https://github.com/advisories/GHSA-9jrq-w75r-8gcw) allows cross-origin script execution through custom middleware. They affect `npm run dev` only; the embedded production bundle does not run the dev server.
- Connection overlay documents now spend the exact-comparison number budget before the overlay schema checks them. The shipped overlay schema compares integer fields such as `enum_sources.*.cache.ttl_secs` and `source_limits.*` against `type: integer`, `minimum` and `maximum`, and with exact comparison that work grows with the square of a number's span, but only tool arguments, agent schema fragments and compiled schemas were held to the budget. A 79-byte overlay carrying `"ttl_secs": 1e-20000` kept the validator busy for about seven seconds, and the schema allows hundreds of such fields, so one `POST /v1{ADMIN_PREFIX}/connections/{id}/openapi/preview` from a principal holding only `admin:tools:read` could hold a runtime worker for hours, where a request timeout cannot cancel it; `PUT` of an overlay did the same while holding the Connection's catalog-mutation guard. An overlay whose numbers would cost more to compare than one 1,024-digit number is now refused with a single problem at `/` before the schema runs. Agent schema fragments keep their own per-fragment check, and a stored or imported overlay is checked the same way when it is loaded.

- Request admission and authentication now enforce the bounds the policy kernel evaluates under, so no request the gateway serves can later be refused at authorization for its shape (issue #488). Three limits are new at admission, each with its own status: a request path longer than `MAX_REQUEST_PATH_BYTES` (default and ceiling 8192, the kernel's own bound) is `414 URI Too Long`; an HTTP method longer than 64 bytes is `501 Not Implemented`; and the request's host -- the `Host` field, or the target's authority where there is one (`:authority` on HTTP/2, so the gRPC listener is covered) -- is validated as `uri-host [":" port]`: a repeated `Host`, a value that is not visible ASCII, a bracketed value that is not an IPv6 literal, a port that is not a port, a character RFC 3986 does not allow in a host, or a `Host` that disagrees with the authority (RFC 9113 section 8.3.1) is `400 Bad Request`, and a host longer than 4096 bytes is `431 Request Header Fields Too Large`. Previously `[a:b:c]` was read as the host `a:b:c` and `host:x` as `host`, and an HTTP/2 `:authority` was never read at all, so host-qualified routes could not match on the gRPC listener; both are now malformed input, the authority now serves as the host, and a rejected host is never echoed. Principal claims are bounded at authentication by every validator -- at most 256 roles, each at most 256 bytes and none empty, and a subject of at most 4096 bytes -- and a credential outside them is `401` (for a JWT, before the revocation store is consulted); the validator's rejection names the bound, while the `auth.failure` audit reason stays the validator chain's generic message. An empty role name, which could never match a policy role, is refused alongside the existing empty-subject check. Service-token scopes are held to the same bounds when a token is created (`400`) and when it authenticates (`401`), and a stored token whose scopes are outside them can no longer be rotated into a fresh credential authentication would refuse (`409`; revoke and recreate it). Configuration that becomes an evaluation input is bounded at startup: a route `path_prefix`, an upstream URL or `GATEWAY_PUBLIC_URL` over 4096 bytes, or a provider issuer over 4096 bytes, is a refused configuration. None of these limits was enforced before: an 8 KiB path or a 300-role token was authorized normally, which the pending kernel cutover (#422) would have turned into a failure at authorization time.

- The rate limiter's bucket storage is now bounded, closing an unbounded-memory cardinality attack: previously every unique rate-limit key -- every distinct source IP, every distinct principal identity -- added a bucket to a `HashMap` for the lifetime of the process, and a principal's `user_id` arrives from a token claim with no length bound of its own, so the memory per entry was attacker-influenced as well as the entry count. Two new settings bound and shape the store: `RATE_LIMIT_MAX_BUCKETS` (default 65536) is a hard ceiling per limiter -- the read lane, the write lane, and each policy `rate_limits` rule each have their own store -- and `RATE_LIMIT_BUCKET_TTL_MS` (default 10 minutes) biases eviction towards buckets a caller has stopped using. At the ceiling one bucket is recycled per new key, second-chance: idle-beyond-TTL first, then scan order, with recently-used buckets earning a reprieve, so a spray of throwaway identities recycles itself rather than displacing active callers. Buckets are keyed by a 64-bit hash of the rate-limit key rather than the key text, so each entry is a fixed handful of bytes no matter how long an attacker's identities are. Eviction resets the evicted key's allowance, so a working set larger than the ceiling continuously recycles callers -- observable as the new `rate_limit_buckets{limiter}` gauge pinned at the ceiling with `rate_limit_bucket_evictions_total{limiter,reason}` climbing, which is the documented signal to raise the ceiling. Two limits stated plainly rather than implied: a spray of more distinct keys than the whole ceiling between two requests from one caller displaces even that caller, as it must in any bounded store; and the ceiling and eviction are per process -- each replica of a multi-replica deployment tracks independently, so shared enforcement across replicas remains open and is planned on the #241 shared-state substrate rather than on a mandatory Redis/Valkey dependency, which this project will not take.

- Inbound TLS certificates now reload without a restart and without dropping established connections. When the files named by `TLS_CERT_FILE`/`TLS_KEY_FILE` or `ADMIN_TLS_CERT_FILE`/`ADMIN_TLS_KEY_FILE` change -- rewritten in place, atomically replaced, or rotated the way the kubelet flips the `..data` symlink a projected Secret's leaves resolve through -- a per-listener watcher on the same machinery `TOOLS_FILE` and `POLICY_FILE` already use reloads them, debounced, with `SIGHUP` as an additional trigger on Unix. **Established connections are untouched by construction**: the reload swaps only the certificate-chain set the live `ServerConfig`'s resolver hands to new full handshakes, through one atomic pointer read per handshake; the `ServerConfig` itself, the accept loop, its admission semaphore, and every stream already handed to the router are never touched, and a request in flight across a reload completes on the connection it started on. **Reload validation is startup validation** -- the same loader and the same resolver builder, not a second copy of the decision -- so parse, size, permissions, the key-matches-leaf pairing, and the SNI name rules over the whole set all run before any swap, and a rotation that fails any of them keeps the last good chains serving. That rejection is observable as an `inbound_tls.reload_failed` audit event, an `inbound_tls_reloads_total{listener,outcome="rejected"}` counter, and an error log line, with the error text carrying only setting names and DNS names on the same discipline as startup errors; there is no retry schedule, so material that stays broken costs exactly one failed attempt. The file watcher also emits a liveness heartbeat -- `inbound_tls_watch_heartbeats_total{listener}`, advancing every few seconds while the watching task runs -- because a dead watcher is otherwise indistinguishable from unchanging certificate files, and rotation silently believed working is the worst state this machinery can be in. The whole SNI chain set reloads as a unit, and the two listeners reload independently. A reload cannot revisit any startup decision except the chains: the client-certificate CA bundle and CRL stay read-once-at-startup (still deferred, still documented), session resumption stays disabled on client-certificate listeners (`send_tls13_tickets=0` and an empty session store hold after a swap, pinned by a pointer-equality test that fails if a reload ever replaces the `ServerConfig`), and ALPN stays `http/1.1`. A deployment whose cert files never change after startup sees no behaviour difference beyond the watcher existing. OCSP remains out of scope.

- Added optional inbound client-certificate authentication, as a first-class validator in the existing auth chain rather than as a side door around it (`CLIENT_CERT_MODE`/`ADMIN_CLIENT_CERT_MODE`, `CLIENT_CERT_CA_FILE`/`ADMIN_CLIENT_CERT_CA_FILE`, `CLIENT_CERT_CRL_FILE`/`ADMIN_CLIENT_CERT_CRL_FILE`, and `CLIENT_CERT_IDENTITY_SOURCE`). Off by default on both listeners: a deployment that sets nothing requests no certificate and runs the same code the previous release did. A verified certificate becomes a `Principal` with `auth_method = client_certificate`, and goes through the same authentication middleware, the same validator chain, and the same RBAC evaluation as a bearer token; `client_certificate` is a new value for a policy rule's `auth_methods`, so existing rules naming `bearer_token` do not start matching certificate callers. `optional` and `required` differ in exactly one thing -- what happens to a caller who sends no certificate -- and a caller who does send one is verified identically under both, so presenting nothing is never worth more than presenting something invalid.

  **Trust anchors are the operator's and only the operator's.** Client certificates are verified against the configured CA bundle, never the platform trust store, and there is no setting that opts into it: trusting the operating system's roots for *client* authentication would mean every certificate every public CA has ever issued authenticates. A mode that asks for certificates without a bundle, without an identity source, or on a listener that terminates no TLS fails startup rather than quietly accepting anonymous connections.

  **Identity is one configured field, exactly one value, canonical and bounded.** `CLIENT_CERT_IDENTITY_SOURCE` selects a SPIFFE ID in a URI SAN (recommended: one per SVID by specification, canonical by specification, and stable across renewal), any URI SAN, or a DNS SAN. A certificate carrying no value of that kind has no identity, and one carrying two *different* values has no identity either -- the gateway never takes the first of several, because whoever assembles a certificate chooses the order of its SANs. A certificate that verifies but yields no identity establishes its connection and is then answered `401` with no principal. The subject DN is deliberately not offered: rendering a DN as text means choosing an escaping that libraries disagree about, and a CA that lets a requester choose their own `CN` lets them choose one containing `,OU=` that collides with somebody else's rendered identity. Identities are held to at most 255 bytes of printable ASCII before becoming a principal, an audit field, or a log field, and are never used as a metric label; the label values are a closed set of compile-time constants.

  **A listener that requests client certificates does not resume TLS sessions, and a credential the caller sends outranks the certificate their connection was established with.** Both are load-bearing and both are now pinned by tests that fail without them. Resumption is disabled — empty session store, no TLS 1.3 tickets — only on listeners where `CLIENT_CERT_MODE` is not `off`, so a deployment that has never heard of client certificates is unaffected. It has to be: a resumed handshake carries no `Certificate` and no `CertificateVerify`, so rustls restores the earlier connection's chain and re-checks nothing about it, which would let an expired or revoked certificate keep authenticating for up to 24 hours and would make everything above about CRLs stop applying to exactly the callers it exists to stop. Re-validating the restored chain would not have been enough, because a resumed connection proves the caller holds the resumption secret rather than the certificate's private key — the proposition mutual TLS is bought for — and there is nothing on such a connection for them to have signed. 0-RTT early data is never enabled on any inbound listener. Separately, a request carrying a bearer token or session cookie is judged on that credential and not on the connection's certificate, so a valid certificate never rescues an expired, revoked, or unknown token: that request is answered `401` rather than served as the certificate's subject.

  **Revocation is checked only when CRLs are configured, and this is stated rather than implied.** rustls consults neither CRLs nor OCSP by default and the gateway adds no other source, so with `*_CLIENT_CERT_CRL_FILE` unset a revoked certificate authenticates until it expires. With it set, revocation is enforced over the whole verified chain, an undeterminable status is a failure, and an expired CRL is treated as no CRL rather than as a still-valid one -- so a CRL that stops being refreshed eventually refuses every caller, which is deliberate: the alternative is a deployment that has silently stopped checking revocation. `inbound_client_certificates_total{listener,outcome}` reports each outcome, including `rejected_revoked` and `rejected_expired_revocation_list`.

  Certificate identity cannot be asserted through a header: it is a request extension written only by the listener that terminated the handshake, and 19 further mTLS assertion headers used by nginx, HAProxy, Traefik, and Envoy (`ssl-client-verify`, `x-ssl-client-s-dn`, `x-forwarded-tls-client-cert`, `x-spiffe-id`, and the rest) join the two already there, so all 21 are stripped as spoofable, so a caller cannot borrow the gateway's position in a topology to assert an identity to an upstream. The CA bundle and CRL are read through the same bounded, capability-confined reader as the server certificate, under the public-material permission rule: group and other *read* is permitted, *write* fails startup. Handshake-time identity extraction runs inside the existing per-listener handshake bound, so it cannot be used to stall an accept loop. Cloudflare Containers cannot carry client certificates -- the edge terminates the caller's connection -- so these settings are deliberately not forwarded there. Hot certificate reload, OCSP, and roles derived from certificates remain out of scope.

- Added SNI support to inbound TLS termination: `TLS_CERT_FILE`/`TLS_KEY_FILE` and `ADMIN_TLS_CERT_FILE`/`ADMIN_TLS_KEY_FILE` now accept a comma-separated list of paths, positionally paired, one key per certificate chain. A deployment that sets exactly one path gets the behaviour it had before, byte for byte. With more than one chain, the listener selects by the server name in the client's TLS handshake: each chain answers to the DNS subject alternative names on its leaf, read by the same parser that verifies chains and lower-cased for ASCII, with the subject CN deliberately not consulted. An exact name beats a wildcard, a wildcard matches exactly one further label (`*.example.com` serves `a.example.com` and neither `a.b.example.com` nor `example.com`), and a client that sends no server name -- or names one nothing claims -- is served by the first chain in the list, which is therefore the listener's default. Selection failures are configuration failures: two chains claiming the same name or wildcard fail startup naming the duplicated name, and a later chain with no DNS SANs fails startup because no server name could ever select it (only the first chain may be nameless, since it is the default). A name that is neither a valid DNS name nor a valid wildcard name is unclaimable rather than matched by something looser than it says. List validation is fail-closed on both ends: an empty entry is refused rather than skipped -- a skipped entry would silently shift every later pairing by one -- and the two lists must agree in length. Selection composes with client-certificate authentication, and a listener that requests client certificates still disables session resumption regardless of how many chains it serves. There is no per-request SNI metric or log field: the server name is caller-controlled, and a caller-controlled label set is a cardinality attack waiting to happen. Paths containing commas cannot be expressed in the list grammar.

- Added an opt-in transparent gRPC proxy transport over HTTP/2 (`GRPC_LISTEN_ADDR`, unset by default, plus a per-route `UPSTREAM_ROUTES[].grpc` policy block). All four call shapes are supported -- unary, server-streaming, client-streaming, and bidirectional -- with gRPC framing, response trailers, deadlines, cancellation, and backpressure preserved end to end and no protobuf inspection or rewriting anywhere. It is a **third listener** rather than a mode on an existing one, deliberately: `axum::serve` builds its HTTP/2 handling internally and exposes no way to configure it, so the resource bounds this transport requires would be unreachable; it also enables RFC 8441 extended `CONNECT` unconditionally, which is a non-goal here; and with `ADMIN_LISTEN_ADDR` unset -- the default -- the admin API shares the data listener's socket, so a mode on that listener would put h2c on the admin surface for every default deployment. The data and admin listeners are untouched and still refuse an HTTP/2 connection preface. HTTP/2 is enabled by depending on `hyper` directly with `http2`, which does **not** enable `hyper-util/http2`; `scripts/check-egress-only.sh` continues to assert that by feature name, and now additionally confines HTTP/2 client and server construction to one named file each. The gRPC listener runs the identical middleware stack as the data listener -- the same `apply_middleware` call with the same value -- so authentication, rate limiting, CSRF, request validation, route classification, RBAC, and direct policy all complete before any DNS lookup, connection, or upstream byte; a denied call produces a protocol-correct gRPC trailers-only response and is asserted to cost zero resolutions and zero accepts. The canonical authorization identity is `/package.Service/Method`, held to the protobuf identifier grammar so it has exactly one spelling. The gateway owns the upstream `:authority`, `content-type`, `te`, and `grpc-timeout`; the client's `Authorization`, `Cookie`, `Host`, forwarding metadata, and hop-by-hop headers never cross the boundary. Per-route bounds cover concurrent calls (per route and per endpoint), admission queue depth and timeout, encoded message size, total bytes per direction, metadata entry count, and connect, idle, and total-duration deadlines; the listener bounds concurrent streams, metadata bytes, frame size, flow-control windows, accepted connections, and the pending-accept-reset allowance that closes the HTTP/2 Rapid Reset shape. Retries are disabled. Protobuf bytes and raw upstream `grpc-message` values never reach logs, metrics, audit, or public errors. Deployment is h2c prior knowledge behind a terminator that re-originates h2c (nginx `grpc_pass`, Envoy); **Cloudflare Containers can never carry gRPC**, because the edge terminates and the Durable Object reaches the container over HTTP/1.1, so the gRPC settings are deliberately not forwarded there. See [docs/deployment/grpc.md](docs/deployment/grpc.md).

  Two properties of that transport are worth stating on their own, because both were wrong in an earlier revision of this change and both are now pinned by tests that fail without them:

  **The effective deadline covers the whole call, from admission.** It is the smaller of the client's capped `grpc-timeout` and the route's `max_duration_ms`, and it is armed before the gateway connects, so one budget spans the admission queue, the wait for the upstream's response HEADERS, and the streaming phase. Arming it only for the streaming phase would have left the pre-HEADERS window unbounded while the admission permit, the endpoint slot and the response-stream registration were all held — which is where a unary RPC spends essentially all of its life, since grpc-go and tonic send HEADERS when the handler returns. Related: `connect_timeout_ms` now waits for the peer's own HTTP/2 connection preface, because `hyper`'s client handshake resolves once the *gateway's* preface has been written and a peer that accepts a socket and then says nothing would otherwise pass every check. It does **not** bound acquiring stream capacity — `hyper`'s `SendRequest::ready()` reports connection liveness rather than `SETTINGS_MAX_CONCURRENT_STREAMS` credit — so a saturated upstream is bounded by the call deadline like any other upstream that has not answered.

  **`AUTH_EXEMPT_PATHS` and `RBAC_EXEMPT_PATHS` do not apply on the gRPC listener.** Those lists exist to let gateway-owned surfaces through without a credential, and the gRPC listener serves none: its only route is the proxy. An exemption matching there could therefore grant exactly one thing, an unauthenticated and unauthorized call forwarded to an upstream. `ADMIN_PREFIX` is in both lists by default and entries are segment-boundary prefixes, so `/admin/Ping` — a well-formed gRPC method path — would have been proxied with both checks skipped, and the startup warning about unowned exempt paths would not have fired because the entry *is* gateway-owned. The gateway's reserved namespace and unsafe raw paths are additionally refused on that listener with `UNIMPLEMENTED`, mirroring the HTTP fallback's `404`. `CSRF_EXEMPT_PATHS` still applies, because a CSRF exemption grants nothing on its own. There is no supported way to expose an unauthenticated gRPC method today.

- Outbound TLS is now configured once, explicitly, inside the egress boundary and handed to the HTTP client, instead of being assembled by reqwest from the CA bundle and client identity it was given. - Added explicit per-route SSE streaming with prompt response-header commitment,
  separate pre-commit/idle/byte/duration controls, bounded backpressure, and
  payload-free terminal audit/metric outcomes for completion, disconnect,
  limits, upstream failure, and shutdown. Ordinary proxy routes retain their
  existing first-chunk pre-commit behavior.

- Added gateway-owned `/livez`, `/startupz`, and `/readyz` lifecycle probes,
  coordinated Ctrl-C/SIGTERM shutdown, bounded in-flight draining, and durable
  audit flush acknowledgement. These three probe paths are now reserved and
  can no longer fall through to an upstream route, which is a proxy-path
  compatibility change. Deployments should use `/readyz` for readiness while
  retaining `/health` only for its legacy compatibility contract.

- `UPSTREAM_ROUTES` now supports stable logical route IDs and static weighted
  endpoint pools with strict startup validation. Physical endpoint selection
  occurs only after authorization and bounded pool admission; configured
  concurrency, queue depth, and queue timeout prevent unbounded work, and
  saturation returns a sanitized `503` without DNS or upstream traffic.
  Existing single-URL routes map to a one-endpoint pool.

- Added a fail-closed request-body abstraction for buffered and streamed proxy
  uploads. Streamed bodies are counted independently of `Content-Length`,
  reject known oversize lengths before DNS, forward no more than the configured
  byte ceiling, preserve backpressure and cancellation, and never turn
  truncated discovery samples into schema evidence. Buffered proxying remains
  the compatibility default; pooled routes may opt into stream mode.

- Outbound HTTP used by the egress client, reverse proxy, identity-provider
  discovery/session calls, and MCP upstream transport now ignores ambient
  `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and lowercase equivalents. This
  prevents process-environment proxy discovery from bypassing validated DNS
  pinning. Deployments that previously depended on those variables now require
  direct connectivity; an outbound proxy will require a future explicit,
  validated gateway configuration.

- Proxy, health-check, identity-egress, and MCP transport failures now log only
  bounded error categories. Post-commit response-stream errors are redacted,
  and the non-standard hop-by-hop `Proxy-Connection` header is stripped in
  both directions. MCP auth challenges, response bodies, content types, and
  discovery egress details are no longer retained in displayable errors.
  Dependency-internal `rmcp` tracing is disabled because it can include peer
  metadata and session identifiers; gateway-owned bounded MCP outcome logs and
  audits remain available.

- Caller-provided buffered bodies on `EgressClient` request paths are now
  rejected before DNS resolution. Gateway MCP `call_tool` payloads are
  conservatively sized and rejected before destination resolution, connection,
  or session initialization, so those guaranteed size denials cannot produce
  upstream traffic.

### Added

- Added an opt-in, per-route WebSocket proxy transport. The gateway terminates
  both sides and re-originates the upgrade rather than tunnelling bytes, so
  frame, assembled-message, and write-buffer bounds, the subprotocol allowlist,
  and close-code propagation are all enforceable. Authentication, rate
  limiting, RBAC, direct policy, route classification, CSRF, and admission all
  complete before the upgrade is considered, and every rejection reachable
  before the egress step produces no DNS lookup, no connection, and no upstream
  byte. The upstream handshake is rebuilt from validated state -- a freshly
  generated `Sec-WebSocket-Key`, the negotiated subprotocol, and the normalized
  allowlisted `Origin` -- and the upstream answer is checked fail-closed for its
  status, `Sec-WebSocket-Accept`, subprotocol, and the absence of any
  extension. Upgraded connections use a dedicated admission pool and
  per-endpoint slots so an hour-long socket cannot starve the route's HTTP
  traffic, survive drain, and end at forced shutdown with `1001`. RFC 8441
  extended `CONNECT` over HTTP/2 and compression negotiation remain out of
  scope.
- Added permission-separated managed Connection CRUD under
  `/v1{ADMIN_PREFIX}/connections`, with redacted read models, server-derived
  actions, cursor pagination, conditional collection/resource ETags, bounded
  request bodies, dependency-safe deletion, atomic runtime publication, and
  payload-safe connection and credential-change audit events.
- Completed issue #240's first-class Connection control plane: trusted
  environment/file aliases, write-only encrypted local secrets with bounded

  [AWS Secrets Manager #272](https://github.com/Greenhat-Security/GreenGateway/issues/272),

- Expanded the Docker development stack to three controllable weighted

- `UPSTREAM_URL`, legacy `UPSTREAM_ROUTES` destinations,

### Migration

- Enabling `CONNECTIONS_SQLITE_PATH` does not convert or disable legacy
  configuration. Legacy upstreams remain read-only projections until each
  route, tool, OpenAPI catalog, or MCP server is explicitly rebound to a
  managed Connection. Preserve old deployment settings and policy until the
  managed lane passes its acceptance window.
- Traffic rollback restores the prior legacy route/tool/MCP configuration and
  disables the managed Connection; it does not require deleting Connection
  metadata, clearing protected bindings, or restoring an older database.
  Database disaster recovery must restore the consistent SQLite/WAL boundary
  together with every master key still referenced by its encrypted rows. See
  [the Connections migration guide](docs/connections/migration.md).

### Fixed

- The scheduled security mutation campaign no longer fails before measuring anything (part of #420). Its clean-source check ran `git status` under the 64 KiB-plus-one-byte file-size limit of short commands, and on a fresh checkout `git status` refreshes stale stat data by rewriting `.git/index`. At `d403b75`, with 693 tracked files, the index is 73,041 bytes, so git was killed with `SIGXFSZ`, and the report stopped at phase `initializing` with reason `process_failure`. The controller's git commands now run as `git --no-optional-locks` and only read the repository; the file-size limit is unchanged. A regression test builds a repository whose index is larger than the limit and runs the campaign's git steps under the controller's own limits. See [the budgets](docs/testing/security-mutations.md#budgets-and-evidence).

- Saving an MCP Connection in the admin UI no longer deletes its stored test profile. The editor hides the test-profile section for MCP Connections and dropped any profile the Connection had been saved with through the admin API. The profile is inert on an MCP Connection, but dropping it changed the stored record on an unrelated save, and on a credentialed Connection the changed test target made that save require secrets permission. Switching a Connection's kind to MCP in the editor still clears the profile.

- Container release tags now depend on successful checks for the exact commit. CI builds a unique candidate, waits for all validation and secret-scanning jobs, and promotes its immutable digest without rebuilding. Pull-request builds cannot publish, and runs superseded before the final ref check leave their candidates unpromoted.

- Policy screens now use server-computed write permission instead of decoding JWT roles in the browser. Repeated saves of a new rule update its returned ID, and the default-deny banner accurately describes forwarding under global shadow enforcement.

- Historical audit search and policy rule preview now read PostgreSQL audit events in cluster mode through the shared storage interface. Preview scans use bounded pages on both backends; permissions, filtering, matching and newest-first samples are preserved.

- Included global read/write rates and bursts, bucket capacity and idle TTL, and rate-limit key-generation IDs and roles in cluster configuration agreement. Divergent joining replicas remain unready. Fingerprint format v2 requires a coordinated fleet cutover; reordered key entries and different local key paths still agree, and secret key material remains excluded.


- Bound admin SSO callbacks and completion to the browser that initiated login using a short-lived HttpOnly transaction cookie. The UI now exchanges the authorization code and state in a same-origin, single-use POST; access tokens no longer travel in redirect fragments. PostgreSQL-backed completion remains atomic across replicas. In-flight logins and open admin pages from the previous protocol must be restarted or reloaded after upgrading.

- Service-token rotation now requires the same live, identity-qualified scope
  delegation authority as creation. Rejected rotations emit a delegation-denied
  audit event and leave the existing credential unchanged. Token administrators
  can still revoke tokens without holding their scopes.
- Concurrent first-use JWT validation now re-checks the verified JWKS key cache
  after a coalesced refresh. Valid waiters no longer receive a spurious
  `unknown kid` rejection when the leading request has populated the key; an
  absent or unverifiable key still fails closed.
- Configured replay-safe proxy methods can now retry a request-phase transport
  disconnect that occurs before response headers, such as a severed reused
  HTTP/1.1 connection. The configured attempt limit, total deadline, alternate
  endpoint preference, and retry budget remain authoritative. Streamed or
  otherwise non-replayable bodies, unsafe methods, TLS validation, policy/DNS
  denial, body failures, cancellation, and post-commit failures remain
  non-retryable.

## [1.0.1] - 2026-07-16

### Security

- Service-token creation now rejects scopes that exceed the creator's current
  authority. An identity-matched wildcard role may delegate any scope;
  otherwise every requested scope must be a defined policy role that the
  creator carries and can activate. Rejected delegation attempts are recorded
  as `service_token.delegation_rejected` audit events. Existing tokens are not
  changed automatically and should be reviewed for over-broad scopes.

- `POST /v1{ADMIN_PREFIX}/policy/rules/preview` now requires both
  `admin:policy:read` and `admin:audit:read` because its response discloses
  audit-history samples and counts. Roles that need rule preview must be
  granted both permissions; previously `admin:policy:read` alone was enough.

- MCP routes derived from `GATEWAY_PUBLIC_URL` are no longer treated as
  authentication, RBAC, or CSRF exempt when they overlap an exempt prefix.
  Exact MCP aliases remain protected, non-MCP subpaths keep their existing
  exemption behavior, and startup warns about authentication or RBAC overlaps.

- Bound discovery endpoint-template cardinality with approximate-LRU eviction
  (`DISCOVERY_ENDPOINT_LIMIT`, default `10000`) to prevent unauthenticated
  storage and memory growth from attacker-controlled request paths (F8).

- Policy hot reload and the policy administration API now reject changes to
  the policy `egress` section. Egress allowlist changes require a gateway
  restart; previously a reload appeared to accept them while long-lived
  egress clients continued enforcing the startup allowlist (F3/F9/F10).

- Hardened admin OIDC login pending-state handling with configurable positive
  TTL, process-wide, and canonical-client-IP limits. Capacity exhaustion now
  rejects new login attempts without evicting existing valid states.

- Shipped environment and deployment defaults no longer hardcode `/admin` in
  `AUTH_EXEMPT_PATHS` or `RBAC_EXEMPT_PATHS`; leaving them unset now preserves
  the dynamic defaults derived from `ADMIN_PREFIX`. Startup also warns when an
  explicit exemption names a path the gateway does not own and may therefore
  proxy upstream.

- Made audit retention pruning use an indexed epoch timestamp instead of a
  repeated full-table `julianday` scan, and limited pruning to at most once per
  minute (F13).

## [0.5.0] - 2026-07-04

### Added — Phase 5 (visual rule builder)

- Rule suggestions from observed traffic: a suggestion engine (evaluated
  off the request hot path) generating baseline `allow` suggestions from the
  observed role/endpoint matrix and anomaly-derived `deny`/`shadow`
  suggestions from open discovery signals, deduplicated against existing
  policy coverage. An admin API (`GET /v1{ADMIN_PREFIX}/suggestions`,
  `POST .../accept`, `POST .../dismiss`) requires `admin:suggestions:read`/
  `admin:suggestions:write`; accepting a suggestion additionally requires
  `admin:policy:write` since it creates a real policy rule.
- Visual rule builder UI: an ordered rule table (drag-reorder, enable/disable
  toggles, per-rule hit counts, action color coding, default-action banner)
  and a rule editor (visual matcher builder for method/path/principal/action
  with inventory-backed path hints, a debounced live preview against
  historical traffic before saving) — full rule lifecycle (create, edit,
  reorder, disable, delete) without touching JSON. One-click "create rule"
  actions from a traffic inventory endpoint, a live-tail event, or an
  anomaly signal pre-fill the editor's matcher fields; signal-originated
  rules default to `shadow` so their impact can be previewed before
  enforcing.
- Policy versioning, diff, and rollback: every policy mutation (rule
  create/patch/delete/reorder, full-document replace, and rollback itself)
  appends an append-only version record (actor, timestamp, structured diff)
  to a dedicated SQLite store; `GET /v1{ADMIN_PREFIX}/policy/history` and
  `POST /v1{ADMIN_PREFIX}/policy/rollback/{version}` expose it, with a
  version-history timeline UI (human-readable per-action diff sentences,
  one-click rollback validated against the current live policy ETag). A
  history-store write failure never turns an already-successful policy
  mutation into an error response — it's surfaced as a non-fatal
  `X-GreenGateway-Policy-History-Warning` response header instead.
- Shadow-mode review workflow: a review queue over the direct-firewall-rule
  engine's live `action: shadow` enforcement (rules are evaluated before the
  route-permission model; a matching shadow rule forwards the request and
  emits a real `authz.would_deny` audit event carrying the matched rule's
  id). `GET /v1{ADMIN_PREFIX}/policy/rules/shadow-review` aggregates, per

  one-click Promote (shadow → deny, gated behind an explicit confirmation
  step since it starts enforcing real blocks) and Disable actions.

### Fixed

- Firewall rules and rate-limit overrides with a path segment that looks like
  a capture but isn't valid (e.g. `/api/{bad-name}`, an unterminated
  `/api/{id`, or an empty `/api/{}`) are now rejected at policy-validation
  time instead of being silently persisted as a rule that can never match any
  request. Previously such a rule would save successfully and appear normal
  in the admin UI while providing no actual coverage.

## [0.4.0] - 2026-07-04

### Added — Phase 4 (traffic discovery)

- Endpoint path templating: normalizes concrete request paths into stable
  endpoint shapes (`/users/123` → `/users/{id}`), with well-known-ID
  recognition (numeric/UUID/hex-hash/ULID) plus a stateful, cardinality-bounded
  learner for slug-style segments.

  is also configured), plus `POST /v1{ADMIN_PREFIX}/traffic/endpoints/review`
  to mark/clear a persisted per-endpoint review flag. Endpoint lifecycle
  fields — `is_new` (configurable window), `reviewed`, and `covered_by_rule`
  (evaluated live against the active RBAC policy) — are independent booleans,
  not a single enum.
- Discovery UI: an embedded traffic inventory table (filters, cursor
  pagination, new/uncovered/reviewed badges, mark/clear review action) and a
  per-endpoint drill-down page (status/latency charts, principal breakdown,

  spec operations; opt-in (`PAYLOAD_CAPTURE_ENABLED`), off-by-default,

  bodies stored unless explicitly enabled; request-shape inference (query

  is configured; and request-time conformance checking — spec-based when a
  spec is configured, inference-based otherwise once enough samples exist —
  flagging missing required query params/JSON body keys or undocumented
  calls as `schema_mismatch` on the observation event, rolled up into a
  persisted `schema_mismatch_count` per endpoint. Conformance checking uses a
  short-TTL in-memory cache for the inferred-schema lookup path so it never
  re-scans the discovery database or re-parses historical samples on every
  request.

  entirely on the background aggregator thread, never inline in request
  handling — with a generic `Signal` model (type, target, explanation,

  principals), and `volume_outlier` (windowed baseline deviation) — each with
  its own configurable, validated threshold. An admin API
  (`GET /v1{ADMIN_PREFIX}/signals`, `POST .../acknowledge`,
  `POST .../dismiss`) requires the dedicated `admin:signals:read`/
  `admin:signals:write` permissions; a summarized `open_signals` field on the
  traffic inventory endpoints requires the same `admin:signals:read`
  permission in addition to `admin:traffic:read`, computed via a single
  set-based query per page rather than one query per endpoint. `signal.opened`
  and `signal.lifecycle_changed` events are pushed on the existing SSE feed,
  and a new admin UI Signals view (filter, evidence display,
  acknowledge/dismiss, live updates) plus signal badges on the traffic
  inventory surface all of the above.

  a self-verifying `.env.example`, and a drift-checked configuration reference.
- Security middleware stack: request-ID + tracing, config-driven CORS, header
  hardening (spoofable-identity stripping), body-size/content-type validation,
  token-bucket rate limiting with a spoofing-resistant canonical client IP, and
  double-submit CSRF — with an asserted middleware order.
- Authentication: a `Principal` model and pluggable `SessionValidator`s, a JWKS
  JWT validator (RS256, configurable roles claim, issuer/audience enforcement),
  and a fail-closed global auth middleware emitting auth audit events.
- Authorization: a deny-by-default RBAC policy engine with config-driven
  route→permission rules (segment-aware matching, unsafe-path fail-close) and
  authz audit events.
- Audit pipeline: a versioned event envelope with SHA-256 redaction, and
  asynchronous stdout/file JSONL sinks off the request hot path.
- Egress firewall: an SSRF-hardened outbound HTTP client (host allowlist,
  private-IP blocking including IPv4-mapped-IPv6/NAT64, pinned-IP resolution),
  with all gateway-originated HTTP routed through it and enforced by CI.
