# Policy evaluation parity matrix

Contract evidence for [#421](https://github.com/Greenhat-Security/GreenGateway/issues/421). It names, per lane, the legacy decision entry point, the kernel entry point that reproduces it, how inputs are normalized, what happens with no match, and what authority the result is bound to.

**HTTP/RBAC (#422 PR 1), the tool lane (#422 PR 2), rate-lane selection (#422 PR 3a), the static egress checks (#422 PR 3b), the admin analysis consumers (#422 PR 4) and, with the legacy retirement, the enum-source precheck and the tool-name coverage check of rule suggestions now use the shared evaluator.** The table names every pre-cutover decision entry point and its replacement. No serving path matches a policy rule outside the evaluator any more: `CompiledPolicy` holds the only serving `RuleMatcher`, one per compiled snapshot, and `the_evaluator_holds_the_only_serving_rule_matcher` fails any other construction outside test code. The tool runtime's non-RBAC fallback evaluates no rules, because a runtime without an `RbacState` has no policy (below). The pre-cutover implementations remain only as frozen test oracles, absent from serving builds and listed under [Legacy retirement](#legacy-retirement). Rule hit counts and the shadow rule review are recorded results, not evaluations, so no kernel entry point serves them, and management permissions are a separate authority the evaluator does not claim (`management_permissions` in `not_evaluated`).

## Trace reasons and limitation codes

Both sets are stable wire contracts, not internal names. `Reason` serializes as `matched_rule`, `missing_permission`, `missing_principal`, `default_allow`, `default_deny`, `host_policy_required`, `incomplete`. `Limitation` serializes as `missing_method`, `missing_path`, `missing_principal_fact`, `missing_dispatch_fact`, `missing_host_fact`.

Every `Limitation` variant now shares the `Missing` prefix, because every one is a fact that was not supplied — the kernel has no "unsupported" limitation since every target is evaluated. `clippy::enum_variant_names` is allowed there with that reason: dropping the prefix would edit a published contract to satisfy a naming lint.

## What is not evaluated

`Evaluation::not_evaluated` enumerates the stages a policy verdict says nothing about: authentication, CSRF, request admission, management permissions, MCP, tools, rate selection, mutable capacity, egress, DNS, transport, upstream execution, live revision freshness and gateway build identity. An `Allow` or `Observe` is never a statement that a request will succeed or forward.

## Facts the lanes require, and what happens without them

A supported fact that is unavailable produces `indeterminate` with a stable limitation, never a default. Three distinctions are load-bearing:

- **`HostFact` is three-state.** `Absent` is a request that carried no `Host` header; `Missing` is a host that was never captured. Only the second is unanswerable. `upstream_route::request_host_without_port` returning `None` means *absent* — mapping it to `Missing` would turn every Host-less request against a host-qualified policy into a denial the legacy path never produced. A malformed or oversized `Host` also yields `None`, but request admission has already answered such a request `400` or `431` before any policy runs (see below), so by evaluation time `None` is a request with no host.
- **`HttpTarget::Missing` means routing was never classified**, which is not the same as a request with no dispatch. A dispatch-scoped rule silently not applying is different from it not matching, and `routing_context_known` is the single bit that decides which happened. Production cannot reach this: `proxy_dispatch_context_middleware` is layered after the RBAC layer in `routing.rs` so that it runs before it, and marks classification unconditionally. `route_classification_is_marked_completed_for_every_path` holds that half of the invariant.
- **A missing principal is not an anonymous principal.** A rule may constrain the principal, so guessing would select a different lane or match a different rule.

## Invariants the kernel's correctness rests on

Neither is enforced by a type, so both are asserted by a test:

- **An MCP alias is never also a classified proxy dispatch.** `HttpTarget::McpAlias` and `ProxyDispatch` are mutually exclusive variants and the kernel evaluates an alias under `contextless()`, while the legacy path threads the real dispatch context into its alias branch. If a request were ever both, the two would diverge in both directions. It cannot happen because `proxy_dispatch_context_middleware` computes an observation context only for paths that are not gateway-owned, and `GatewayRoutes::from_config` puts every `mcp_route_paths` entry into `prefix_owned_paths` — two call sites of the same function, agreeing by shared derivation and nothing else. Asserted by `every_mcp_route_path_is_gateway_owned_so_an_alias_is_never_a_classified_dispatch`.
- **Route indices cross two vectors.** `match_route` enumerates `engine.policy().routes`; an adapter resolving `RuleReference::Route(index)` for audit attribution reads `RbacPolicyState.routes`, a separate clone. They agree today only because both are clones of the same vector in order. The differential fixtures therefore assert the resolved `permission` and `path_prefix`, not only the outcome and reason — an index-base mismatch is otherwise invisible: right verdict, wrong audit record.

## Rejections the kernel keeps, and why a served request cannot reach them

`EvaluationError` has ten variants. Seven are adapter-controlled or unreachable by construction, as [#422](https://github.com/Greenhat-Security/GreenGateway/issues/422) enumerates. The other three — `ContextTooLarge`, `InvalidPrincipal` and `InvalidHost` — were reachable from production until [#488](https://github.com/Greenhat-Security/GreenGateway/issues/488) moved each limit to where a limit belongs, with a status code of its own:

| Kernel rejection | Trigger | Refused first by | Answer |
| --- | --- | --- | --- |
| `ContextTooLarge` | path over `MAX_REQUEST_PATH_BYTES` (8 KiB, also the setting's ceiling) | `middleware::validate`, before authentication | `414` |
| `ContextTooLarge` | method over 64 bytes | same | `501` |
| `ContextTooLarge` | host over 4 KiB (`Host` field or the target's `:authority`) | same | `431` |
| `ContextTooLarge` | more than 256 roles, a role over 256 bytes, a subject or issuer over 4 KiB | every `SessionValidator`, through `auth::principal::check_principal_shape` (`Principal::check_shape`): JWT, cookie-session introspection and service tokens judge the facts they shape from a credential; the client-certificate validator holds the bound by construction (`MAX_IDENTITY_BYTES <= MAX_PRINCIPAL_SUBJECT_BYTES` is a compile-time assertion, roles are empty, the issuer is a constant) and judges the built principal all the same | `401` |
| `InvalidPrincipal` | an empty subject or an empty role | same | `401` |
| `InvalidHost` | a host that is not a bare host, from either source | `upstream_route::host_header`, read by admission | `400` |
| `ContextTooLarge` | a dispatch fact (route id, route host, route path prefix, upstream origin) over 4 KiB, or an MCP alias identity over 8 KiB | configuration validation at startup: route ids and hosts are bounded below it by their own grammars, and route path prefixes, upstream URLs and `GATEWAY_PUBLIC_URL` (from which the origin and the MCP resource path derive) are refused above `request_bounds::MAX_DISPATCH_FACT_BYTES` | refused configuration |

The kernel keeps its checks: it is pure and states its own work limit rather than trusting that a caller applied one. What changed is that both sides now read the same constants (`request_bounds`, `auth::principal`) and, for the host, the same predicate (`upstream_route::is_bare_host`), and `request_host_without_port` no longer produces anything that predicate refuses. `the_kernel_bounds_are_exactly_the_bounds_admission_and_authentication_enforce` pins each boundary on both sides of the same byte, and `a_request_and_principal_that_pass_admission_and_authentication_cannot_be_refused_by_the_kernel_for_shape` is a property over lengths and host forms: whatever `request_shape_problem` and `check_principal_shape` accept, `evaluate` never answers with one of the three.

The issuer bound is worth a sentence. A principal's issuer is configuration — the provider's normalized `issuer`, or `provider:<name>` — not a claim, so an issuer over 4 KiB is an operator's mistake rather than an attacker's input. Configuration validation refuses it at startup, and the JWT and cookie-session validators judge it by the same predicate at every authentication all the same, so it cannot reach the kernel by either route. Note that the validator's rejection text (`principal claims out of bounds: ...` for a JWT, `cookie-session claims out of bounds: ...` for an introspected session) is the individual validator's verdict; the validator chain every deployment runs (`auth::ChainValidator`) reports the generic `no configured auth provider accepted the credential` to `auth.failure`.

## Evidence

The differential matrices drive both the **frozen original middleware** and the **live `rbac_middleware` adapter** against the kernel. The oracle is the original implementation, never a newly hand-written evaluator or the new adapter alone. That is not stylistic. It caught a semantic the kernel had wrong — a selected virtual upstream with no host-bound route is refused outright — where a hand-written oracle would have encoded the same wrong assumption twice and passed. In the same change a hand-written assertion elsewhere in the suite *was* wrong about the same behaviour.

Two corollaries, both learned the hard way:

- **The oracle includes the guard, not just the extracted function.** Comparing the rate lane against `matching_limiter` directly hid that `policy_rate_limit_request` returns before reaching it for a request with no principal, so the kernel was reporting an override governing traffic production never rate-limits.
- **Compare the installed instance, not a copy.** The middleware oracles read the `CompiledPolicy` the `RbacState` installed. A separately compiled copy of the same policy can agree with the middleware while the installed one diverges, and the comparison would not notice.

Purity is asserted rather than assumed: `pure_evaluation_is_thread_safe_deterministic_bounded_and_redacted_without_a_runtime` evaluates with no async runtime present and checks the trace is bounded and carries no identity values, and `evaluating_a_policy_emits_no_audit_events` drives allow, deny, observe and indeterminate decisions plus a rate selection through a capturing audit sink and requires it to stay empty. A shadow observation is *reported* as `Evaluation::observation` for a caller to emit, never emitted by the kernel.

## Digests

`PolicyDigest::Source` covers the exact accepted source bytes and is available only to the offline compiler, the only caller that holds them. `PolicyDigest::ValidatedPolicy` covers an install path that never did: the live gateway hands over an already-parsed `Policy`, and loading canonicalizes it, so the bytes cannot be reconstructed. It carries frame kind `gg.validated-policy.v1`, deliberately outside ADR-0004's reserved `source`/`semantic` namespace — see `policy-evaluation-kernel.md` for why it is not, and cannot become, JCS.

A result bound to one digest is not reusable under the other, and a context pinned to one is rejected by the other rather than answered.

## Tool lane evidence and cutover limits

**Oracle.** The frozen pre-cutover tool lane from 05c295a: `tools/runtime_legacy_tests.rs` (`legacy_admit`, `legacy_tool_visible_to_context`, `legacy_composite_leaf_enabled`, `legacy_authorize_http_operation`) over `middleware/rbac_legacy_tests.rs` (`legacy_evaluate_tool_authorization`, `legacy_evaluate_tool_http_rule`, `legacy_tool_policy_eligibility`). It is the original implementation, never a hand-written evaluator, and it is absent from serving builds.

**Differential fixtures** (`policy_eval::tools::tests`). `generated_policies_are_decided_alike_by_the_frozen_consumers_and_the_live_runtime` is a proptest with a fixed seed (`422_002`, 128 cases) over generated tool entries, tool and path rules, enforcement mode and default. `the_frozen_consumers_and_the_live_runtime_agree_across_the_named_matrix` adds the cases the corpus reaches only by chance: a rule before and after the deciding one, disabled rules in between (so source ordinals and ids must be attributed exactly), every first-tool action under both modes and defaults, and each identity constraint alone. Both ask the frozen consumers and the live runtime every question over seven identities (anonymous, bearer, cookie, service token, client certificate, another issuer, 256 roles) and four names, and compare admission errors and admitted limits, whether work ran, a full served `execute_with_context` on a third runtime, visibility, composite enablement, inventory eligibility, rendered-HTTP decisions over three methods and four paths, and the audit each side emitted, field by field. Since the legacy retirement they also ask the enum-source precheck of the same policy, once per source: each of the four names, a name longer than any policy key and a source that names a path only, over five rendered requests (a percent-encoded segment, the root, and one with a fixed query that neither side may audit). The precheck's oracle is `legacy_authorize_source_request`, below. `live_adapters_translate_the_kernel_answer_for_invocation_visibility_inventory_and_composite` and `rendered_http_matches_live_direct_rules_unknown_dispatch_and_audit_attribution` check each adapter's translation of the installed kernel's answer; they are not parity evidence, because the live consumers are now the kernel.

The runtime Actor projection accepts three auth modes and drops a client-certificate identity, whereas inventory retains it. The fixtures pin both outcomes on both sides.

**Refusals.** Where the evaluator refuses to answer, the adapter blocks, in shadow mode too: `tool_name_out_of_bounds` (a name over `MAX_TOOL_NAME_BYTES`, refused before the evaluator is asked), `policy_evaluation_incomplete` and `policy_evaluation_error`. A refused invocation is `tool.invoke.rejected` and a refused rendered request `authz.denied`, each with the refusal as `reason` and `matched_rule_id: null`; an inventory preview is ineligible with that reason, and visibility and composite enablement answer no. MCP answers them as a `policy_denied` error carrying the reason, the playground as `403 policy_denied`, and executor observations as `403` with the refusal's reason. They are the only answers that differ from the frozen consumers, always toward a block: an over-long name (old: unknown tool), a principal the evaluator refuses for shape, and rendered facts it refuses. `refusals_block_with_stable_reasons_where_the_frozen_consumers_answered` pins each. The adapter also admits only on the evaluator's own allow effect: an `Allowed` invocation or a no-rule rendered answer with any other effect is refused as `policy_evaluation_error`, so a later kernel change fails closed.

**Bounds.** Policy validation refuses a `tools` key or a rule `tool_name` over 4096 bytes (`request_bounds::MAX_TOOL_NAME_BYTES`), without echoing it, so no policy names a tool the evaluator cannot be asked about. A stored or published policy carrying a longer name no longer loads, which fails closed. Discovered MCP and OpenAPI tool names are bounded at 128 characters; a `TOOLS_FILE` name only by that file's size cap, so a call to such a local tool is the one served path to `tool_name_out_of_bounds`. Rendering holds a rendered request to the evaluator's own bounds before its rule is asked: a method over 64 bytes, and any path `validate_rendered_http_path` refuses (over 8 KiB, relative, an empty or dot segment, a malformed escape), fail as configuration errors. That refuses some requests the gateway used to send, such as an empty path argument. `the_tool_lane_bounds_are_exactly_the_bounds_policy_validation_and_the_adapter_enforce` pins both sides of each bound.

Tool context version 1 and semantics `gg-tool-policy-v1` are independent of the HTTP context version. Every result binds the operation and all supplied policy facts. Missing facts fail closed; malformed facts return errors. Inventory has no anonymous live contract, so an anonymous inventory context is inconsistent. Composite enablement can complete with a missing identity because it does not use identity. Trace reuse (`canonical_trace_bytes`, `reusable_for`) stays offline, and the live adapters still compute each answer's context binding.

### Which snapshot judges a tool decision

Every live tool-lane policy read goes through `effective_policy()`, and registry and Connection lookups go through their own pinned accessors.

- **Each invocation is pinned, in both modes.** The tool runtime runs every invocation (`execute_with_context`, and `execute_result_with_context_and_outcome`, which the executor, MCP calls, MCP task rejection and the admin playground all reach) inside `RbacState::with_request_policy_snapshot`. Admission, the queue wait, the playground's execution precondition, the rendered-HTTP rule and composite leaf enablement are then judged by one snapshot. In cluster mode it is the bundle the revision gate admitted the request under; in standalone mode it is the live lane, read once when the invocation starts. A revision installed while the call is queued or running judges the next invocation, never part of this one, so admission from one snapshot cannot pair with another's rules and allow what neither allows. `a_revision_installed_after_admission_never_judges_the_rest_of_the_invocation` installs a revision from inside the work, between admission and the rendered request; `a_revision_installed_while_an_invocation_is_queued_never_judges_its_rendered_request` installs one while the call waits for a permit.
- **Cluster mode also pins the request.** `rbac_middleware` pins the admitted bundle (policy, tools, Connections) as task-locals of the request's task and hands the same pins to the request as a `RequestPins` extension. Task-locals do not cross `tokio::spawn`. MCP `tools/list`, `tools/call` and task rejection run in tasks rmcp spawns, so `McpServer` re-enters the pins with `with_request_pins` before its first registry or policy read. `mcp_requests_are_judged_by_the_admitted_revision_not_one_installed_in_flight` and `tool_http_operation_reads_the_pinned_policy_not_the_live_lane` hold that.
- **The admin playground adds refuse-only live checks.** Its precondition judges the execute permission and the eligibility behind its etag inside `with_request_policy_snapshot` (`request_snapshot_grants_permission`, `ToolEligibilitySnapshot`), which inside the runtime is the invocation's snapshot. It also re-reads the management lane live (`principal_has_permission`), and its last rendered-HTTP check, after the precondition, reads the live lane (`authorize_http_operation_live`). Both live reads follow a pinned decision that already allowed the call, so each can only refuse: a revocation or a deny published while the call was queued or its precondition ran still stops it. `a_pinned_request_snapshot_answers_permission_and_eligibility_while_the_management_lane_reads_live`, `the_live_rendered_http_check_refuses_inside_a_pinned_invocation` and `pinned_playground_invocation_still_refuses_a_deny_published_during_its_precondition` hold this. Composite leaves and MCP proxy tools have no such final live check; they are judged by the pinned snapshot.
- **Inventory reads one snapshot per listing.** `CapabilityInventory` takes one `ToolEligibilitySnapshot` per build, so a listing cannot straddle an install between two tools. `a_tool_eligibility_snapshot_taken_before_an_install_answers_every_tool_from_it` holds it.
- **Not pinned.** In standalone mode MCP `tools/list` asks each tool's visibility separately of the live lane, so one listing can straddle an install. Each tool's answer still comes from one snapshot, and a listing grants nothing: every call is judged afresh. The enum-source precheck reads the live lane's installed snapshot once and asks its compiled evaluator both the enable bit and the deny rules (`the_enum_source_precheck_judges_enablement_and_denies_by_one_snapshot`); the refresher runs outside any request, and an admin overlay install resolves its sources against the live policy its read-modify-write builds on.

Registry existence and listing metadata, composite grant validity, the enum-source refresh after its precheck, the non-RBAC fallback's entries and default, transport and mutable execution state are outside this contract. The named operation and `not_evaluated` trace fields make those limits explicit. A tool's outbound request is decided by the static egress lane below, through the same `EgressClient` every other caller uses.

## Rate lane evidence and cutover limits

**Oracle.** The frozen pre-cutover policy rate stage from 5fdf2b6: `middleware/rate_limit_legacy_tests.rs` (`legacy_policy_rate_limit_request`, the `legacy_matching_limiter` selector it consults, and `legacy_selected_override_limit` for comparing the kernel directly). It runs over the same override stores the live stage builds, so the two are compared bucket for bucket, and it is absent from serving builds.

**Differential fixtures** (`middleware::rate_limit::differential`). `generated_policies_select_and_charge_alike_in_the_frozen_and_live_stages` is a proptest with a fixed seed (`422_003`, 128 cases) over generated overrides (each principal constraint, methods including a wildcard, lower-case and extension methods, eight path patterns, burst and rate), enforcement mode and default. `the_frozen_and_live_stages_agree_across_the_named_matrix` adds the cases the corpus reaches only by chance: no overrides, an unconstrained override, first match among identical predicates, rules before and after the deciding one, each principal constraint alone, wildcard and lower-case methods, a one-segment wildcard, captures, the root alone and everything below it, each under both modes and both defaults. Both drive the frozen and the live middleware with seven identities (anonymous, bearer, cookie, service token, client certificate, a subject shared with a second issuer, 256 roles), four methods and seven paths, twice each, and compare every request: the selection (rule fingerprint and declared limit), the status, the response's policy decision, every override bucket's remaining tokens for the caller, downstream work, and the audit each side emitted. `rate_lane_selection_matches_the_frozen_selector` (`policy_eval::tests`) compares the kernel against the frozen selector directly.

**Refusals.** Where the stage cannot select a lane it refuses the request; it never lets one pass unmetered. The reasons are `unsafe_path` for a path `is_unsafe_request_path` refuses (the authorization stage's own guard, applied before the evaluator is asked), `policy_evaluation_error` when the evaluator refuses the question, and `policy_evaluation_incomplete` when it lacks a fact. The answer is the authorization stage's answer for a request it does not evaluate (`rbac::refuse_unevaluated`): `403 {"error":"forbidden"}`, `authz.denied` with the reason and no rule, a denied policy decision, no bucket charged and no downstream work. Evaluator refusals also log one warning with bounded enums.

These are the only answers that differ from the frozen stage, and they always refuse. Two are reachable, and each is a request the authorization stage refused with the same answer anyway: a path with a percent-encoding, an empty or dot segment or a backslash (`unsafe_path`), and an asterisk-form target such as `OPTIONS *` (`policy_evaluation_error`). The frozen stage selected an override on the raw path, charged its bucket and passed the request on to be refused, answering `429` instead once the bucket was spent. The live stage refuses it at once, so these requests no longer spend an override's budget. `a_refused_path_is_answered_and_audited_as_the_authorization_stage_answered_it` puts the authorization stage behind both and requires the same status, decision and audit record. One detail differs in cluster mode: for an asterisk-form target the authorization stage's record carried the served `security_revision`, and the rate stage's carries none, because the revision gate has not run. Every other refusal is unreachable from a served request: request admission and authentication bound the method, path and principal first (#488), and the adapter supplies the context version and snapshot itself. `a_selection_that_names_no_bucket_of_its_rule_is_refused` pins the adapter's own check that the bucket it charges was built for the rule the evaluator read.

**Which snapshot selects.** The rate stage runs after authentication and before the authorization stage and its cluster revision gate (`routing::apply_middleware`). It selects with the `RbacPolicyState` the RBAC lane installed, the same `Arc`, handed over by every install path (attaching the stage, `replace_policy`, `install_revision_snapshot_locked`), and builds its buckets from the rule vector that instance's evaluator indexes (`CompiledPolicy::rate_limit_rules`). The selector and its buckets are one value, swapped together, so a request racing an install cannot take an index from one policy and charge the bucket at that position in the next. `every_install_hands_the_rate_stage_the_installed_snapshot_with_its_own_buckets` moves an override to another index across a reload and checks a duplicate revision install resets nothing. The question is bound to the request's pinned snapshot when there is one. None exists at this stage today, so it is the installed snapshot; a request pinned to another is refused by the evaluator (`SnapshotMismatch`) rather than charged against buckets built for a different policy (`a_request_pinned_to_another_snapshot_is_refused_rather_than_charged_against_this_one`).

In cluster mode the selection is therefore made against the replica's most recently installed revision, before the gate admits the request at the authority's current one, and the authorization decision that follows can come from a newer bundle. That is not one decision built from two snapshots: the rate stage only adds a constraint and never grants, so the pair cannot allow what neither allows. Buckets reset on every install, as before. Before this change no revision install reached the rate stage at all: `install_revision_snapshot_locked` compared the snapshot `rcu` returns, which is the one it replaced, with its candidate, so cluster replicas kept the overrides they booted with until restart. It now hands the stage every revision it installs, and only those, which the postgres leg of the install test pins.

**Not changed.** The global lanes, bucket storage and eviction, the rate-limit keys, the shared store and its rule-fingerprint keys, the probe exemption, and `503` with no upstream attempt when the authority cannot be reached. Shadow enforcement mode does not soften rate limits, on either side. A request with no principal reaches no override, on either side.

## Static egress lane evidence and cutover limits

**Oracle.** The frozen pre-cutover checks from 198ab93: `egress/static_legacy_tests.rs` (`legacy_checked_destination`, `legacy_rebind_checked_destination`, `legacy_revalidated_destination`, and the `legacy_checked_url`, `legacy_checked_host`, `legacy_checked_policy_port`, `legacy_resolve_and_check` and `legacy_checked_socket_addr` steps they composed). It reads the configuration and resolver of the same client the live adapter compiled its evaluator from. The predicates those checks called are shared with the live lane, which still calls them -- `host_glob_matches`, `is_non_global_ip`, `ip_matches_policy_cidr` and `checked_port` -- so what the oracle freezes is the composition: which check runs, in which order, and with what answer. The predicates keep their own tests, and `host_glob_matches` its mutation target.

**Differential fixtures** (`egress::static_differential_tests`). `generated_controls_and_answers_are_decided_alike_by_the_frozen_and_live_checks` is a proptest with a fixed seed (`422_004`, 128 cases) over generated controls (exact hosts including a bracketed IPv6 literal and an upper-case entry built by hand, host patterns, port lists, the non-global switch, a NAT64 prefix, and policy CIDRs of both families), one to four URLs per case (five schemes, three userinfo forms, eleven hosts, five ports, a query and a fragment, plus irregular URLs with no host, no parse or an out-of-range port) and an answer set (fourteen sets, on the asked port or another one, or a resolver failure). `the_frozen_and_live_checks_agree_across_the_named_matrix` adds each refusal on its own, pairs of refusals that must report the earlier check, and the admissions the corpus reaches only by chance, and requires each case to end in the category it names. Both compare, on one client, the checked destination or the error's safe category and full text, and every name each side asked the resolver for. Every destination that passes is then rebound and revalidated by both, against every URL of its case and with six substituted pinned addresses, on the installed client and on one under other controls, and neither side may resolve anything doing so.

**Zero DNS on a refusal.** The live adapter asks the evaluator first with `ResolutionFact::Missing`. A destination the static checks refuse is refused whatever the facts are, so it is answered `Deny` there and the adapter never reaches its resolver. Only `Indeterminate(missing_resolution_fact)` sends it to resolve, after which it asks again with the answers. `a_statically_refused_destination_never_reaches_the_resolver_on_any_entry_point` drives every resolving entry point (`checked_destination`, `request`, `request_with_headers`, `stream_request_with_body`, `stream_request_with_body_for_sse`) with each static refusal over a resolver that panics when called, and checks that the same controls with an answering resolver resolve an admitted destination exactly once. `rebinding_and_revalidation_never_reach_the_resolver_even_when_they_admit` holds the same for the paths that never resolve. `an_upstream_the_static_egress_checks_refuse_is_never_resolved_or_contacted` holds it end to end: a proxied request to an upstream whose port the policy `egress` section does not list is answered `502` with no resolver call and nothing reaching the upstream, while the same policy listing the upstream's port resolves it and forwards the request. In the kernel, `a_refused_destination_is_decided_without_resolution_facts` states that a refusal is complete without facts and unchanged by any.

**Refusals.** Where the evaluator refuses the question, or gives an answer the question cannot have (an allow to the static question, an indeterminate answer to the address question, an ordinal outside the supplied answers), the adapter refuses the destination as `invalid_policy`, with one warning carrying the bounded evaluator error (`every_answer_the_evaluator_cannot_give_fails_closed`). Every input that could cause either is the adapter's own: the context version, the snapshot it compiled, and an answer set it supplied. The evaluator imposes no bound of its own on a URL or an answer set, because the pre-cutover checks had none, and a bound found at decision time would refuse destinations the gateway reaches today. No answer differs from the frozen checks: every error, warning and category is the one they produced, so retry and passive-health classification, proxy answers and audit categories read the same `EgressError`.

**Which controls decide.** Each `EgressClient` compiles its `CompiledEgressPolicy` from its own configuration when it is built, beside the policy and configuration generations that bind its checked destinations, and decides every destination by it. A reconfigured or derived client (`reconfigured`, `with_tls_material`, `with_response_cap`) compiles its own. The policy `egress` section is still a startup snapshot until the configuration is rebuilt, as before.

**Not changed.** The DNS lookup and the injected resolver, redirect refusal, the exact-pinned client cache and its generation checks, TLS and mTLS, the gRPC transport, request and response bounds, and the loopback health probe. This lane's `not_evaluated` names authentication, the HTTP policy, tools, rate selection, mutable capacity, DNS, redirects, TLS, transport, request and response bounds, upstream execution, live revision freshness and gateway build identity.

## Analysis consumer evidence and cutover limits

The admin consumers that judged policy beside the evaluator now ask it, or, for hit counts, read the live adapter's own attribution. None of them is a simulation or a replay: the preview is still a historical match counter over one candidate rule, coverage is still a synthetic question about representative requests, and nothing here claims Policy Studio simulation or replay coverage, which #243 owns.

**Oracle.** The consumers as they stood at 6fc83e9: `analysis_legacy_tests.rs` (`legacy_preview_matches`, the preview's per-observation match with its actor projection, and `legacy_endpoint_coverage_scope` with the host-route check and the representative helpers it called) and `discovery/suggestions_legacy_tests.rs` (`legacy_policy_has_covering_action` with `legacy_host_route_covers_principal` and its helpers).

**Differential fixtures** (`analysis_differential`, `discovery::suggestions::coverage_differential`). Three proptests with a fixed seed (`422_005`, 256 cases each). `generated_rules_and_observations_are_counted_alike_by_the_frozen_and_live_previews` generates a candidate rule (five method sets, six path patterns, every principal constraint, four dispatch bindings, three actions, enabled or not) and an observation (five methods including an unparsable one, nine paths including three the evaluator refuses, an actor in three supported modes, an unknown mode or none, with and without roles and issuer, and classified, unclassified or unmarked routing with seven dispatch shapes including route facts without an origin). The live answer must equal the frozen one, except that an observation whose facts are refused is `malformed_observation`, and an unevaluated one is `missing_principal_fact` or `missing_dispatch_fact` only when the frozen preview said no match, the actor's mode or the classification is in fact missing, and the rule is enabled and reads that fact. `generated_policies_report_the_same_endpoint_coverage_as_the_frozen_inventory` requires the same scope for generated rules, host-bound and unbound routes, roles with issuer and authentication-mode restrictions (other than to client certificates, the one case that differs, which is named below), three methods, six templates and six routing contexts. `generated_candidates_are_covered_alike_by_the_frozen_check_and_the_evaluator` requires the same coverage off a host-routed dispatch, and on one allows only the difference described below, checking its cause.

**Differences, each toward the live evaluator's answer, each pinned by name.**

- The preview reports an observation it cannot judge instead of counting it either way: a path, method, principal or dispatch the evaluator refuses (the frozen preview matched a percent-encoded or dot-segment path against a pattern, though no served request reaches the policy stage with one), an actor whose authentication mode no principal carries, against a rule that reads the principal, and an unclassified observation against a dispatch-bound rule (the frozen preview counted both as non-matches). Such an observation is counted in `unevaluated_reasons` and sets `complete: false` (`observations_the_frozen_preview_counted_without_the_facts_are_now_reported_unevaluated`, `policy_rule_preview_contextless_binding_excludes_unclassified_history`).
- The preview judges a client-certificate actor with its identity, as live evaluation does; the frozen preview judged it anonymous (`a_client_certificate_actor_is_judged_with_its_identity_rather_than_as_anonymous`).
- Endpoint coverage with no recorded routing context is `unknown`: the evaluator is missing the dispatch fact, where the frozen inventory judged the endpoint under an unknown dispatch. So is a representative request the evaluator refuses, or route facts recorded without an origin (`an_endpoint_with_no_recorded_routing_context_has_unknown_coverage`, `a_representative_request_the_evaluator_refuses_has_unknown_coverage`, `endpoint_rule_coverage_without_rules_is_none`).
- On a host-routed context, a role's representative caller decided by a direct deny is principal-scoped coverage. The frozen inventory met that deny only through the deny's own representative caller, which for a rule restricted to client certificates was a bearer caller that never met it (`host_routed_coverage_asks_whether_a_role_caller_is_authorized_or_decided`).
- A host-routed suggestion candidate is covered only when its representative caller activates a role that grants the host-bound route's permission and no direct deny decides it first; the frozen check required only that one of its roles grant the permission (`a_host_routed_candidate_is_covered_only_by_a_role_it_can_activate`, `a_host_routed_candidate_a_direct_deny_decides_is_not_covered_by_an_allow`).
- A signal candidate bound to a pooled route is judged as that route's traffic; the frozen check judged it as contextless traffic, so a route-bound rule did not cover it and a contextless-only rule did (`a_signal_candidate_is_judged_as_traffic_dispatched_the_way_it_would_be_bound`).
- A suggestion candidate the evaluator cannot judge is proposed, as an uncovered one is, and counted in the run's `coverage_unevaluated`; the frozen check matched it as it could (`a_candidate_the_evaluator_cannot_judge_is_proposed_and_counted`).

**Facts the consumers do not have, and how each is marked.** Discovery does not keep a route id, so endpoint coverage and baseline candidates supply one only for a pooled route, whose `pool:` origin names it; a rule bound to the derived id of another route is not credited, which under-reports coverage. Signal candidates do not keep a legacy route's id either. The preview reads no request host, which no direct rule reads. Representative principals are synthetic: a rule's representative caller holds its first principal id, first issuer and all its roles, with a service-token, then session-cookie, else bearer mode, so a rule restricted to client certificates alone is not credited through its own caller. No consumer reads an MCP alias identity: the preview judges an observation by its recorded path, and coverage by the endpoint template.

**Errors.** An evaluator error that is not a refusal of the supplied facts is the consumer's own mistake (a context version or snapshot it built wrongly). The preview fails with `500` rather than count around it, as ADR-0004 requires of an analysis run. Endpoint coverage reports `unknown` and logs a warning with the bounded error, rather than fail a whole traffic listing; nothing reports it as coverage.

**Not changed.** The preview's SQL pre-filter, scan ceiling, sample strategy and permissions; the hit-count endpoint's response, keys and `503` without an audit query store; coverage scopes and the meaning of `covered_by_rule`; and how suggestions are planned, bound, stored and accepted. The tool-name coverage check kept its answers in this slice and moved onto the evaluator with the [legacy retirement](#legacy-retirement).

## Legacy retirement

The last consumers that matched policy rules beside the evaluator now ask it, and the non-RBAC tool fallback no longer carries rules at all. `CompiledPolicy` holds the only serving `RuleMatcher`, one per compiled snapshot. `the_evaluator_holds_the_only_serving_rule_matcher` scans the gateway's sources and fails on any other construction outside test code: a test file, an in-file `#[cfg(test)] mod tests` block, or a statement gated by its own `#[cfg(test)]`. The matcher's contextless conveniences (`RuleMatcher::evaluate`, `RuleMatcher::evaluate_denies`, `RuleDispatchContext::classified`) are compiled only into tests. `Rule::matches`, a single-rule check no serving code calls, keeps its `allow(dead_code)`: making its helper test-only would add a top-level `cfg(test)` item to `rbac/matcher.rs`, which the pure-path benchmark's source projection refuses.

**What moved.**

- **The enum-source precheck.** It copied the live policy (`current_policy()`) and built a `RuleMatcher` from its rules on every call. It now reads the live lane's installed snapshot once (`RbacState::live_policy_snapshot`) and asks that snapshot's compiled instance, the one live requests are judged by, `CompiledPolicy::evaluate_source_request`: the named tool's enable bit, then the direct deny rules alone, as an anonymous contextless `GET` of the rendered path without its query. The order, the answers and the audit are those of the frozen precheck; a denial names its rule by the snapshot's own `rule_ids`. The evaluator holds the path to the rendered-HTTP bounds (`validate_rendered_http_path`). A compiled source plan's path has already passed `normalize_origin_relative_path`, which is stricter (1 KiB, no dot or encoded-separator segment), so no compiled source is refused for its path. A tool name longer than any policy key (4096 bytes) names no entry, so the adapter refuses it as `tool_disabled` without asking, which is how the frozen precheck answered it. Where the evaluator refuses anyway, or names a rule the snapshot does not have, the source is refused before any I/O with the existing failure reason `http_rule_denied`, so refresh state, API responses and the admin UI read a value they already know, and the refusal is audited as `authz.denied` with reason `policy_evaluation_error` and no rule, with one warning carrying the bounded error (`an_enum_source_the_evaluator_refuses_is_refused_and_audited_without_a_rule`). Shadow enforcement does not soften it, as it softened no deny rule before.
- **The tool-name coverage check of rule suggestions.** `CompiledPolicy::match_tool_rules` answers the question the check asks: the first enabled tool-name rule whose own predicates accept the representative principal, without the tool lane's admission, which coverage does not ask about. Its index is resolved on the same instance. A candidate it cannot judge is proposed and counted in `coverage_unevaluated`, as an HTTP candidate is.
- **The non-RBAC tool fallback's rules.** A `ToolRuntime` without an `RbacState` exists only when no policy is configured, and bootstrap never gave its configuration any rules: `ToolRuntimeConfig::from_env_defaults` carries none, and the policy-derived configuration is used only beside the policy's `RbacState`. `ToolRuntimeConfig` no longer has a `rules` field, so a rule cannot be handed to a runtime that would match it outside the evaluator, nor set where it would silently not be enforced. Tests that set tool-name or rendered-HTTP rules on such a runtime now build it with the policy's `RbacState`, as production does.

**Oracles kept.** Each frozen implementation is compiled only into tests and is the oracle of the differential tests named in its lane's section.
