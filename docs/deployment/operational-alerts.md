# Operational alerts and first response

The [Prometheus rules](alerts/greengateway.rules.yml) turn existing gateway signals
into actionable alerts. They cover lifecycle stalls, audit loss and backpressure,
requests refused because their audit records could not commit, PostgreSQL pool
pressure, selected cluster health conditions, and cluster mode's durable
authority-change evidence: changes refused for their evidence, journal capacity and
delivery. This advances
the existing-signal inventory and rule-validation work in [issue #440](https://github.com/Greenhat-Security/GreenGateway/issues/440);
the signal gaps below remain open. It does not prove notification delivery,
incident response, or recovery time.

## Deploy and validate

1. Copy [the scrape example](alerts/prometheus.example.yml), [the expected-target
   inventory](alerts/targets.example.rules.yml), and the rule file into your
   monitoring configuration. Scrape every gateway replica directly. A load-balanced
   `/metrics` address can alternate processes and hide a failed replica.
2. Keep `job="greengateway"`. Assign `deployment_mode="standalone"` or `"cluster"`
   explicitly from reviewed deployment configuration. This is a monitoring label,
   not a metric emitted by the gateway. Assign each target a unique, bounded,
   opaque `instance` value such as `gateway-1`, replacing Prometheus's default
   address label through target relabeling. Do not use a hostname, URL, deployment
   secret, principal, tool name, or per-boot UUID as an alert label.
3. Declare each expected target separately using
   `greengateway_monitoring:target_expected` with value `1` and the same job,
   instance and mode. Invalid modes, inventory values other than `1`, and
   discovered targets without matching inventory produce a configuration alert.
   The inventory must remain when a target disappears from service discovery.
   Update it only for an intentional addition, replacement or decommission;
   generating it from currently healthy targets defeats missing-target detection.
4. Protect the scrape network and Prometheus configuration. `/metrics` and the
   probes are on the data listener, including when `ADMIN_LISTEN_ADDR` is set.
   Set the actual listener address, TLS and credentials through your deployment's
   approved monitoring configuration; the example supplies no credentials.
5. Probe `/readyz` separately through the supervisor/load balancer and monitor its
   failure externally. A successful `/metrics` scrape proves neither readiness nor
   successful authority access. Keep probes running: schema compatibility is
   refreshed by startup validation and readiness ledger reads, not by scraping.
6. Map `owner="gateway-operations"` and the rules' `severity` labels to real
   on-call routes in your Alertmanager. Critical alerts page; warning alerts
   request timely investigation. The platform team is the default responder;
   escalate audit loss to security and release verification failures to the
   release owner. The example intentionally contains no notification receiver or
   personal contact details. Independently monitor Prometheus rule evaluation,
   Alertmanager delivery, and the monitoring service itself.

From the repository root, using the Python version in `build-tools.json`:

```sh
python -m pip install PyYAML==6.0.3
python scripts/alert_rules.py install
python scripts/alert_rules.py check
```

The wrapper uses the pinned, checksum-verified `promtool` to check rule syntax,
the example configuration, and the synthetic rule fixtures. Deployment-specific
copies must receive the same checks after every edit. Rule tests establish
expression behavior; they do not establish that a real notification reached its
responder.

## Signal contract

These names come from [the metric registry](../../gateway/src/metrics.rs) and
their emitters. `up` is generated by Prometheus. Unless noted, gateway gauges
below have no application labels; scrape labels identify the replica.

| Existing signal | Emission and meaning | Limit |
| --- | --- | --- |
| `greengateway_gateway_ready`, `greengateway_gateway_draining` | [Lifecycle](../../gateway/src/lifecycle.rs), at construction, transitions and scrape. `(0,0)` means starting, `(1,0)` lifecycle ready, `(0,1)` draining. | Lifecycle ready does **not** mean the authority, security gate or required upstream is ready. |
| `greengateway_audit_queue_depth`, `greengateway_audit_queue_capacity`, `greengateway_audit_queue_oldest_age_seconds` | [Audit writer](../../gateway/src/audit/mod.rs), sampled on scrape. Includes queued work and asynchronous sink backlog; oldest age also captures an in-flight delivery stuck with an empty channel. | Queue capacity depends on the configured sink. Use the exported capacity, not a hard-coded event count. |
| `audit_events_dropped_total{reason=...}` | Audit admission and sink delivery failures; `reason` is a fixed classification. Every `reason` is exported at `0` from startup (`postgres` only in cluster mode). | A loss counter, not a recoverable backlog. Process restarts limit what a scrape sees. |
| `greengateway_audit_flush_total{outcome="failure"}` | Audit sink flush failures, including terminal flush. Exported at `0` from startup. | Failure requires investigation; the rule does not identify which records remain durable. A process may exit before its final counter is scraped. |
| `greengateway_audit_durability_refusals_total{reason}` | [Audit durability](../../gateway/src/audit/durable.rs), on the replica that refused: a request answered `503 audit_unavailable` under `AUDIT_DURABILITY=required` (the default) because its authentication or authorization record could not commit to the audit store of record. `reason` is `admission`, `store` or `timeout`. Every `reason` is exported at `0` from startup, in both modes. | `/readyz` stays `200` while it climbs. It counts refused requests, not lost records: lost records are on `audit_events_dropped_total`, and a `timeout` record can still commit after its request was refused. Under `best_effort` it stays at `0`. |
| `greengateway_database_pool_size`, `greengateway_database_pool_available`, `greengateway_database_pool_waiting` | [PostgreSQL pool](../../gateway/src/storage/postgres.rs), sampled on scrape when a database pool exists. | Cluster mode only; momentary snapshots can miss short exhaustion bursts. |
| `greengateway_database_pool_timeouts_total` | Classified pool checkout timeouts since boot. | Cluster mode only; exported at `0` from startup. |
| `greengateway_schema_compatible` | [Migration validation](../../gateway/src/storage/migrations.rs) and [readiness](../../gateway/src/ha_status.rs): `1` means a compatible, integrity-checked ledger, `0` means incompatible. | A stopped readiness probe leaves the last verdict exported. A startup refusal may happen before a metrics listener exists. |
| `greengateway_cluster_heartbeat_age_seconds`, `greengateway_cluster_config_mismatch` | [Membership](../../gateway/src/cluster_membership.rs), at registration and after heartbeat attempts. Age is seconds since the last successful heartbeat; mismatch is `1` until sticky agreement. | A stopped task can leave a frozen value while metrics scraping succeeds. Drain intentionally stops background work. |
| `greengateway_security_revision_lag` | [Security reconciler](../../gateway/src/security_cluster.rs), after background passes. Difference between observed and compiled watermarks, bounded below by zero. | Optional runtime; neither zero nor nonzero lag proves readiness. Failed counter reads can leave equal watermarks; frequent legitimate commits can sustain lag while admissions succeed. |
| `greengateway_authority_event_capacity_refusals_total`, `greengateway_authority_event_evidence_failures_total` | [Journal append](../../gateway/src/storage/postgres_authority_events.rs) and each evidence producer, on the replica that refused the change. A Connection delete, service-token rotate or revoke, JWT revoke, or cluster admin session grant or withdrawal whose evidence row or journal entry cannot commit rolls back whole and is refused: the first counter counts a full journal (which refuses an admin session grant but never a withdrawal), the second any other refused or failed evidence statement, an admin session's expiry prune included. The second also counts a policy or tools document commit, or a managed MCP or OpenAPI catalog publication, refused because its migration 23 evidence row could not be inserted. | Cluster mode only; both exported at `0` from startup. A failure of the transaction's own `COMMIT` is the mutation's failure and is counted by neither. Which producer failed is not a label; the refusing replica's log names the operation. Policy, tools and catalog evidence is not journaled, so a full journal never refuses those changes. |
| `greengateway_authority_event_journal_retained`, `_capacity`, `_oldest_undelivered_age_seconds` | [Journal statistics](../../gateway/src/authority_events/dispatcher.rs), published by the maintenance leader after every successful retention step and by the dispatcher's leader after every step. | One shared table, so a reading says nothing about the replica exporting it, and a former leader keeps exporting its last reading. Without `AUTHORITY_EVENT_SINK` every retained event counts as undelivered. |
| `greengateway_cluster_maintenance_leader`, `greengateway_leader_task_last_success_age_seconds{task="authority_event_retention"}` | [Maintenance singleton](../../gateway/src/cluster_maintenance.rs): `1` on the replica holding the maintenance lease and `0` after its term; on that leader, how long ago the retention job last succeeded according to the fenced ledger. | Leader-only, and a job that never succeeded has no age series. They say which journal reading is current, not whether the journal is healthy. |
| `greengateway_authority_event_delivery_failures_total{kind}`, `greengateway_cluster_lease_age_seconds{scope="authority_event_dispatcher"}` | [Dispatcher](../../gateway/src/authority_events/dispatcher.rs): failed steps by a fixed `kind`, and how long this replica has held the dispatcher lease (`0` after its term). Only a replica with `AUTHORITY_EVENT_SINK` set ever creates either series. | Lazy; their presence is how the rules tell a configured sink from none. `kind="fenced"` is a leadership handover, not a failed delivery. |
| `up{job="greengateway"}`, `greengateway_monitoring:target_expected` | Scrape success and separately maintained target inventory. | Scrape success is transport evidence. Inventory is operator intent, not application telemetry. |

Every counter a single-event rule reads (audit loss, audit flush failure, audit
durability refusal, pool timeout and both authority refusals) is exported at `0`
as soon as the metrics
recorder is installed, with every label value the rule can match. A counter
series that first appeared at `1` would have no earlier sample, and
`increase(...[5m])` cannot see a change without one: the first event after a
process start, often the only one, would never page. Other counters, such as
the dispatcher's failure series, are still created on their first event, and
an absent failure counter is not itself a failure. `increase(...[5m])` also
needs enough samples to observe a change: an event before the first scrape, a
short-lived process or a failure during shutdown can escape a counter-based
rule. Use retained, access-controlled
logs and durable audit reconciliation alongside these alerts; do not interpret
silence as proof that no event was lost.

Leader-only metrics such as `greengateway_cluster_members_live`,
`greengateway_leader_task_last_success_age_seconds` and discovery projector gauges
may be absent or retain their previous value after leadership changes. They are
not mandatory signals in this starter pack. Fixed metric names alone cannot
prove a background producer is still advancing its observations. The
authority-event journal gauges are the one leader-published family the pack
depends on, so it reads them only from the current maintenance leader and
reports their absence or staleness as `GreenGatewayAuthorityEventJournalUnobserved`
(see the authority-event notes under [Alert policy](#alert-policy)).

## Alert policy

Thresholds are starting assumptions, not product SLOs. The examples assume a
30-second scrape and evaluation interval. Review thresholds against observed
traffic, startup and shutdown budgets, and audit retention needs. Change the
checked-in expressions and their fixtures together; there is no gateway
environment variable that changes a Prometheus threshold.

| Alert | Severity | Default condition and hold | First response |
| --- | --- | --- | --- |
| `GreenGatewayMetricsTargetDown` | critical | Failed scrape or an expected target without a successful scrape, 2 minutes | [Monitoring](#metrics-availability): confirm process, network and target inventory. |
| `GreenGatewayMetricsJobMissing` | critical | No `up` series for the gateway job, 2 minutes | [Monitoring](#metrics-availability): restore the scrape job; this is not evidence that every gateway stopped. |
| `GreenGatewayExpectedTargetsMissing` | warning | No declared expected-target inventory, 2 minutes | [Monitoring](#metrics-availability): restore reviewed target inventory. |
| `GreenGatewayMonitoringConfigurationInvalid` | warning | Invalid mode or inventory value, or a discovered target has no matching inventory entry, for 2 minutes | [Monitoring](#metrics-availability): reconcile labels and inventory; cluster alerts depend on them. |
| `GreenGatewayMetricsMissing` | critical | Successful scrape lacks a required lifecycle or audit gauge, 2 minutes | [Monitoring](#metrics-availability): inspect the exporter/version and relabel filters. |
| `GreenGatewayStartupStalled` | warning | Both lifecycle gauges zero for 10 minutes | [Lifecycle](#lifecycle-stalls): inspect startup configuration and dependencies. |
| `GreenGatewayDrainStalled` | warning | Draining remains set for 10 minutes | [Lifecycle](#lifecycle-stalls): inspect in-flight work and shutdown evidence. |
| `GreenGatewayAuditLoss` | critical | Observed drop-counter increase over 5 minutes, held for 2 minutes | [Audit](#audit-delivery): page the audit/security owner and preserve the loss window. |
| `GreenGatewayAuditBacklog` | warning | On a lifecycle-ready replica, depth exceeds 80% of capacity or oldest age exceeds 30 seconds, for 5 minutes | [Audit](#audit-delivery): restore sink progress before capacity is exhausted. |
| `GreenGatewayAuditFlushFailures` | warning | Observed failed-flush increase over 5 minutes, held for 2 minutes | [Audit](#audit-delivery): investigate durable sink failures and reconcile the affected window. |
| `GreenGatewayAuditDurabilityRefusals` | critical | Observed durability-refusal increase over 5 minutes, held for 2 minutes | [Audit durability refusals](#audit-durability-refusals): requests are being answered `503`; restore the audit store of record. |
| `GreenGatewayDatabasePoolSaturated` | warning | Waiting callers and zero available connections for 5 minutes | [Database capacity](#database-capacity): investigate query duration and connection limits. |
| `GreenGatewayDatabasePoolTimeouts` | warning | Observed timeout increase over 5 minutes, held for 2 minutes | [Database capacity](#database-capacity): inspect checkout errors and primary access. |
| `GreenGatewaySchemaIncompatible` | critical | Compatibility gauge zero for 1 minute | [Cluster authority](#cluster-authority): verify ledger and binary compatibility before any migration. |
| `GreenGatewayClusterHeartbeatStale` | warning | Published heartbeat age reaches 30 seconds for 1 minute | [Cluster authority](#cluster-authority): confirm authority access and roster state. |
| `GreenGatewaySecurityRevisionLag` | warning | Published lag remains positive on a serving replica for 5 minutes | [Cluster authority](#cluster-authority): inspect readiness, reconciliation failures and recent changes. |
| `GreenGatewayClusterConfigMismatch` | warning | Fingerprint mismatch remains set for 5 minutes | [Cluster authority](#cluster-authority): compare intended configuration and rollout strategy. |
| `GreenGatewayClusterMetricsMissing` | critical | Successful cluster scrape lacks a pool size, available or waiting gauge, 2 minutes | [Monitoring](#metrics-availability): verify mode labels, build and exporter filtering. |
| `GreenGatewayAuthorityEventCapacityRefusals` | critical | Observed capacity-refusal increase over 5 minutes, held for 2 minutes | [Authority-event journal](#authority-event-journal): a revocation, rotation or Connection delete did not happen; free journal room, then have it retried. |
| `GreenGatewayAuthorityEvidenceWriteFailures` | critical | Observed evidence-failure increase over 5 minutes, held for 2 minutes | [Authority evidence failures](#authority-evidence-failures): a revocation, rotation, Connection delete, admin session change, or policy, tools or catalog change did not happen; find why the database refused the evidence, then have the change retried. |
| `GreenGatewayAuthorityEventJournalFull` | critical | The current maintenance leader reports the journal's units in use (retained events plus units held for admin session withdrawals) at or above capacity for 1 minute | [Authority-event journal](#authority-event-journal): the next authority change will be refused; free room now. |
| `GreenGatewayAuthorityEventJournalFilling` | warning | The current maintenance leader reports the journal's units in use above 80% of capacity for 5 minutes | [Authority-event journal](#authority-event-journal): restore delivery or retention before the journal is full. |
| `GreenGatewayAuthorityEventDeliveryLag` | warning | With a dispatcher configured, a current maintenance leader with a recent retention success reports the oldest undelivered event older than 120 seconds, for 5 minutes | [Authority-event delivery](#authority-event-delivery): find the stalled sink or dispatcher. |
| `GreenGatewayAuthorityEventDeliveryFailures` | warning | Observed dispatcher failures other than `fenced` in every 5-minute window for 10 minutes | [Authority-event delivery](#authority-event-delivery): read the failing step's `kind` and the replica's log. |
| `GreenGatewayAuthorityEventJournalUnobserved` | warning | A scraped cluster deployment has no maintenance leader that exports the retained, capacity and oldest-age gauges with a retention success under 300 seconds old, for 10 minutes | [Authority-event journal](#authority-event-journal): restore the leader, its retention job or the exported gauges. |

The cluster rules select `deployment_mode="cluster"`; standalone deployments
must not be judged against PostgreSQL-only metrics. Optional revision metrics and
failure counters, seeded or not, are deliberately excluded from mandatory-signal checks. A missing
mandatory gauge produces a monitoring alert instead of being treated as zero.
Prometheus staleness and lookback behavior can delay missing-series detection;
the configured `for` interval starts when the expression first detects absence.

The heartbeat threshold assumes `CLUSTER_MEMBER_STALE_MS=30000`. Align it with
the deployed setting and heartbeat interval. The one-minute hold adds detection
delay beyond that threshold; it does not extend the gateway's readiness lease.
Pool pressure, revision lag and heartbeat warnings require lifecycle ready and a
successful scrape; they are suppressed during normal startup and drain. Schema
and configuration mismatch checks remain active during startup and drain when
scraping succeeds. Startup/drain allowances must also be reconciled with the
supervisor's deadlines:
a process killed before ten minutes is caught through availability monitoring,
not the lifecycle-stall rule. Audit loss remains relevant during drain; planned
maintenance must not suppress it merely because lifecycle readiness is zero.
Durability refusals are judged the same way, per replica and in both modes: each
one is a request the gateway answered `503`, whatever its lifecycle phase.

The authority-event rules also select `deployment_mode="cluster"`: standalone mode
has no journal. The two refusal counters are judged per replica, like audit loss,
and are not suppressed during startup or drain, because every increase is an
authority change that did not happen. The journal gauges describe one shared
table and are published only by a leader, while every former leader keeps
exporting its last reading. The journal rules therefore read the current
maintenance leader alone (`greengateway_cluster_maintenance_leader == 1`) and
alert once per deployment, without an `instance` label. Retained events fall only
when retention prunes them, so a leader whose retention keeps failing still
reports a lower bound, and the capacity rules keep using it. The delivery-lag rule
trusts the oldest-undelivered age only from a leader whose `authority_event_retention`
job succeeded within 300 seconds, which assumes the default
`CLUSTER_MAINTENANCE_INTERVAL_MS=60000`; scale it with the interval. When no
current leader publishes the three journal gauges with a recent retention success,
`GreenGatewayAuthorityEventJournalUnobserved` fires instead of letting a frozen or
missing reading pass as healthy. Its ten-minute hold covers a maintenance
handover and a restarted fleet's first pass.

A deployment without `AUTHORITY_EVENT_SINK` journals and retains events but
delivers none, so every retained event is undelivered by design
(`AUTHORITY_EVIDENCE_DURABILITY=required` refuses to start such a replica). The lag rule
judges delivery only where some scraped replica exports the dispatcher's lease age
or its failure counter: a configured dispatcher creates one of them on its first
term or its first failed attempt. A dispatcher that once claimed the cursor and
whose sink was later turned off creates neither, but its cursor still holds every
newer event, which the capacity rules then catch. The 120-second lag threshold
assumes a sink that normally keeps up within seconds: the dispatcher polls every
second and offers a refused batch again within 75 seconds at most. Set it from
your delivery objective.

## Readiness diagnosis

Read the affected replica's `/readyz` response, not a load-balanced response.
Healthy output is HTTP `200` with `{"status":"ready"}`. HTTP `503` returns one
coarse reason from the chain below; after fixing it, probe again because another
condition may have been masked by the earlier one.

| Reason, in evaluation order | Interpretation and action |
| --- | --- |
| `starting` / `draining` | Lifecycle phase; follow [Lifecycle](#lifecycle-stalls). |
| `contract_fenced` | The durable contract fence excludes this build, and nothing will reopen it; replace the replica with an eligible build ([the durable contract fence](postgres.md#the-durable-contract-fence)). |
| `config_fingerprint_mismatch` | Cluster static configuration has not agreed; follow the [rollout procedure](failover.md#gateway-replica-failure). |
| `storage_unavailable` | Authority access failed or this replica's session is read-only. First distinguish replica-local pool, connectivity, grant or query failures using [Database capacity](#database-capacity); use [failover](failover.md#database-primary-failure) only after confirming primary loss or a read-only primary. |
| `schema_incompatible` | Ledger integrity or binary/schema contract failed; follow [Cluster authority](#cluster-authority). |
| `instance_lease_invalid` | Heartbeat age reached `CLUSTER_MEMBER_STALE_MS`; check authority access and membership. |
| `security_revision_not_compiled` | Security admissions have been failing continuously beyond the reconcile grace; inspect current authority and reconciliation errors. Lag gauges alone cannot diagnose this. |
| `required_upstream_unavailable` | A configured required proxy pool is unavailable; follow [production data-plane health checks](production-data-plane.md#lifecycle-probes). |

The cluster-specific reasons do not exist in standalone mode. No alert in this
pack replaces the readiness probe or changes the gateway's fail-closed behavior.

## First-response runbooks

### Metrics availability

The platform on-call owns scrape and rule failures. Inspect Prometheus target
and rule health, then the affected replica's supervisor state and listener.
Confirm the opaque instance and mode match the expected inventory; check whether
metric relabeling removed required gauges. Restore instrumentation before
concluding the service is healthy. Do not remove a failed target from the
inventory to clear an alert. When replacing an instance intentionally, review
both inventory and scrape configuration together and verify the new target.

### Lifecycle stalls

The platform on-call checks startup logs, configuration validation and dependency
reachability. A startup failure can occur before any HTTP endpoint binds, so also
inspect supervisor restart/failure events. During a prolonged drain, inspect
`greengateway_inflight_requests`, stream shutdown and audit backlog, and compare
elapsed time with `SHUTDOWN_DRAIN_DELAY_MS`, `SHUTDOWN_TIMEOUT_MS` and the audit
drain budget. Follow [deliberate replica maintenance](failover.md#deliberate-replica-maintenance).
Do not force-kill solely to clear an alert: first assess unfinished work and audit
loss and preserve the bounded shutdown outcome.

### Audit delivery

The platform on-call restores sink availability and capacity; the security/audit
owner assesses any missing record window. Record the affected replica IDs,
timestamps and fixed failure classifications in restricted incident evidence.
Inspect sink errors and the configured storage path/primary, free space, locks
and latency. Growing oldest age indicates increasing delivery delay even when
depth is small; successful deliveries may continue while the sink falls behind.
Correlate successful-flush and failure/drop counters with sink logs to distinguish
slow progress from a stall. For PostgreSQL, use
[pool sizing](pool-sizing.md) and [failover](failover.md); for restoration, use
the [audit continuity checks](backup-and-recovery.md).

A drop-counter increase is actual loss; a counter reset or clearing alert does
not restore those events. Reconcile available durable records with the incident
window and document any unrecoverable gap. Do not disable audit, relax admission
controls, or silently discard the backlog to make monitoring green. Keep raw
audit payloads, tokens, provider addresses and detailed errors out of alert
annotations and shared incident summaries.

Under the default `AUDIT_DURABILITY=required`, the same sink failures also
refuse traffic; see [Audit durability refusals](#audit-durability-refusals).

### Audit durability refusals

The platform on-call restores the audit store of record; the security/audit
owner signs off on any change to the durability setting. Under the default
`AUDIT_DURABILITY=required` the gateway acts on an authentication or
authorization decision only once its record has committed to the audit store of
record: the SQLite database named by `AUDIT_SQLITE_PATH` in standalone mode,
`greengateway.audit_events` in cluster mode
([configuration](../configuration.md#audit_durability)). A request whose record
cannot commit is answered `503 audit_unavailable` before any upstream, tool or
handler work, and counted on `greengateway_audit_durability_refusals_total{reason}`.
`/readyz` stays `200`, so a load balancer keeps routing to the refusing replica:
this alert, not readiness, is what reports the outage.

Read the `reason` on the affected replica:

- `store`: the store refused or lost the batch. The flush-failure and drop
  counters and the sink's log line carry the cause; follow
  [Audit delivery](#audit-delivery), and in cluster mode
  [Database capacity](#database-capacity).
- `timeout`: the record did not commit within `AUDIT_DURABILITY_TIMEOUT_MS`
  (default `5000`). Look for a slow store or a saturated pool: the queue's oldest
  age and, in cluster mode, the pool gauges. The record may still commit after
  its request was refused.
- `admission`: the audit writer did not take the record, because its queue was
  full or its admission had closed for shutdown. Compare
  `greengateway_audit_queue_depth` with `_capacity`; a full queue is a sink that
  is not keeping up.

The first refusal of an episode, and the first success after it, are logged once
each. Service resumes on its own once the store commits again, and nothing needs
replaying, because a refused request was never acted on. Switching to
`AUDIT_DURABILITY=best_effort` to restore traffic trades the outage for decisions
that may never be recorded; it needs the audit owner's sign-off, and the window it
covers belongs in the incident record.

### Database capacity

The platform/database on-call compares the affected replica's `/readyz` reason
with its peers and checks `gateway cluster-members`, then the primary's connection
count and slow/blocked queries. Check replica-local pool pressure, connectivity,
grants and query failures; follow [pool sizing](pool-sizing.md) before raising
connection limits or timeouts. Restore a single writable authority using
[failover](failover.md) only after confirming primary loss or a read-only primary;
never direct security reads to a lagging replica.

### Cluster authority

For schema incompatibility, compare the running binary's contract with the
migration ledger using the [deployment procedure](postgres.md#schema-migrations).
Do not repair checksum failures by editing the ledger or enabling automatic
migrations. Follow the [rollback boundary](rollback-boundary.md): a backup is
not permission to rewind revocations or other security state for an older
binary. Use [disaster recovery](disaster-recovery.md) if authority state was lost.

For heartbeat or revision warnings, correlate authority errors, the roster and
readiness. A lag warning is an investigation trigger, not proof of stale
authorization. For configuration mismatch, compare the newcomer to the reviewed
configuration and either roll it back or deliberately drain the old generation
as described in [failover](failover.md#gateway-replica-failure). Do not bypass
fingerprint agreement to complete a rollout.

### Authority-event journal

The platform on-call frees journal room; the security on-call owns every refused
change. The journal keeps one row per committed Connection delete, service-token
rotate or revoke, JWT revoke and cluster admin session grant or withdrawal until a
sink has accepted it and `AUTHORITY_EVENT_RETENTION_HOURS` has passed, and holds one
more unit for the withdrawal of every admin session still signed in. At
`AUTHORITY_EVENT_JOURNAL_CAPACITY` units in use (`_retained`, which counts both) each
of those changes is refused and commits nothing, rather than evicting an accepted
event ([durable delivery](../authority-evidence.md#durable-delivery)); an admin
sign-in, which needs two units, is refused one unit earlier. A logout, a replacing
sign-in, a provider rejection and a session expiry are never refused: each spends
the unit its grant held ([admin session withdrawals](../authority-evidence.md#admin-session-withdrawals-and-journal-capacity)).
A refused revoke leaves the token or JWT live, so record the window and the
refusing replicas, and have each refused change retried once there is room.

Free room in this order: restore delivery so the cursor advances and retention can
prune (see [Authority-event delivery](#authority-event-delivery)); shorten
`AUTHORITY_EVENT_RETENTION_HOURS`; or raise `AUTHORITY_EVENT_JOURNAL_CAPACITY`.
Both settings are part of the static-configuration fingerprint, so change them on
every replica in one rollout, as [failover](failover.md#gateway-replica-failure)
describes for any fingerprint change. Compare `greengateway_authority_event_undelivered`
with `_retained` on the maintenance leader: undelivered close to retained means
delivery is the bottleneck, few undelivered means delivered events are waiting out
the retention window. `_reserved` is the part of `_retained` held for admin session
withdrawals: retention cannot free it, and it shrinks only as sessions end. A
dispatcher that once claimed the cursor stays a required
consumer after its sink is turned off; stop delivering deliberately as the durable
delivery section describes instead of waiting for retention. Never delete journal
or evidence rows by hand.

For `GreenGatewayAuthorityEventJournalUnobserved`, find the maintenance leader
(`greengateway_cluster_lease_age_seconds{scope="maintenance"}` above zero, or
`gateway cluster-members`), then read its
`greengateway_leader_task_last_success_age_seconds{task="authority_event_retention"}`
and `greengateway_cluster_maintenance_job_runs_total{job="authority_event_retention",outcome="failure"}`,
and check whether relabeling drops the journal gauges. With no leader, follow
[Cluster authority](#cluster-authority). A retention job that keeps failing cannot
free capacity, so treat it as the start of a filling journal.

### Authority evidence failures

The security on-call owns the refused changes; the platform or database on-call
finds the cause. The database refused or did not answer an evidence row or its
journal entry, so the change it described rolled back whole and was refused. There
is nothing to reconcile, because nothing committed, but the change did not happen:
a token or JWT that was to be revoked is still live, a Connection that was to be
deleted still exists, and a refused policy, tools or catalog change leaves the
previously active document or catalog enforcing.

The refusing replica's log names the failed operation and the classified store
error: `change_evidence_append` (Connection delete),
`service_token_change_evidence_append`, `jwt_revocation_evidence_append`,
`document_change_evidence_append` (policy and tools commits),
`catalog_change_evidence_append` (catalog and overlay publications) or
`authority_event_journal_append`. A missing grant or a schema that does not match
this binary refuses every such change, so compare the ledger with the binary first
([schema migrations](postgres.md#schema-migrations)); timeouts and unavailable
errors point to [Database capacity](#database-capacity). Once the cause is fixed,
have each refused change retried and confirm it with its evidence row. Never relax evidence
writing or edit the evidence tables to make a change go through.

### Authority-event delivery

The platform on-call restores delivery; the security/audit owner decides whether
the downstream system needs a backfill. Delivery runs outside every authority
transaction, so a stalled sink delays evidence but refuses nothing until the
journal fills. The leader of the dispatcher is the replica with
`greengateway_cluster_lease_age_seconds{scope="authority_event_dispatcher"}` above
zero; inspect its log and `greengateway_authority_event_delivery_failures_total{kind}`:

- `sink`: the sink refused the batch. For `AUTHORITY_EVENT_SINK=file`, check the
  file's directory, free space and permissions; for `log`, the log pipeline.
- `projection`: a journaled event cannot be delivered faithfully, so delivery is
  stalled at that position. The log names the position; this needs an engineering
  decision and is never fixed by skipping the event.
- `lease_acquire`, `cursor_claim`, `journal_read`, `cursor_advance`: authority
  access; follow [Database capacity](#database-capacity).

An oldest-undelivered age that climbs while the undelivered count does not fall is
a stall; one that climbs while the count falls is a sink that cannot keep up.
Delivery resumes from the persisted cursor and is at least once, so consumers
deduplicate on `(authority_id, event_id)`. Do not turn the sink off to clear the
alert: a dispatcher that once claimed the cursor keeps holding undelivered events,
and the journal then fills.

### Artifact verification failure

The release owner and security on-call handle provenance/SBOM/signature failures.
Stop promotion or deployment of the affected digest, retain the verification
result and reviewed source identity, and follow [Verifying image provenance and
retrieving the SBOM](../RELEASING.md#verifying-image-provenance-and-retrieving-the-sbom).
Distinguish unavailable evidence from a verified identity or digest mismatch;
neither is permission to bypass verification. A prior approved binary is an
option only within the documented schema/security rollback boundary. This is a
release-system signal, not an invented gateway runtime metric.

### Security incident

The security on-call leads when the trigger is a suspected compromise rather
than a failing signal: a leaked JWT or service token, an exposed upstream
credential, or a replica that is no longer trusted. Follow the
[security incident runbook](incident-rehearsal.md) to withdraw the identities,
rotate the affected Connection's secret reference, verify that every replica
compiled the resulting revision, collect sanitized evidence, and replace a
suspect replica with a verified image against the same database. A withdrawal
does not recall work or bytes already admitted; a hard stop is a controlled
drain plus upstream credential or network revocation, as that runbook states.

## Remaining operational proof

The pack does not yet cover every security-signal category in #440:

| Category | Current disposition |
| --- | --- |
| Egress denials | No dedicated bounded egress-policy denial counter. Use existing restricted audit evidence for investigation; client-cache or transport failure counters are not denial counts. A safe metric and workload-based informational trend remain follow-up work. |
| Authentication and authorization denials | No dedicated bounded denial counter for a complete trend. Audit outcomes remain the investigation source; denial volume alone does not establish an availability incident. Metric design and informational thresholds remain deferred. |
| Authentication/JWKS dependency availability | No dedicated bounded availability counter for the complete dependency path. Define an appropriate signal separately; do not infer identity-provider health from unrelated errors or expose issuer URLs in labels. |
| Rate-limit denials | `greengateway_rate_limit_shared_decisions_total` exists in cluster mode, with bounded `lane` labels and `outcome` values `allowed`, `denied`, `unavailable`. It covers shared-authority decisions, not every local rejection or standalone traffic. Informational denial-trend thresholds require a workload baseline and are deferred; `unavailable` is an authority failure, distinct from a deliberate denial. |
| Authority-change evidence outside the cluster journal | The rules cover the cluster-mode journal of [durable delivery](../authority-evidence.md#durable-delivery), admin session evidence included since migration 26, and a policy, tools or catalog change refused because its migration 23 evidence row could not be inserted pages through `greengateway_authority_event_evidence_failures_total`; that evidence is still neither journaled nor delivered. Standalone mode has no journal or dispatcher: its SQLite token, Connection and local-secret evidence commits in its store's own transaction, and a failed evidence insert refuses the change as that store's failure, with no dedicated counter. No authority-evidence durability mode makes an event sink mandatory yet ([issue #425](https://github.com/Greenhat-Security/GreenGateway/issues/425)). None of these gaps has a signal to alert on. The rules prove expression behaviour on synthetic series, not that a downstream system received the events. |

The disposable incident rehearsal for #440 is described in
[the security incident runbook](incident-rehearsal.md#what-the-release-gate-rehearses):
the `ha_security_two_replica` release-gate leg withdraws identities, rotates a
Connection's secret reference, checks revision convergence and the audit
evidence for secret material, and replaces a replica, on every pull request.
That rehearsal remains separate from the target-platform production exercise in
[issue #389](https://github.com/Greenhat-Security/GreenGateway/issues/389),
which must prove real alert delivery to the assigned responder and measure
detection, notification, acknowledgement and recovery times; the
[qualification kit's alert drill](qualification.md#8-alert-delivery) records
routing and rule timing for that exercise. Neither passing
`promtool` fixtures nor a disposable local rehearsal completes those operational
recovery objectives.

Durable loss records across restarts, independently observable background-task
freshness, and complete readiness reason metrics also require separate signal
design. Until they exist, use retained evidence and external readiness monitoring
for those gaps. Do not infer such signals from unrelated counters or put raw
dependency errors into labels.
